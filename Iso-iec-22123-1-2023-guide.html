0. この規格を一言でいうと

「クラウドの話をするときに、みんなが同じ意味で言葉を使えるようにするための"辞書"」 です。

  • 規格のスコープは1行だけで、クラウドコンピューティング分野で使われる用語を定義することです。
  • 「何をすべきか」を要求する規格（要求事項型）ではなく、用語集型の規格です。そのため「準拠認証を取る」という種類のものではありません。
  • 一方で、他のクラウド関連規格（アーキテクチャ、SLA、セキュリティなど）が共通で参照する土台になります。

Step 2: 2023年版で何が変わったか

規格の「まえがき」には、主な変更点が8つ書かれています。初学者は「何が"言葉の整理"として変わったのか」を押さえると理解が速いです。

# 変更点（要約） 初学者向けの意味
1 hybrid cloud の定義を変更 「プライベート＋パブリックを使う形」に整理された
2 CSC role / CSP role / CSN role を追加 「誰か」と「何をするか」を分けて考えられるようになった
3 CSC / CSP / CSN の定義を role ベースに改訂 「party が role を担う」という構造に統一
4 ISO/IEC 27000 由来の「機密性・完全性・情報セキュリティ」の定義を削除 セキュリティ用語は 27000 側を参照する方針
5 inter-cloud の定義を変更 「プライマリ CSP が他 CSP のサービスを使って提供する形」に整理
6 multi-cloud 関連用語を追加 マルチクラウドが正式な用語として定義された
7 peer cloud service(provider) → secondary cloud service(provider) に名称変更 「対等」ではなく「二次的（裏で使われる側）」という意味が明確に
8 「複数性と構成」に関する用語を新しい節（3.14）に追加 複数 CSP をまたぐ構成用語が独立した

Step 4: 基礎用語 ― cloud computing / cloud service / cloud solution

対応節: 3.1（用語は3つだけ）

用語 やさしい言い換え 押さえどころ
cloud computing ネットワーク経由で、伸縮自在で共有可能なリソースの集まりを、セルフサービスで、必要なときに使い・管理できるようにする考え方（パラダイム） リソースの例として、サーバー、OS、ネットワーク、ソフトウェア、アプリ、ストレージ装置が挙げられている
cloud service cloud computing を通じて提供される1つ以上の機能で、定められたインタフェースから呼び出せるもの 「機能」＋「インタフェース」がセット
cloud solution 複数の cloud service を組み合わせ、制御して、利用者の要件を満たす形にしたもの 配備モデルはどんな組み合わせでも使える

具体例で理解する

「社内の勤怠システムをクラウドで作る」場合:

  1. cloud service = 仮想マシン、マネージドDB、オブジェクトストレージ、認証サービス（それぞれ1つの"機能"）
  2. cloud solution = それらを組み合わせて勤怠システムとして成立させた全体
  3. cloud computing = そうした利用を可能にしている仕組み・考え方全体
💡

注意: 上の「仮想マシン」「勤怠システム」は理解のための例です。規格本文に製品名や具体例の記載があるわけではありません。

Step 5: 配備モデル（デプロイメントモデル）

対応節: 3.2（10用語：5-1 の cloud deployment model と、5-2・5-3 の9用語）

5-1. 配備モデル（cloud deployment model）とは

cloud deployment model は、「物理・仮想リソースの"制御（コントロール）"と"共有のされ方"によって、クラウドをどう構成するか」 の分類です。

5-2. 基本の4モデル

モデル 誰が使う？ リソースを誰が制御（コントロール）する？
private cloud 1つの CSC だけが専用に使う その CSC
public cloud 原則どの CSC でも使える CSP
community cloud 共通要件と関係性をもつ特定のグループだけが共有 グループ内の少なくとも1メンバー
hybrid cloud private と public の両方を使う （構成要素ごとに異なる）
💡

「制御」と「管理・運用」は別の観点です: 配備モデルを分けるのは、リソースを誰が制御するかです。日々の管理・運用（保守や監視など）は第三者に委託されていてもかまいません。たとえば、CSC が制御するリソースを外部事業者が管理・運用していても、そのクラウドは private cloud に該当し得ます。

5-3. 2023年版で整理された複数 CSP 系の配備モデルと関連用語

配備モデルは multi-cloud・hybrid multi-cloud・federated cloud・inter-cloud です。cloud service federation は配備モデルではなく、federated cloud の前提となる関係を表す関連用語です。

用語（種別） 要点
multi-cloud（配備モデル） CSC が、2社以上の CSP のパブリッククラウドサービスを使う。統合と管理の責任は CSC 側にある
hybrid multi-cloud（配備モデル） CSC が hybrid cloud と multi-cloud の両方のサービスを使う
cloud service federation（関連用語） 2つ以上の CSP が、合意したポリシー・プロセス・信頼で結びついてサービスを提供する関係（※モデルではなく"連合"という関係の名前）
federated cloud（配備モデル） federation のメンバーがサービスを提供する配備モデル
inter-cloud（配備モデル） CSP が、他の CSP のサービスを1つ以上使って自社サービスを提供する形。プライマリ CSP が仲介・集約・裁定（アービトラージ）などで提供することが多い、と注記されている

5-4. 「どのモデル？」判定フロー（簡易版）

このフローは private / public / community / hybrid / multi-cloud / hybrid multi-cloud の 6 モデルだけ を対象にした簡易版です。5-3 の federated cloud と inter-cloud は CSP 間の関係で決まるモデルのため、このフローの対象外です（違いは 5-6 を参照）。

5-5. 組み合わせの関係図

5-6. 「multi-cloud」と「inter-cloud」「federated cloud」の違い

ここが初学者が最も混同しやすいポイントです。**「誰が複数のクラウドをつないでいるか」**で整理します。

モデル 複数 CSP をつなぐのは誰？ CSC から見える CSP は？（実装依存の典型例）
multi-cloud CSC 自身 複数見える
inter-cloud プライマリ CSP（裏で他社のサービスを使う） 基本的にプライマリのみ
federated cloud CSP 同士（合意に基づく連合） 連合として提供される
⚠️

注意: 「CSC から見える CSP は？」の列は、理解のための典型的な見え方の例示です。どの CSP がエンドポイントとして CSC に見えるかは構成・契約などの実装に依存し、ISO/IEC 22123-1 が定めているものではありません。

💡

ベストプラクティス: 設計書やRFPで「マルチクラウド」と書く場合、**「CSC が統合責任を持つ前提か」**を明記すると、inter-cloud や federated cloud との取り違えを防げます。

Step 6: 役割と関係者（party / role / CSC / CSP / CSN）

対応節: 3.3（16用語）

6-1. まず「party」と「role」を分ける（2023年版の重要ポイント）

用語 意味 例えるなら
party 自然人・法人・それらのグループ。1つ以上の role を担える 「人・組織」そのもの
role 共通の目的をもつ活動（activity）の集合 「帽子」
sub-role role の活動の部分集合 「帽子の一部の機能」
activity 特定の営み、またはタスクの集まり 個別の作業
functional component 活動に必要な機能的な構成要素（実装に裏付けられる） 作業に使う部品

同じ会社が、あるときは CSC role、別のときは CSP role を担うことがあります（例: 自社でクラウドを使いつつ、顧客向けにもクラウドサービスを提供する場合）。

6-2. 3つの主役

party を表す用語（CSC / CSP / CSN）と、role を表す用語（CSC role / CSP role / CSN role）は、それぞれ独立した用語として定義されています。

用語 種別 意味
CSC（cloud service customer） party CSC role を担う party
CSP（cloud service provider） party CSP role を担う party
CSN（cloud service partner） party CSN role を担う party
CSC role role クラウドサービスを使うための活動の集合
CSP role role クラウドサービスを利用可能にする活動の集合
CSN role role CSP role や CSC role（または両方）を支援・補助する活動の集合

6-3. その他の関係者と関連用語

用語 意味
CSU（cloud service user） CSC に紐づいて cloud service を実際に使う自然人、またはその代理主体（デバイスやアプリケーションも含まれ得る）
cloud auditor CSN の一種。クラウドサービスの提供・利用について監査する責任をもつ
cloud service broker CSN の一種。CSC と CSP の関係を取りもつ（交渉する）
cloud service developer CSN の一種。cloud service の設計・開発・テスト・保守に責任をもつ
device platform cloud service デバイスプラットフォーム提供者が、そのデバイスプラットフォームを支えるために提供する cloud service（例: アプリマーケットプレイス）

6-4. 関係図

6-5. 具体例

場面 CSC CSP CSN
自社システムをパブリッククラウドへ移行 自社 クラウド事業者 移行支援ベンダー（支援）、第三者監査法人（auditor）
SaaS を従業員が利用 自社（契約主体） SaaS 事業者 代理店（broker 的な役割になり得る）
自社が提供するクラウドアプリを外部の顧客が利用 顧客企業（契約主体）。その従業員などのアプリ利用者は CSU 自社（CSP role を担う） ―
💡

注意: 上表の具体例は理解用の例示で、規格本文の記載ではありません。

Step 7: クラウドの主要特性

対応節: 3.4（5用語）

用語 やさしい言い換え 実務での確認ポイント
on-demand self-service CSC が、必要なときに、自動で／CSP とほぼやり取りせずコンピューティング能力を用意できる コンソールや API で即時に払い出せるか
resource pooling CSP が持つ物理・仮想リソースをまとめて、1つ以上の CSC に提供する 専有ではなく共有プールから提供される前提
measured service 利用量が計測され、監視・制御・報告・課金できる形でサービスが提供される 使用量メトリクスと請求が連動しているか
tenant 物理・仮想リソースの集合へのアクセスを共有する1人以上の CSU 「テナント＝契約単位」とは限らず、利用者の集合として定義
multi-tenancy 複数のテナントとその計算・データが、互いに隔離され、相互にアクセスできないようにリソースを割り当てること 隔離の仕組みとレベルの確認が重要
💡

補足: NIST SP 800-145 は「broad network access」「rapid elasticity」を含む5つの本質的特性を挙げています。22123-1 の 3.4 節に収録されているのは上の5用語で、特性の数え方が NIST と一致しているわけではないことに注意してください（詳細は「NIST との比較」参照）。ただし 22123-1 の cloud computing の定義自体に「scalable and elastic（伸縮自在）」「network access」が含まれています。

Step 8: 能力タイプとサービスカテゴリ（IaaS / PaaS / SaaS ほか）

対応節: 3.5（12用語）

8-1. 2階層で整理されている

22123-1 は、サービス分類を2階層で考えます。

  1. cloud capabilities type（能力タイプ）: 使われるリソースの種類に基づく大分類（3種類）
  2. cloud service category（サービスカテゴリ）: 共通の性質を持つクラウドサービスのグループ（1つ以上の能力タイプを含み得る）

8-2. 能力タイプ（3種類）

能力タイプ CSC にできること
application capabilities type CSP のアプリケーションを使う
infrastructure capabilities type 処理・ストレージ・ネットワークリソースをプロビジョニングして使う
platform capabilities type CSP がサポートする言語・実行環境で、自作／調達したアプリをデプロイ・管理・実行する

8-3. サービスカテゴリ（7種類）

カテゴリ 略称 内容 能力タイプとの関係
infrastructure as a service IaaS 提供されるのが infrastructure capabilities type infrastructure
platform as a service PaaS 提供されるのが platform capabilities type platform
software as a service SaaS 提供されるのが application capabilities type application
communications as a service CaaS リアルタイムのやり取りと協働 application と platform の両方を提供し得る
compute as a service CompaaS ソフトウェアのデプロイ・実行に必要な処理リソースの提供と利用 注記: 他の能力が別途必要な場合がある
data storage as a service DSaaS データストレージと関連機能の提供と利用 3種類のどれでも提供し得る
network as a service NaaS 通信の接続性と関連ネットワーク機能 3種類のどれでも提供し得る
ℹ️

実線は「そのカテゴリそのもの／注記で明示された組み合わせ」、点線は「3種類のどれでも提供し得る」を表します。ラベル付きの点線（infrastructure → CompaaS）は、CompaaS が提供する処理リソースが infrastructure capabilities type の処理リソースに相当することを示す目安です。規格は CompaaS の能力タイプを明示しておらず、他の能力が別途必要な場合があります（8-3 の注記）。

8-4. IaaS の責任範囲（規格が書いている部分）

IaaS の注記では、CSC は基盤となる物理・仮想リソースを管理も制御もしないが、OS・ストレージ・デプロイしたアプリケーションは制御できると述べられています。ホストファイアウォールなどネットワークの一部を限定的に制御できる場合もあります。

8-5. 責任範囲の目安（※一般的な理解。規格本文の表ではありません）

レイヤー IaaS PaaS SaaS
アプリケーションのデータ・設定 CSC CSC CSC（設定の範囲内）
アプリケーション本体 CSC CSC CSP
ランタイム・ミドルウェア CSC CSP CSP
OS CSC CSP CSP
仮想化基盤・物理機器 CSP CSP CSP
⚠️

注意: 実際の責任分界は各 CSP のサービスごと・契約ごとに異なります。上表は初学者が全体像をつかむための一般的な目安です。

Step 9: 相互運用性と可搬性

対応節: 3.6（相互運用性）／ 3.8（可搬性）

9-1. 2つの違い

概念 一言で 場面
interoperability（相互運用性） つないで一緒に動かせるか 稼働中のシステム同士が情報を交換し、使い合えるか
portability（可搬性） 移して動かせるか データやアプリを別の環境へ移せるか

9-2. 相互運用性の5つの観点

用語 確認する観点 たとえ
transport interoperability 確立された通信基盤で情報をやり取りできるか 電話回線がつながるか
syntactic interoperability 交換する情報の形式を相手が理解できるか 同じ文字コード・フォーマットか
semantic data interoperability データモデルの意味を相手が理解できるか 「顧客」という言葉が同じ意味か
behavioural interoperability やり取りの結果が期待どおりになるか 依頼した処理が想定どおり動くか
policy interoperability 双方に適用される法令・組織・ポリシーを守れるか 個人情報保護の要件を満たすか

さらに、一般用語の cloud interoperability は「CSC のシステムがクラウドサービスと、またはクラウドサービス同士が、定められた方法で情報を交換し予測可能な結果を得られる能力」と定義されています。

9-3. 可搬性の整理

可搬性はデータとアプリケーションの2系統です。観点は、data portability が 3つ（syntactic・semantic・policy）、application portability が 5つ（syntactic・instruction・metadata・behaviour・policy）です（下表の cloud data portability / cloud application portability は、クラウドサービス間に限定した一般用語です）。

系統 用語 観点
データ data portability 再入力なしで容易に別システムへ移せる（紙に出して打ち直すのは「容易」とは言えない、と注記されている）
データ cloud data portability あるクラウドサービスから別のクラウドサービスへの data portability
データ data syntactic portability 移行先でデコードできる形式か
データ data semantic portability 移行先でデータモデルの意味が理解されるか
データ data policy portability 移行元・移行先の法令・ポリシーを守れるか
アプリ application portability 移行元システムから移行先システムへ移せる
アプリ cloud application portability あるクラウドサービスから別のクラウドサービスへの移行
アプリ application syntactic portability アプリの成果物（artefact）の形式を移行先でデコードできる
アプリ application instruction portability 命令セットが移行先で実行できる
アプリ application metadata portability メタデータが移行先で保持・理解される
アプリ application behaviour portability 移行先で同等の結果が得られる
アプリ application policy portability 移行元・移行先の法令・ポリシーを守れる
💡

ベストプラクティス: 相互運用性の5つの観点（transport・syntactic・semantic data・behavioural・policy）と可搬性の各観点は、互いに独立した観点です。規格は確認する順序や深さの階層を定めていません。移行計画やマルチクラウド設計で、観点ごとに「どこまで確認したか」を整理するチェックリストとして使えます。

Step 10: サービス契約まわりの用語（SLA / SLO / SQO）

対応節: 3.7（11用語）

10-1. 用語の整理

用語 意味（要約）
service level agreement (SLA) サービス提供者と顧客の間で、サービスとサービス目標を特定する文書化された合意（一般的な SLA）
cloud service agreement CSP と CSC の間で、対象の cloud service を統制する文書化された合意。複数の文書にまたがってもよい
cloud service level agreement (cloud SLA) cloud service agreement の一部で、SLO と SQO を含むもの
cloud service level objective (cloud SLO) CSP が約束する、定量的な特性（間隔尺度・比率尺度の値）。範囲で表現し得る
cloud service qualitative objective (cloud SQO) CSP が約束する、定性的な特性（名義尺度・順序尺度の値）。列挙リストで表現し得る。人の解釈が要る場合が多い
metric 測定の条件とルール、結果の解釈を定める測定の標準
cloud service product cloud service と、それが提供されるビジネス条件（価格、評価、サービスレベルなど）をセットにしたもの
product catalogue CSP が CSC に提供するcloud service product の一覧
service catalogue ある CSP のcloud service の一覧
failure notification policy サービス停止の連絡方法（誰がどう通知し、更新をどう伝えるか）を定める方針
remedy CSP が SLO を満たせなかった場合に CSC が受け取れる補償

10-2. 包含関係

10-3. SLO と SQO の見分け方

観点 SLO SQO
性質 定量的 定性的
値の尺度 間隔尺度・比率尺度 名義尺度・順序尺度
表現の例 範囲（上限・下限） 列挙リスト、有無（existence / nonexistence）
解釈 数値で機械的に判定しやすい 人の解釈が必要になりやすい
💡

ポイント: 「99.9% 以上の可用性」のように数値で測れる約束が SLO、「暗号化に対応している」のように有無や分類で表す約束が SQO というイメージで整理すると理解しやすくなります（この具体例は理解用で、規格本文のものではありません）。

Step 11: クラウドデータの分類

対応節: 3.9（本文で確認できた範囲: 3.9.1〜3.9.4）

クラウド上のデータを「誰が管理権をもつか」と「どこから生じたか」で分類しています。

用語 管理権 何のデータか
cloud service customer data CSC 法的その他の理由で CSC の管理下にあるデータのうち、CSC が cloud service に入力した、または CSC（または代理）が公開インタフェースを通じてサービスの機能を使った結果として生じたもの
cloud service derived data CSP CSC が cloud service を使った結果として派生したデータ（利用ログ、設定・カスタマイズ情報など）
cloud service provider data CSP cloud service の運用に固有のデータ（リソース構成・利用状況、仮想マシンの割り当てなど）
account data CSP cloud service を管理するために必要な、CSC ごとに固有のデータ

注記から学べる重要ポイント

  • cloud service が、CSP が用意したデータや公開データを扱うことがあり、それらは customer data ではない場合がある。
  • ただし CSC が操作して生み出した出力データは、著作権の一般原則に従って多くの場合 customer data になり得る。ただし cloud service agreement に別段の定めがあればそちらが優先される、と注記されている。
⚠️

実務での注意: 「利用ログは CSP が管理するデータ（derived data）」という整理は、ログの閲覧・エクスポート・保存期間をどう契約に書くかを考えるきっかけになります。データの扱いは必ず cloud service agreement で確認してください。

NIST SP 800-145（2011年）との比較

NIST SP 800-145 は Peter Mell 氏と Timothy Grance 氏による文書で、5つの本質的特性・3つのサービスモデル・4つの配備モデルを整理した、広く参照されている定義です。

観点 NIST SP 800-145（2011） ISO/IEC 22123-1:2023
性質 米国 NIST の特別刊行物（約7ページ） 国際規格（ISO カタログ・IEC Webstore では16ページ、SIS では18ページ）。用語集の形式
特性 on-demand self-service / broad network access / resource pooling / rapid elasticity / measured service 3.4 節に on-demand self-service / resource pooling / measured service / tenant / multi-tenancy。elastic・network access は cloud computing の定義に含まれる
サービスモデル SaaS / PaaS / IaaS（3つ） 能力タイプ3種＋サービスカテゴリ（IaaS / PaaS / SaaS に加え CaaS / CompaaS / DSaaS / NaaS）
配備モデル private / community / public / hybrid（4つ） 4つに加え multi-cloud / hybrid multi-cloud / federated cloud / inter-cloud など
役割 （用語としては限定的） party / role / CSC / CSP / CSN / CSU を体系化
契約・データ・可搬性 範囲外 SLA／SLO／SQO、データ分類、可搬性・相互運用性を定義
更新 2011年9月発行。大きな更新なし（第三者の解説による） 2023年2月発行

注意すべき違い: 「hybrid cloud」

出典 hybrid cloud の捉え方
22123-1:2023 private cloud と public cloud を使う配備モデル
米国財務省 Shared Cloud Lexicon（NIST 系の定義を踏襲） 2つ以上のクラウド（オンサイト／オフサイトの private・community、public）が別々の存在のまま結び付いた構成

「hybrid」という同じ言葉でも、組み合わせる対象の範囲が異なるため、文書で使うときはどの定義に従うかを明記すると安全です。

欧州での採用状況

ISO/IEC 22123-1:2023 は、欧州規格 EN ISO/IEC 22123-1:2026 として最終版が2026年4月に公開されました。これは技術内容を変えない同一採用です。CENELEC の公表一覧に記載された日付は次の意味です。

略語 意味 日付
DAV（date of availability） EN の確定版が利用可能になった日 2026-04-08
DOP（date of publication） 各国が同一の国家規格として出版するか、承認（endorsement）する期限 2026-10-31
DOW（date of withdrawal） 内容の矛盾する国家規格を廃止する期限 2026-10-31

DOP は各国が採用を完了しなければならない期限の上限であり、各国の実際の採用日（国家規格としての発効日）は国ごとに異なります（下記の例を参照）。

これとは別に、DIN は最終版に先立つ草案 prEN ISO/IEC 22123-1:2025（DIN EN ISO/IEC 22123-1:2026-02 草案）を2026年1月に公開していました。DIN ISO/IEC 17788:2016-04 からの変更点として、hybrid cloud の定義変更、CSC／CSP／CSN role の追加、multi-cloud 関連用語の追加などが挙げられています。

調査時点では各国での採用も始まっています。たとえばエストニアの EVS-EN ISO/IEC 22123-1:2026（2026年4月15日から有効）、スペインの UNE-EN ISO/IEC 22123-1:2026（2026年5月承認）があります。

開発者・アーキテクトの視点（ロックインの議論）

22123-1 の multi-cloud／portability／interoperability は、実務のロックイン（囲い込み）の議論と強く結びつきます。

Gregor Hohpe 氏（『The Software Architect Elevator』著者）の整理

Gregor Hohpe 氏は、Martin Fowler 氏のサイトに掲載された記事 "Don't get locked up into avoiding lock-in" で、ロックインを単純な真偽ではなく多面的なものとして整理しています。氏自身のブログによれば、ロックインは次の観点に分解できます。

ロックインの観点 例えるなら
vendor lock-in 特定ベンダーへの依存
product lock-in 特定製品への依存
version lock-in 特定バージョンへの依存
architecture lock-in 特定アーキテクチャへの依存
platform lock-in 特定プラットフォームへの依存
skill lock-in 特定スキルセットへの依存
legal lock-in 契約・法的な拘束
mental lock-in 思い込みによる固定化

さらに氏は、ロックインを避けると別のロックインに入ってしまうことがあるため、「避ける」より切り替えコストと選択肢のコストを総合的に判断すべきだと論じています。

22123-1 の用語との対応

💡

実務上のポイント: 「マルチクラウドにすればロックインを回避できる」とは限りません。22123-1 の multi-cloud の注記は、統合と管理の責任が CSC 側に移ることを明示しています。相互運用性の5観点と可搬性の観点（データは3観点、アプリケーションは5観点）で何を確保するかを決めたうえで、コストと比べて判断するのが現実的です。

Ivan Pepelnjak 氏（ネットワークエンジニア／ipSpace.net）も、Hohpe 氏の連載の「ロックインの色合い（shades of lock-in）」の部分を必読として紹介しています。
