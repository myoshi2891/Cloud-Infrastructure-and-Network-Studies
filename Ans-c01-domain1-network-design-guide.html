ステップ 1: なぜエッジサービスが必要か

ユーザーが地球の反対側にあるリージョンのアプリケーションへ直接アクセスすると、次の問題が起きます。

  • 物理的な距離による遅延 (往復時間) が大きい
  • TCP と TLS のハンドシェイクで何度も往復するため、遅延が何倍にも膨らむ
  • インターネット経路は混雑や障害の影響を受け、品質が安定しない

エッジサービスは、ユーザーの近くで通信を受け止め、そこから先を AWS のグローバルバックボーンネットワークで運ぶことで、これらを改善します。

ステップ 2: Amazon CloudFront を理解する

CloudFront は HTTP と HTTPS のコンテンツを世界中のエッジロケーションでキャッシュして配信する CDN です。静的コンテンツだけでなく、動的コンテンツや API の高速化にも使えます。

オリジン コンテンツの取得元。S3、ALB、API Gateway、EC2、オンプレミスのサーバーなど

キャッシュを制御する 3 つのポリシー

ポリシー 役割 設計の考え方
キャッシュポリシー キャッシュキー (何を同一リクエストとみなすか) と TTL を決める キャッシュキーに含める要素は必要最小限にして、ヒット率を上げる
オリジンリクエストポリシー キャッシュキーには含めないが、オリジンに転送する情報を決める 認証ヘッダーなどを転送しつつ、キャッシュは分断させない
レスポンスヘッダーポリシー CORS やセキュリティヘッダーを付与する HSTS などをエッジで一括付与する

オリジンのアクセス保護

  • S3 オリジンには、Origin Access Control (OAC) を使い、CloudFront 経由でのみ S3 を読めるようにする。旧方式の OAI よりも、SSE-KMS やすべてのリージョンへの対応など機能が広い。
  • ALB や EC2 オリジンを、インターネットに公開せずに CloudFront の背後に置きたい場合は、VPC オリジンを使う。プライベートサブネット内のリソースをオリジンにできる。
  • VPC オリジンを使わない構成では、ALB のセキュリティグループで CloudFront のマネージドプレフィックスリスト (com.amazonaws.global.cloudfront.origin-facing) を許可し、さらに CloudFront からカスタムヘッダー (秘密の値) を付けて ALB 側で検証する、という二重の防御が定番。 
# CloudFront から ALB への通信だけを許可するセキュリティグループルールの例
# (プレフィックスリスト ID は pl- で始まる値を、リージョンごとに確認して指定する)
aws ec2 authorize-security-group-ingress \
  --group-id sg-0123456789abcdef0 \
  --ip-permissions 'IpProtocol=tcp,FromPort=443,ToPort=443,PrefixListIds=[{PrefixListId=pl-xxxxxxxx}]'

配信コンテンツの保護

手段 用途
署名付き URL と署名付き Cookie 有料コンテンツなど、特定ユーザーだけに配信する。信頼されたキーグループで署名する
AWS WAF SQL インジェクション、レートベースルール、Bot 対策などの L7 防御
AWS Shield Standard は CloudFront で自動適用。より高度な保護は Shield Advanced
地理的制限 国単位で配信を許可または拒否する
フィールドレベル暗号化 特定のフォーム項目をエッジで公開鍵暗号化し、オリジンの手前までは復号できないようにする
TLS 設定 視聴者からエッジの間と、エッジからオリジンの間の両方で HTTPS を強制する

落とし穴: CloudFront のカスタムドメインに使う ACM 証明書は、バージニア北部リージョン (us-east-1) で発行する必要があります。ALB 用の証明書は ALB と同じリージョンで発行します。この違いは頻出です。

エッジでの処理 (CloudFront Functions と Lambda@Edge)

項目 CloudFront Functions Lambda@Edge
実行タイミング ビューアーリクエストとビューアーレスポンス ビューアーとオリジンの両方向、計 4 か所
用途 URL の書き換え、ヘッダー操作、簡単なリダイレクトなど軽量処理 認証、外部呼び出し、複雑な処理
特徴 非常に低レイテンシーで低コスト。ネットワークアクセスは不可 処理能力が高く柔軟。Lambda は us-east-1 で作成する

可用性を高める機能

  • オリジンフェイルオーバー: プライマリとセカンダリのオリジンをオリジングループにまとめ、特定のステータスコードやタイムアウトで自動的に切り替える。読み取り系メソッド (GET、HEAD、OPTIONS) が対象。
  • Origin Shield: オリジンへのリクエストを集約し、オリジンの負荷とコストを減らす。オリジンに最も近いリージョンを選ぶ。
  • 継続的デプロイ: ステージング用ディストリビューションで、一部のトラフィックだけに新設定を試せる。

運用とコスト

  • 無効化 (インバリデーション) は便利だが、頻繁に行うのは避け、ファイル名にバージョンを含める運用 (例: app.v2.js) を優先する。
  • 料金クラスで、配信するエッジロケーションの範囲を絞ってコストを下げられる。
  • AWS オリジンから CloudFront へのデータ転送は課金されない。CloudFront を前段に置くと、転送コストの面でも有利になることが多い。

ステップ 3: AWS Global Accelerator を理解する

Global Accelerator は、2 つの静的なエニーキャスト IP アドレスを提供し、ユーザーを最寄りのエッジから AWS のバックボーン経由で最適なリージョンのエンドポイントへ導くサービスです。CloudFront と違い、キャッシュはしません。

主な概念

用語 意味
アクセラレーター 静的 IP アドレスを持つ、Global Accelerator の本体 (標準とカスタムルーティングの 2 種類)
リスナー ポート範囲とプロトコル (TCP または UDP) を指定して、受信接続を待ち受ける
エンドポイントグループ リージョンごとのエンドポイントの集まり。トラフィックダイヤルで、リージョンへの配分割合を調整できる
エンドポイント ALB、NLB、EC2 インスタンス、Elastic IP アドレス
ヘルスチェックとフェイルオーバー 異常なエンドポイントから自動で切り離す。DNS の TTL に依存しないため切り替えが速い

標準アクセラレーターとカスタムルーティングアクセラレーター

種類 特徴 典型的な用途
標準 最も近い正常なエンドポイントへ振り分ける Web アプリ、API、一般的な TCP と UDP アプリ
カスタムルーティング アプリが決めた特定の EC2 インスタンスとポートへ確定的に振り分ける ゲームのセッション割り当て、VoIP

設計上のポイント

  • 固定 IP アドレスが必要な場合 (取引先のファイアウォールで許可 IP を固定したいなど) に強い。
  • クライアント IP アドレスの保持に対応するエンドポイントがある (詳細はドキュメントで確認)。
  • トラフィックダイヤルで、リージョン間の段階的な切り替えやメンテナンスができる。
  • BYOIP (自前の IP アドレス範囲の持ち込み) に対応している。
  • ブルーグリーンのリージョン切り替えや、DR のフェイルオーバーに向く。

補足: インバウンドとアウトバウンドの両方向を意識する

試験ガイドのスキルは「グローバルな受信と送信トラフィックの要件を評価する」と書かれています。

  • 受信 (ユーザーからアプリ): CloudFront や Global Accelerator で最適化する
  • 送信 (アプリからユーザーやインターネット): 大きなコンテンツの配信は CloudFront で行い、オリジンからのデータ転送コストを抑える。プライベートサブネットからのインターネット向け通信は NAT ゲートウェイや、集約したエグレス VPC を使う (Task 1.6 を参照)
  • ユーザーからの大容量アップロードには、S3 Transfer Acceleration もエッジロケーションを活用する選択肢になる

ステップ 1: DNS の基礎

DNS は「名前 (www.example.com)」を「IP アドレス」に変換する分散データベースです。

TTL (Time To Live)

  • リゾルバーが応答をキャッシュしておく秒数。
  • TTL を長くすると、問い合わせ回数が減って高速になるが、変更の反映が遅れる。
  • TTL を短くすると、変更やフェイルオーバーの反映は速いが、問い合わせ回数が増える。
  • 移行作業の前に TTL を短くしておき、切り替え後に戻す運用が定番。

ゾーンと委任

  • ゾーン: 一つの管理主体が管理する DNS 名前空間の範囲。
  • 委任: 親ゾーンに NS レコードを置いて、サブドメイン (例: dev.example.com) の管理を別のゾーンや別のアカウントに任せること。
  • 委任セット: 同じ 4 つのネームサーバーを複数のゾーンで再利用できる Route 53 の機能。

DNSSEC

DNSSEC は、DNS の応答が改ざんされていないことを、デジタル署名で検証できるようにする仕組みです。

  • 署名鍵を使ってレコードに署名し、親ゾーンに登録した DS レコードを起点に、信頼の連鎖で検証する。
  • Route 53 では、AWS KMS の非対称カスタマーマネージドキー (us-east-1 に作成、ECC_NIST_P256) をキー署名鍵 (KSK) として使う。
  • 有効化の流れは、(1) 署名を有効化、(2) 親ゾーン (レジストラ) に DS レコードを登録、の 2 段階。
  • ベストプラクティスとして、有効化前に TTL を短くし、署名に関するエラーのアラームを設定しておく。鍵の管理を誤ると、名前解決が失敗する可能性がある。
  • Route 53 Resolver には、DNSSEC の検証を有効にする機能もある (署名検証の失敗した応答を拒否できる)。

ステップ 2: Route 53 の主要機能

ホストゾーン

種類 用途 特徴
パブリックホストゾーン インターネットに公開する名前 世界中の DNS リゾルバーから問い合わせ可能

プライベートホストゾーンの要点

  • VPC の設定で、DNS ホスト名と DNS 解決 (enableDnsHostnames と enableDnsSupport) を両方有効にする必要がある。
  • パブリックと同名のプライベートゾーンを作ると、関連付けた VPC 内ではプライベートが優先される。内部と外部で違う答えを返す「スプリットビュー DNS」を実現できる。
  • 別アカウントの VPC を関連付けるには、ホストゾーンのあるアカウントで関連付けの承認を作成し、VPC 側のアカウントで関連付ける (CLI か API で行う)。 
# 1. ゾーンを持つアカウント側で、別アカウントの VPC の関連付けを承認する
aws route53 create-vpc-association-authorization \
  --hosted-zone-id Z0123456789ABCDEFGHIJ \
  --vpc VPCRegion=ap-northeast-1,VPCId=vpc-0123456789abcdef0

# 2. VPC を持つアカウント側で、VPC をホストゾーンに関連付ける
aws route53 associate-vpc-with-hosted-zone \
  --hosted-zone-id Z0123456789ABCDEFGHIJ \
  --vpc VPCRegion=ap-northeast-1,VPCId=vpc-0123456789abcdef0

トラフィックポリシー (Traffic Flow)

ステップ 3: ハイブリッド DNS (Route 53 Resolver)

VPC には、Amazon が提供する DNS リゾルバー (VPC の CIDR のベースアドレス + 2、または 169.254.169.253) があり、標準で VPC 内の名前解決を行います。オンプレミスとの間で名前を相互に解決するために、Resolver エンドポイントを使います。

コンポーネント 方向 役割
インバウンドエンドポイント オンプレミス から AWS オンプレミスの DNS が、VPC 内の IP アドレス宛てに転送すると、プライベートホストゾーンなどの名前を解決できる
アウトバウンドエンドポイント AWS から オンプレミス 転送ルールに従って、特定ドメインの問い合わせをオンプレミスの DNS サーバーへ送る

Resolver の設計ポイント

  • エンドポイントは、高可用性のため、複数の AZ に IP アドレス (ENI) を配置する (最低 2 つ)。
  • エンドポイントのセキュリティグループで、DNS のポート (UDP と TCP の 53。暗号化 DNS を使う場合は 853 や 443) を許可する。
  • 転送ルールは AWS RAM で複数アカウントに共有できる。一方、ルールの関連付けは VPC ごとに必要。
  • ルールは、最も具体的なドメイン名のものが優先される。
  • 1 つの ENI あたりの問い合わせ処理能力には上限がある。VPC の Amazon 提供 DNS には、ENI あたり 1 秒間 1,024 パケットの上限があるため、大量の問い合わせがある環境ではキャッシュや分散を考える。
  • Route 53 Resolver DNS Firewall で、ドメインリストに基づいて VPC からの DNS 問い合わせをフィルタリングできる (ドメイン 4 でも登場)。

ステップ 4: Route 53 によるグローバルトラフィック管理

  • レイテンシールーティングで、ユーザーに最も遅延の小さいリージョンへ誘導する。
  • フェイルオーバーとヘルスチェックで、リージョン障害時にセカンダリへ切り替える。
  • 位置情報ルーティングで、データ主権や言語に応じて振り分ける。
  • DNS ベースの制御は、リゾルバーのキャッシュ (TTL) により、切り替え完了までに時間差が出る点に注意する。即時性が重要なら、Global Accelerator と組み合わせる。

ステップ 6: ドメイン登録

  • Route 53 は、ドメインレジストラーとしてドメインの登録、更新、移管を行える (Route 53 を通じて登録すると、パブリックホストゾーンが自動的に作られる)。
  • 他社のレジストラーで登録したドメインでも、Route 53 のホストゾーンを使える。その場合、レジストラー側のネームサーバーを、Route 53 のホストゾーンに表示される 4 つの NS 値に変更する (委任)。
  • 運用上の要点は、自動更新の有効化、転送ロック (不正な移管の防止)、WHOIS 情報のプライバシー保護、DNSSEC を使う場合の DS レコード登録。
  • ドメインの移管には認証コードが必要。
  • 登録、更新、移管の API は、バージニア北部 (us-east-1) のエンドポイントを使う。

ステップ 1: ロードバランサーの種類を理解する

Elastic Load Balancing (ELB) には、主に次の 3 種類の現行ロードバランサーがあります (Classic Load Balancer は旧世代)。

種類 動作する層 主なプロトコル 得意なこと
Application Load Balancer (ALB) L7 HTTP、HTTPS、gRPC、WebSocket パスやホスト名によるルーティング、認証、WAF 連携
Network Load Balancer (NLB) L4 TCP、UDP、TLS 超低遅延、高スループット、静的 IP、送信元 IP の保持、PrivateLink
Gateway Load Balancer (GWLB) L3 のゲートウェイと L4 の負荷分散 IP パケット (GENEVE でカプセル化) ファイアウォールや IDS などの仮想アプライアンスの透過的な挿入

ALB の詳細

  • リスナールールの条件として、ホスト名、パス、HTTP ヘッダー、HTTP メソッド、クエリ文字列、送信元 IP を使える。
  • アクションは、転送、リダイレクト、固定レスポンス、認証 (Amazon Cognito または OIDC 対応の IdP) など。
  • ターゲットの種類は、インスタンス、IP アドレス、Lambda 関数。
  • 加重ターゲットグループで、ブルーグリーンデプロイやカナリアリリースができる。
  • AWS WAF を直接関連付けられる。
  • 静的 IP アドレスは持たない (ノードの IP は変わるため、必ず DNS 名を使う)。クライアントの IP は X-Forwarded-For ヘッダーで確認する。
  • 相互 TLS (mTLS) に対応している。

NLB の詳細

  • AZ ごとに静的 IP アドレス (Elastic IP を割り当て可能) を持つため、固定 IP が必要な要件や、ファイアウォールでの許可リストに適する。
  • 送信元 IP アドレスを保持できる。ターゲットの種類によって挙動が異なる点に注意する (IP ターゲットではプロキシプロトコル v2 の利用が有効な場面がある)。
  • TLS リスナーで ACM の証明書を使った TLS 終端ができる。または TCP リスナーで暗号化されたままバックエンドへ通す (TLS パススルー)。
  • セキュリティグループを関連付けられる (作成時に設定)。
  • AWS PrivateLink のエンドポイントサービスの裏側には、NLB か GWLB が必要。
  • ALB をターゲットにできるため、ALB の前に NLB を置いて静的 IP を得る構成が可能 (Global Accelerator でも代替できる)。

GWLB の詳細

  • セキュリティアプライアンス (次世代ファイアウォール、IDS、IPS など) の前段に置く。
  • GENEVE プロトコル (UDP のポート 6081) で、元のパケットをカプセル化してアプライアンスへ渡す。
  • 利用側の VPC には、GWLB エンドポイント (GWLBe) を作り、ルートテーブルのターゲットに指定してトラフィックを通す。
  • フロー単位のスティッキネス (同じフローは同じアプライアンスへ) を保つ。
  • 集中型の検査 VPC を作り、Transit Gateway で各 VPC から集約する構成が代表的 (Task 1.6)。

ステップ 6: スケーリングの要因

  • ALB と NLB は、トラフィックに応じて自動でスケールする。
  • 急激な (数分での) 大幅なトラフィック増が予想される場合は、事前に AWS サポートに相談するか、ALB のキャパシティユニットの予約機能を検討する。
  • ALB は、サブネットに十分な空き IP アドレス (少なくとも 8 個。/27 以上のサブネットを推奨) が必要。スケール時にノードが追加されるため。
  • ALB のノードの IP アドレスは変わるので、IP アドレスを固定して前提にしない。必ず DNS 名を使う。
  • 課金とスケールの単位は、ALB は LCU (ロードバランサーキャパシティユニット)、NLB は NLCU で、CloudWatch メトリクスで消費量を確認できる。
  • AZ の偏りがある場合は、クロスゾーン負荷分散の設定で、ターゲットへの負荷の均等性が変わる。

ステップ 7: Auto Scaling との統合

  1. ターゲットグループを Auto Scaling グループ (ASG) にアタッチする。インスタンスは起動時に自動で登録され、終了時に自動で登録解除される。
  2. ASG のヘルスチェックタイプを ELB にして、ロードバランサーのヘルスチェックで異常と判断されたインスタンスを、ASG が自動で置き換える。
  3. スケーリングポリシーに、ターゲット追跡スケーリングで、ターゲットあたりのリクエスト数 (ALBRequestCountPerTarget) を使うと、負荷に応じた台数調整ができる。
  4. 登録解除の遅延とライフサイクルフックを使い、スケールイン時にも処理中のリクエストを安全に完了させる。
  5. ウォームプールとスロースタートで、新しいインスタンスの立ち上がりによる性能劣化を和らげる。

  • 「静的 IP が必要」「UDP」と書かれていれば NLB。ALB には静的 IP も UDP もない。

  • 「クライアントの本当の IP が知りたい」は、ALB なら X-Forwarded-For。NLB なら送信元 IP の保持か、プロキシプロトコル。
  • クロスゾーン負荷分散は、ALB は既定で有効、NLB と GWLB は既定で無効。

フローログは、ネットワークインターフェイス (ENI) を通る IP トラフィックのメタデータ (パケットの中身ではない) を記録する機能です。

項目 内容
取得範囲 VPC 全体、サブネット、個別の ENI。Transit Gateway にも設定できる
出力先 CloudWatch Logs、Amazon S3、Amazon Data Firehose

トラフィックの種類 ACCEPT のみ、REJECT のみ、すべて、から選べる
集計間隔 10 分 (既定) または 1 分
カスタムフォーマット VPC ID、サブネット ID、インスタンス ID、TCP フラグ、方向、トラフィックパス、AZ ID など追加のフィールドを選べる

  --traffic-type ALL \
  --log-destination-type s3 \
  --log-destination arn:aws:s3:::example-flow-logs-bucket/vpc/ \
  --max-aggregation-interval 60 \
  --log-format '${version} ${vpc-id} ${subnet-id} ${instance-id} ${srcaddr} ${dstaddr} ${srcport} ${dstport} ${protocol} ${tcp-flags} ${bytes} ${action} ${flow-direction} ${traffic-path}'
-- CloudWatch Logs Insights で、拒否された通信の上位を調べる例

  • フローログは、セキュリティグループとネットワーク ACL のどちらで拒否されたかを直接示さない。トラブルシューティングでは、REJECT のパターンから推測する。
  • 大量のログはコストになるため、必要な範囲と期間に絞り、S3 のライフサイクルで保管期間を管理する。

ステップ 5: VPC Reachability Analyzer

  • 送信元と宛先を指定すると、パケットを実際には送らずに、VPC の構成 (ルートテーブル、セキュリティグループ、ネットワーク ACL、ゲートウェイなど) を解析して、到達可能かを判定する。
  • 到達できない場合は、どのコンポーネントがブロックしているかを示す。到達できる場合は、経路上のホップを一覧にする。
  • 新しい接続の設計の検証や、変更前後の確認、トラブルシューティングに使う。
  • 構成の静的な解析のため、アプリケーションの層 (ポートでの待ち受けやアプリの動作) の問題は検出できない。
  • 補完的なサービスとして、Network Access Analyzer が、意図しないネットワークアクセスを見つけるために使われる (ドメイン 4 に関連)。

ステップ 8: ネットワーク性能のベースラインを取る

ベースラインは「正常時の姿」を記録して、異常を判断する物差しにするものです。

  1. 平常時に、一定期間 (少なくとも数週間。曜日や時間帯、月末などの周期を含める) のメトリクスを収集する。
  2. スループット、遅延、パケット損失、同時接続数、エラー率などを、ピークと平均の両方で記録する。
  3. その値をもとに、アラームのしきい値を決める。周期性が強い場合は、CloudWatch の異常検出を使うと、時間帯ごとの変動を自動で学習できる。
  4. システムの変更 (構成の変更、トラフィックの増加) があれば、ベースラインを更新する。
  5. ハイブリッド接続は、Network Synthetic Monitor などで、継続的に遅延とパケット損失を測定すると、障害の切り分けが速くなる。

ステップ 1: ルーティングの基礎

方式 特徴 向く場面
静的ルーティング 管理者が手動で経路を設定する。障害時の自動切り替えがない 小規模、単純な構成
動的ルーティング (BGP) ルーター同士が経路情報を交換し、障害時に自動で経路を切り替える 冗長構成、大規模、ハイブリッド接続全般

BGP の基本

  • BGP は、異なる自律システム (AS) 間で経路を交換するプロトコル。AWS とオンプレミスの間では eBGP を使う。
  • AS 番号 (ASN): 自分の AS を識別する番号。プライベート ASN の範囲は、16 ビットの 64512 から 65534 と、32 ビットの 4200000000 から 4294967294。
  • 経路選択の基本は「最長一致 (より具体的なプレフィックス) が優先」。同じプレフィックスなら、BGP 属性で優劣を決める。
  • BGP セッションは、ホールドタイマーでダウンを検出する。より速く検出したい場合は、BFD (双方向フォワーディング検出) を使う。Direct Connect では AWS 側で BFD が自動で有効になるので、オンプレミスのルーター側で設定する。
  • ルート数には上限があり、超過するとセッションが切れる場合がある。そのため、広告するプレフィックスは集約する。

主な BGP 属性

属性 意味 使い方
ローカルプリファレンス 自 AS 内で、どの出口を優先するか (値が大きいほど優先) オンプレミスから AWS へ出ていく経路を制御する
AS パス (プリペンド) 経路が通過する AS の数 (短いほど優先) 自分の ASN を重複して付けて、経路を劣後させる
MED 隣接する AS に、どの入口を使ってほしいかを示す 同じ隣接 AS との複数のリンク間の優先度
コミュニティ 経路に付けるタグ Direct Connect では、ローカルプリファレンスの指定や、広告範囲の制御に使う

ステップ 2: AWS Direct Connect (DX)

Direct Connect は、オンプレミスと AWS を、専用線で接続するサービスです。インターネットを経由しないため、遅延と帯域が安定し、データ転送料金も低くなります。

接続の種類

種類 内容
専用接続 (Dedicated) AWS から直接、専用のポートを提供する (1、10、100 Gbps など)。お客様が、DX ロケーションまでの回線を手配する
ホスト接続 (Hosted) AWS パートナーが提供する。50 Mbps など、小さい帯域から選べる

仮想インターフェイス (VIF)

VIF の種類 接続先 用途
プライベート VIF VPC (仮想プライベートゲートウェイ) または Direct Connect ゲートウェイ プライベート IP で VPC へ接続する
トランジット VIF Direct Connect ゲートウェイ経由で Transit Gateway 多数の VPC を、Transit Gateway で集約して接続する
パブリック VIF AWS のパブリックサービス (S3、DynamoDB などのパブリックエンドポイント) インターネットを経由せず、パブリックエンドポイントへ接続する
  • 各 VIF は、IEEE 802.1Q の VLAN タグで識別される (L2 の概念)。
  • ホスト接続は、1 つの VIF のみをサポートする。
  • Direct Connect ゲートウェイは、グローバルなリソースで、任意の DX ロケーションの VIF から、異なるリージョンの VPC や Transit Gateway へ接続できる。

落とし穴: 1 つの Direct Connect ゲートウェイに、複数の VPC を関連付けても、VPC 間の通信は転送されません (VPC 間の推移的な通信は不可)。VPC 同士をつなぎたい場合は、Transit Gateway などを使います。

物理層 (L1) と L2 の概念

項目 内容
光モジュールと光ファイバー シングルモードファイバー。1 Gbps は 1000BASE-LX、10 Gbps は 10GBASE-LR、100 Gbps は 100GBASE-LR4 など、速度に応じた規格を選ぶ
オートネゴシエーション ポートの速度設定と、AWS 側の設定を合わせる。不一致はリンクが上がらない原因になる
LAG (リンクアグリゲーション) LACP (IEEE 802.3ad) で、同じ帯域の複数の接続を、1 つの論理的な接続にまとめる。帯域の拡大と冗長化ができる。構成できる接続数と、最小リンク数の設定がある
ジャンボフレーム プライベート VIF は MTU 9001、トランジット VIF は MTU 8500 まで対応する。パブリック VIF は非対応
MACsec 対応する専用接続 (10 Gbps と 100 Gbps) で、L2 の暗号化ができる

MTU の注意: 経路上の MTU が不一致だと、大きなパケットが破棄され、通信が不安定になる場合がある (PMTUD のための ICMP を許可する)。Site-to-Site VPN は、MTU が約 1500 バイトに制限される。

ステップ 2: VPC ピアリング

項目 内容
特徴 2 つの VPC 間のプライベートな接続。同一アカウントも別アカウントも、同一リージョンもリージョン間も可
推移的ルーティング 不可 (A と B、B と C がピアリングでも、A と C は通信できない)

ステップ 3: AWS Transit Gateway

用語 意味
アタッチメント VPC、VPN、Direct Connect ゲートウェイ、Transit Gateway ピアリング、Connect を、Transit Gateway に接続する単位
ルートテーブル Transit Gateway 内のルーティング表。複数作って、ネットワークを分離できる
関連付け (アソシエーション) アタッチメントに、使用するルートテーブルを 1 つ決める (受信したトラフィックの検索先)
伝播 (プロパゲーション) アタッチメントの CIDR を、ルートテーブルへ自動で登録する (複数のテーブルへ可能)
静的ルートとブラックホール 手動のルート。ブラックホールは、特定の宛先を破棄する

アプライアンスモード 検査用 VPC のステートフルなアプライアンスで、往路と復路を同じ AZ のアプライアンスへ通す (非対称ルーティングの防止)

設計のポイント

  • Transit Gateway はリージョナルなリソース。複数のリージョンは、Transit Gateway のピアリングか、Cloud WAN で接続する。
  • VPC アタッチメントには、AZ ごとに 1 つのサブネットを指定する。AZ をまたぐ到達性のために、利用する AZ すべてのサブネットを指定する。
  • ルートテーブルを分けて、ネットワークを分離 (セグメンテーション) する。たとえば、本番、開発、共有サービスなどに分けて、許可する経路だけを伝播させる。
  • RAM で、組織内の他のアカウントに共有できる。
  • Transit Gateway は、アタッチメントの時間課金と、処理したデータ量の課金がある。

ステップ 6: IP アドレスの重複を管理する

最も良い対策は、重複させない設計 (IP アドレス計画) です。AWS では、Amazon VPC IP Address Manager (IPAM) で、組織全体の CIDR の割り当てを管理できます。

すでに重複してしまっている場合の選択肢です。

方法 内容 注意点
PrivateLink 公開するサービスだけを、重複しない方法 (ENI の IP) で接続する サービス単位の一方向の接続のみ
プライベート NAT ゲートウェイ 重複する CIDR を、重複しない別の IP (ルーティング可能なサブネットの IP) へ変換して、Transit Gateway などを経由して通信する NAT の設計が必要。接続は NAT 側から開始する

セカンダリ CIDR (100.64.0.0/10 など) ルーティングしない用途 (コンテナの Pod など) に、別の範囲を追加する 既存の通信相手との重複は解決しない

再設計 (IP アドレスの付け替え) 根本的な解決 工数が大きい

実際の試験は複数選択やマッチング形式です。ここでは、考え方を確認するための簡易問題です。

問題 1

グローバルなユーザー向けの、UDP を使うゲームのサーバーが、複数のリージョンにあります。取引先のファイアウォールで、許可する IP を固定する必要があります。最も適切な 2 つの組み合わせはどれですか。

  1. Amazon CloudFront
  2. AWS Global Accelerator
  3. NLB をエンドポイントにする
  4. ALB をエンドポイントにする
  5. Route 53 の加重ルーティング
答えと解説

答え: 2 と 3。UDP と静的 IP が必要なため、Global Accelerator を使い、UDP に対応する NLB をエンドポイントにします。CloudFront は HTTP と HTTPS が対象で、ALB は UDP を扱えません。

問題 2

オンプレミスのサーバーが、VPC のプライベートホストゾーンの名前を解決する必要があります。必要な構成はどれですか。

  1. Resolver のインバウンドエンドポイントを作り、オンプレミスの DNS から条件付きフォワーダーで転送する
  2. Resolver のアウトバウンドエンドポイントを作る
  3. パブリックホストゾーンに同じレコードを作る
答えと解説

答え: 1。オンプレミスから AWS への問い合わせはインバウンドエンドポイントです。アウトバウンドは逆方向 (AWS からオンプレミス) です。

問題 3

Direct Connect を、プライマリの接続として使います。障害時に、自動で、VPN に切り替わるようにしたいです。トラフィックを、通常は DX に流すには、どのように設計しますか。

  1. DX と VPN の両方で BGP を使い、同じプレフィックスを広告する (AWS は既定で DX を優先する)
  2. VPN のみ静的ルートにする
  3. DX を静的ルートにする
答えと解説

答え: 1。BGP を使うことで、障害時に自動で経路が切り替わります。同じプレフィックスの場合、AWS は一般に DX を優先します。オンプレミス側から AWS へ出る経路は、ローカルプリファレンスで DX を優先させます。

問題 4

IP アドレスが重複している 2 つの VPC があり、一方のアプリケーションの API だけを、もう一方の VPC から利用したいです。最も適切なものはどれですか。

  1. VPC ピアリング
  2. Transit Gateway
  3. AWS PrivateLink
答えと解説

答え: 3。PrivateLink は、サービス単位で一方向に公開でき、CIDR の重複の影響を受けません。ピアリングと通常の Transit Gateway の接続は、重複する CIDR では使えません。

問題 5

ファイアウォールアプライアンスを、すべての VPC のトラフィックの経路に、透過的に挿入し、往復のトラフィックを同じアプライアンスへ通したいです。必要なものを 2 つ選んでください。

  1. Gateway Load Balancer
  2. Transit Gateway のアプライアンスモード
  3. Application Load Balancer
  4. VPC ピアリング
答えと解説

答え: 1 と 2。GWLB でアプライアンスを透過的に挿入し、Transit Gateway のアプライアンスモードで、往復のフローを同じ AZ のアプライアンスへ通します。

問題 6

VPC 内の特定のサブネットで、拒否された通信を調べたいです。パケットの内容までは不要です。使うものはどれですか。

  1. Traffic Mirroring
  2. VPC Flow Logs と CloudWatch Logs Insights
  3. Reachability Analyzer
答えと解説

答え: 2。フローログは、ACCEPT と REJECT を含む通信のメタデータを記録します。Logs Insights で、拒否された通信を集計できます。
