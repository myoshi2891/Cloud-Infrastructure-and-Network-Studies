コンテナイメージのビルド・push と GKE へのデプロイ（echo-web）

Go 製サンプルアプリ echo-web を、Docker でイメージ化し、Kubernetes（GKE）上で公開するまでを初学者向けに解説します。

開発チームから「echo-web をコンテナ化して Kubernetes 上で動かせるか確認してほしい」と依頼されたシナリオです。チャレンジラボは手順書が提示されないため、コマンドの「なぜ」まで理解することが重要です。

4. Task 1: Kubernetes クラスタを作成する

gcloud container clusters create echo-cluster \
  --zone ${ZONE} \
  --num-nodes 2 \
  --machine-type e2-standard-2
オプション 意味 間違えると
echo-cluster クラスタ名 採点されない
--zone 作成場所（ゾーンクラスタ） 別ゾーンだと採点されない
--num-nodes 2 ゾーンあたりのノード数 多いと上限に注意
--machine-type ノードのスペック（2 vCPU・8 GB） 既定タイプになる
ノード数の考え方--region でリージョンクラスタを作ると「ゾーン数 × 2 台」になり、「2台まで」の制約を破ります。今回は必ず --zone を使います。

4-1. 待ち時間の活用（別タブの注意）

作成には約 3〜5 分かかります。別の Cloud Shell タブで Task 2・3 を進められますが、環境変数はタブごとに独立しているため、新しいタブで 3 章の変数設定をやり直してください。Task 4 は、最初のタブで作成完了が表示されてから実行します。

4-2. 認証情報の取得と確認

gcloud container clusters get-credentials echo-cluster --zone ${ZONE}
kubectl get nodes

STATUS が Ready のノードが 2 台表示されれば成功です。NotReady は起動途中なので 1〜2 分待ちます。

5. Task 2: タグ付き Docker イメージをビルドする

アプリ一式は Cloud Storage の gs://プロジェクトID/echo-web.tar.gz にあります。ダウンロード→展開→ビルドの順に進めます。

5-1. ダウンロードと展開

gsutil cp gs://${PROJECT_ID}/echo-web.tar.gz .

# 展開専用の空ディレクトリを作り、そこへ展開する
BUILD_DIR=$(mktemp -d ./echo-web-build.XXXXXX)
echo "BUILD_DIR=${BUILD_DIR}"
tar -xzf echo-web.tar.gz -C "$BUILD_DIR"
ls -la "$BUILD_DIR"
なぜ専用ディレクトリに展開するのかdocker build は指定ディレクトリを丸ごと「ビルドコンテキスト」として Docker に渡します。ホームディレクトリ全体を渡すと、無関係なファイルや認証情報まで送られ、ビルドも遅くなります。
変数の消失BUILD_DIR は別タブや再接続で空になります。echo で表示した値を設定し直してください。

5-2. 内容の確認

grep -nE '^[[:space:]]*(COPY|ADD)' "$BUILD_DIR/Dockerfile"
cat "$BUILD_DIR/Dockerfile"
cat "$BUILD_DIR/.dockerignore" 2>/dev/null || echo ".dockerignore なし"
観点 確認内容
Dockerfile の場所 BUILD_DIR 直下にあること。サブディレクトリに展開された場合は、Dockerfile のあるディレクトリを BUILD_DIR に設定し直してから 5-3 の docker build を実行する
COPY / ADD 取り込み元がすべて BUILD_DIR 内にあること
.dockerignore main.go など必要なファイルを除外していないこと
EXPOSE 待受ポート（8000）を示すメタデータ。ポートを開く機能ではない

5-3. ビルド

docker build -t gcr.io/${PROJECT_ID}/echo-app:v1 "$BUILD_DIR"
docker images

-t は tag の t で、名前とタグを付けます。末尾の "$BUILD_DIR" を省略すると引数不足でエラーになります。docker images に gcr.io/プロジェクトID/echo-app の v1 が出れば成功です。

6. Task 3: イメージを gcr.io に push する

Docker はそのままでは Google のレジストリにログインできないため、gcloud を認証ヘルパーとして登録します（途中の確認は Y）。 

gcloud auth configure-docker
docker push gcr.io/${PROJECT_ID}/echo-app:v1

期待する出力の流れは次のとおりです。

最後に v1: digest: sha256:... と表示されれば成功です。確認は次のとおりです。 

gcloud artifacts docker images list us-docker.pkg.dev/${PROJECT_ID}/gcr.io
gcloud artifacts docker tags list us-docker.pkg.dev/${PROJECT_ID}/gcr.io/echo-app
Container Registry から Artifact Registry へContainer Registry は非推奨で、後継は Artifact Registry です。gcr.io ドメインは Artifact Registry 側で引き続き使えます。ラボでは指定どおり gcr.io、新規の実務や試験の解答では Artifact Registry（REGION-docker.pkg.dev/...）を選びます。

7. Task 4: アプリをクラスタにデプロイして公開する

7-1. 最重要ポイント：2 つのポートを区別する

名前 誰のポートか このラボの値
--port Service が外部に見せるポート 80
--target-port コンテナが実際に待ち受けるポート 8000
よくあるミス--port 8000 だけを指定すると、Service は 8000 番だけを公開するため、http://IP（80番）への接続は拒否またはタイムアウトしてつながりません。LoadBalancer Service は L4 で転送するため、HTTP のエラー応答（504 など）は返りません。

7-2. Deployment を作成

# 現在のコンテキストの Namespace を記録する（未設定なら Kubernetes の既定値 default）
NAMESPACE=$(kubectl config view --minify -o jsonpath='{..namespace}')
export NAMESPACE=${NAMESPACE:-default}
echo "NAMESPACE=${NAMESPACE}"

kubectl create deployment echo-web \
  --namespace "$NAMESPACE" \
  --image=gcr.io/${PROJECT_ID}/echo-app:v1
kubectl get deployment echo-web
kubectl get pods

READY が 1/1、Pod の STATUS が Running になれば成功です。表示された NAMESPACE は公開・削除でも同じ値を使うため、控えておきます。

7-3. Service を作成して外部公開

kubectl expose deployment echo-web \
  --namespace "$NAMESPACE" \
  --type=LoadBalancer \
  --port 80 \
  --target-port 8000
kubectl get service echo-web --watch

EXTERNAL-IP が <pending> から IP アドレスに変わるまで約 1〜2 分待ち、Ctrl+C で watch を終了します。

7-4. 参考：宣言的な方法（マニフェスト）

実務では YAML を Git 管理する方法が推奨です。Service は selector のラベルで Pod を探すため、ラベルの一致が必須です（コマンド方式では自動で一致します）。 

apiVersion: apps/v1
kind: Deployment
metadata:
  name: echo-web
spec:
  replicas: 1
  selector:
    matchLabels:
      app: echo-web
  template:
    metadata:
      labels:
        app: echo-web
    spec:
      containers:
        - name: echo-web
          image: gcr.io/PROJECT_ID/echo-app:v1
          ports:
            - containerPort: 8000
---
apiVersion: v1
kind: Service
metadata:
  name: echo-web
spec:
  type: LoadBalancer
  selector:
    app: echo-web
  ports:
    - port: 80
      targetPort: 8000
適用前に PROJECT_ID を置き換えるimage: の gcr.io/PROJECT_ID/echo-app:v1 の PROJECT_ID は、自分のプロジェクト ID に置き換えてから適用します。イメージ名 echo-app とタグ v1 は変えません。置き換えないと ImagePullBackOff になります。

上の YAML を echo-web.yaml という名前で保存し（例: nano echo-web.yaml）、PROJECT_ID を 3 章で設定した値へ置換して適用します。 

# PROJECT_ID を置換して適用する（echo-web.yaml が保存済みであることを先に確認する）
if [ ! -f echo-web.yaml ]; then
  echo "echo-web.yaml がありません。上の YAML を保存してから再実行してください" >&2
  false
else
  sed "s/PROJECT_ID/${PROJECT_ID}/" echo-web.yaml | kubectl apply -f -
fi

9. トラブルシューティング

注意この節の kubectl は、7-3 で記録した NAMESPACE を対象にします。別タブや再接続後は値が空になるため、診断の前に表の下にあるコマンドの先頭で設定し直してください。
症状 原因 対処
http://IP に接続できない（接続拒否・タイムアウト） アプリ未起動、または Service が 80 番を公開していない（--port 8000 のみ等）／targetPort が 8000 でない／Ready な Endpoint がない 1〜2分待つ。kubectl get service echo-web --namespace "$NAMESPACE" で PORT(S) が 80:… か、kubectl describe service echo-web --namespace "$NAMESPACE" で TargetPort が 8000/TCP か確認（get service には targetPort が表示されない）。kubectl get endpoints echo-web --namespace "$NAMESPACE" の ENDPOINTS が <none> なら、待つだけでは解消しないことがあるため、kubectl get service echo-web --namespace "$NAMESPACE" -o jsonpath='{.spec.selector}' の selector が kubectl get pods --namespace "$NAMESPACE" --show-labels で Ready の Pod のラベルと一致するか確認
後半の採点項目が通らない 別ゾーンでクラスタ作成 指定の ZONE で作り直す
EXTERNAL-IP が pending LB 作成中、または割り当て不足 2〜3分待つ。kubectl describe service echo-web --namespace "$NAMESPACE"
ImagePullBackOff イメージ名・タグ・ID の誤り、push 漏れ kubectl describe pod --namespace "$NAMESPACE" -l app=echo-web --show-events=true で名前を確認し push を再実行
CrashLoopBackOff アプリが起動直後に落ちる kubectl logs --namespace "$NAMESPACE" -l app=echo-web で原因確認
push 時の認証エラー 認証ヘルパー未設定 gcloud auth configure-docker
build で Dockerfile がない BUILD_DIR が空・違う場所 ls -la "$BUILD_DIR" で確認し設定し直す
別クラスタにつながる コンテキスト未切替 get-credentials を再実行 
# 別タブや再接続後は NAMESPACE が空になるため、7-3 で表示した値を設定し直す
read -r -p "echo-web を作成した Namespace を入力 (空欄なら default): " NAMESPACE
export NAMESPACE=${NAMESPACE:-default}
echo "NAMESPACE=${NAMESPACE}"
kubectl describe pod --namespace "$NAMESPACE" -l app=echo-web
kubectl logs --namespace "$NAMESPACE" -l app=echo-web
kubectl describe service echo-web --namespace "$NAMESPACE"
kubectl get endpoints echo-web --namespace "$NAMESPACE"   # 空なら selector 不一致、または一致する Pod が Ready でない（selector と Pod の READY を両方確認）

# Service の作り直し
kubectl delete service echo-web --namespace "$NAMESPACE"
kubectl expose deployment echo-web --namespace "$NAMESPACE" --type=LoadBalancer --port 80 --target-port 8000

10. ベストプラクティス（実務・試験向け）

11. コマンド一括版（復習用）

注意まずは各 Task を理解しながら 1 つずつ実行してください。これは「理解後の復習用」です。ZONE はラボの指定値に必ず置き換えます。 
# ===== 0. 変数 =====
export PROJECT_ID=$(gcloud config get-value project)
read -r -p "ラボ指定のゾーンを入力 (例: us-central1-a): " ZONE
export ZONE

# 以降はサブシェル内で実行し、必須コマンドが 1 つでも失敗したらその時点で止める
# （set -e の影響を呼び出し元のシェルに残さないため、( ) で囲む）
(
set -euo pipefail

# ===== 1. クラスタ作成 =====
gcloud container clusters create echo-cluster \
  --zone ${ZONE} \
  --num-nodes 2 \
  --machine-type e2-standard-2
gcloud container clusters get-credentials echo-cluster --zone ${ZONE}

# ===== 2. ビルド（現在の作業ディレクトリで実行する） =====
gsutil cp gs://${PROJECT_ID}/echo-web.tar.gz .
BUILD_DIR=$(mktemp -d ./echo-web-build.XXXXXX)
tar -xzf echo-web.tar.gz -C "$BUILD_DIR"
ls -la "$BUILD_DIR"   # Dockerfile と .dockerignore の内容を 5-2 のとおり確認する
docker build -t gcr.io/${PROJECT_ID}/echo-app:v1 "$BUILD_DIR"

# ===== 3. push =====
gcloud auth configure-docker
docker push gcr.io/${PROJECT_ID}/echo-app:v1

# ===== 4. デプロイと公開 =====
# 現在のコンテキストの Namespace を記録し、以降の作成先を揃える（クリーンアップで使うので表示された値を控える）
NAMESPACE=$(kubectl config view --minify -o jsonpath='{..namespace}')
NAMESPACE=${NAMESPACE:-default}
echo "NAMESPACE=${NAMESPACE}"
kubectl create deployment echo-web --namespace "$NAMESPACE" --image=gcr.io/${PROJECT_ID}/echo-app:v1
kubectl expose deployment echo-web --namespace "$NAMESPACE" --type=LoadBalancer --port 80 --target-port 8000
# Ctrl+C で watch を止めたときの終了コード 130 だけを正常終了とみなし、それ以外の失敗は伝える
WATCH_STATUS=0
kubectl get service echo-web --watch || WATCH_STATUS=$?
if [ "$WATCH_STATUS" -ne 0 ] && [ "$WATCH_STATUS" -ne 130 ]; then
  exit "$WATCH_STATUS"
fi
)
途中で失敗した場合表示されたエラーを直してから、失敗したステップ以降を 1 つずつ実行してください（クラスタ作成済みのまま全体を再実行すると、clusters create が「既に存在する」で止まります）。

12. クリーンアップ

ラボ環境は自動削除されますが、自分のプロジェクトで試した場合は課金されます。ロードバランサが課金対象のため、Service から先に削除します。

削除の前に、対象のプロジェクト、ゾーン、Namespace を確認します。別タブや再接続後はこれらの変数が空になるため、ラボ画面の ZONE（自分のプロジェクトで試した場合はクラスタを作成したゾーン）と、7-2 で表示した NAMESPACE を設定し直し、表示された値が削除対象と一致することを確認します。 

export PROJECT_ID=$(gcloud config get-value project)
read -r -p "ラボ指定のゾーンを入力 (例: us-central1-a): " ZONE
export ZONE
read -r -p "echo-web を作成した Namespace を入力 (空欄なら default): " NAMESPACE
export NAMESPACE=${NAMESPACE:-default}
echo "PROJECT_ID=${PROJECT_ID}"
echo "ZONE=${ZONE}"
echo "NAMESPACE=${NAMESPACE}"

kubectl は現在のコンテキストのクラスタを操作します。別のクラスタを操作しないよう、echo-cluster がそのゾーンに存在すること、認証情報を取得できること、現在のコンテキストが echo-cluster であること、echo-web Service が NAMESPACE 以外の Namespace にないことをすべて確認できた場合だけ、Service、Deployment、クラスタの順に削除します。どれか 1 つでも失敗すると、以降のコマンドは実行されず、0 以外の終了ステータスで止まります。その場合は ZONE、PROJECT_ID、NAMESPACE を見直してください。echo-web Service がどの Namespace にもない場合は、再実行でもクラスタの削除まで進みます。 

# 4 つの確認がすべて成功した場合だけ、Service、Deployment、クラスタの順に削除する
# 別の Namespace に echo-web Service が残ったままクラスタを削除すると、ロードバランサが削除されずに課金が続くおそれがある
gcloud container clusters describe echo-cluster --zone ${ZONE} --project ${PROJECT_ID} --format="value(name,location)" \
  && gcloud container clusters get-credentials echo-cluster --zone ${ZONE} --project ${PROJECT_ID} \
  && [ "$(kubectl config current-context)" = "gke_${PROJECT_ID}_${ZONE}_echo-cluster" ] \
  && ECHO_WEB_NAMESPACES=$(kubectl get service --all-namespaces --field-selector metadata.name=echo-web -o jsonpath='{range .items[*]}{.metadata.namespace}{"\n"}{end}') \
  && OTHER_NAMESPACES=$(printf '%s\n' "$ECHO_WEB_NAMESPACES" | awk -v ns="$NAMESPACE" 'NF && $0 != ns') \
  && { [ -z "$OTHER_NAMESPACES" ] || { echo "echo-web Service が別の Namespace にあるため中止します: $OTHER_NAMESPACES" >&2; false; }; } \
  && kubectl delete service echo-web --namespace "$NAMESPACE" --ignore-not-found \
  && kubectl delete deployment echo-web --namespace "$NAMESPACE" --ignore-not-found \
  && gcloud container clusters delete echo-cluster --zone ${ZONE} --project ${PROJECT_ID}

イメージを削除する前に、v1 と同じ DIGEST を指すタグが他にないか確認します。

gcloud artifacts docker tags list us-docker.pkg.dev/${PROJECT_ID}/gcr.io/echo-app
確認結果 実行するコマンド
v1 のみがその DIGEST を指す gcloud artifacts docker images delete us-docker.pkg.dev/${PROJECT_ID}/gcr.io/echo-app:v1 --delete-tags
同じ DIGEST を指す別タグがある gcloud artifacts docker tags delete us-docker.pkg.dev/${PROJECT_ID}/gcr.io/echo-app:v1（タグだけ外す）

--delete-tags は、そのイメージを指すタグをすべて削除するため、事前確認が必要です。
