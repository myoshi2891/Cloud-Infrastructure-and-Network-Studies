2. 認定の全体像

2.1 取得要件

CCNP Security は 2 つの試験に合格すると付与されます。

  • コア試験（必須）: 350-701 SCOR（120 分）
  • コンセントレーション試験（1 つ選択）: 90 分

各試験に合格すると、それぞれ個別の「スペシャリスト認定」も得られます。コア試験は CCIE Security の筆記（資格要件）も兼ねるため、1 回の合格で両方の道が開けます。

補足

順序は自由です。コンセントレーションを先に受けても構いません。

2.3 どのコンセントレーションを選ぶ？

選択肢 向いている人 学習の特徴
SNCF ファイアウォール運用者 FMC の画面操作・ポリシー・トラブルシュートが中心。実機または仮想環境があると学びやすい
SISE NAC／ID 基盤担当 ポリシー設計の理解と、スイッチ側設定の知識の両方が必要
SSCA クラウド／リモートワーク／SSE 担当 概念の理解が中心。Duo・Secure Access・Secure Workload の役割分担を整理する
SDSI 設計・コンサル 「状況に対して最適な設計を選ぶ」形式。フレームワーク知識が重要

3.3 暗号の基礎

用語 一言説明
ハッシュ 同じ入力なら同じ固定長の値。元に戻せない。改ざん検知（整合性確認）には SHA-256 等を使う。パスワード保存には SHA-256 単体は不適で、ソルト付きの低速（適応型）方式 Argon2id 等を使う
HMAC 共有鍵付きハッシュ。メッセージ認証に使う

TLS Web 等で使う暗号化通信。TLS 1.3 が現行の推奨
IPsec IP レイヤの暗号化。VPN で多用（IKE で鍵交換、ESP で暗号化）

1.2 脆弱性とエクスプロイト（OWASP Top 10、CVE、CVSS）

1.10 セキュリティ機器 API を呼び出すスクリプトの読解（Python）

何か: 試験では短い Python スクリプトを読み、「何をしているか」「どこが問題か」を答える形式が想定されます。次の 3 点を見ます。

  1. 認証（トークン取得・ヘッダ付与）
  2. リクエスト（メソッド・URL・パラメータ・ボディ）
  3. 応答処理（ステータスコード・JSON の取り出し・エラー処理）
import os
import requests

BASE = "https://fmc.example.local"      # 管理センターの FQDN（例）
USER = os.environ["FMC_USER"]           # 資格情報はコードに書かず環境変数/シークレット管理から
PASS = os.environ["FMC_PASS"]
CA   = "/etc/ssl/certs/ca-bundle.crt"   # 証明書検証を有効にする（verify=False は避ける）

# 1) トークン取得（Basic 認証）
r = requests.post(f"{BASE}/api/fmc_platform/v1/auth/generatetoken",
                  auth=(USER, PASS), verify=CA, timeout=10)
r.raise_for_status()
token  = r.headers["X-auth-access-token"]
domain = r.headers["DOMAIN_UUID"]

# 2) トークンを付けて API を呼ぶ（オブジェクト一覧の取得例）
resp = requests.get(f"{BASE}/api/fmc_config/v1/domain/{domain}/object/networks",
                    headers={"X-auth-access-token": token},
                    params={"limit": 25}, verify=CA, timeout=10)
resp.raise_for_status()

# 3) JSON を処理
for item in resp.json().get("items", []):
    print(item["name"])
HTTP メソッド 意味 例
GET 取得 オブジェクト一覧の取得
POST 作成 新規ネットワークオブジェクトの作成
PUT 更新（置換） 既存オブジェクトの更新
DELETE 削除 オブジェクトの削除
ステータス 意味・対処
200 / 201 / 204 成功／作成成功／成功（本文なし）
400 要求の形式不正（JSON・必須項目を確認）
401 / 403 認証失敗／権限不足（トークン期限・ロールを確認）
404 リソースが存在しない（URL・ID を確認）
429 レート制限（待ってから再試行）
5xx サーバ側エラー（時間をおいて再試行）
ベストプラクティス
  • 資格情報をソースコードに埋め込まない（環境変数・シークレットマネージャ）。
  • TLS 証明書の検証を無効化しない（verify=False は検証用途に限定）。
  • タイムアウト・再試行・ページネーション・レート制限対応を入れる。
  • API 用アカウントは最小権限のロールにし、操作は監査ログで追跡できるようにする。

2.1 FW／IPS の導入形態（デプロイメントモデル）

何か: ファイアウォール（FW）は「通信を許可／拒否する門番」、IPS は「通信の中身を見て攻撃を検知・遮断する仕組み」です。Cisco Secure Firewall（FTD）は両方の機能を 1 台で提供します（次世代ファイアウォール＝NGFW）。

モード 動作 向いている場面
ルーテッド（Routed） L3 ホップとして動作し、各インタフェースに IP を持つ 境界 FW の標準構成
トランスペアレント（Transparent） L2 の「ブリッジ」として挿入。データ IF に IP を持たない 既存の IP 設計を変えずに挿入したい場合
IPS インライン 通信が機器を通過し、遮断（ドロップ）できる 防御を目的とする IPS
IPS パッシブ SPAN／TAP でコピーを受けて検知のみ（遮断できない） まず検知だけ試したい／本番に影響を与えたくない

検知方式: シグネチャ（既知の攻撃パターン）、プロトコル異常、レピュテーション、振る舞い。Cisco の脅威情報組織 Talos がルールや評判情報を提供します。

ベストプラクティス
  • IPS は まず監視（検知のみ）で誤検知を調整 → 段階的にブロックへ。
  • 重要拠点は HA（アクティブ／スタンバイ） を前提に設計する（SNCF 1.3）。
  • 暗号化通信は、プライバシー・性能・法令を考慮し復号対象を絞る（2.8 参照）。

2.3 ネットワークインフラのセキュリティ（VLAN／SGT、L2 防御）

ブロードキャスト嵐 大量のブロードキャスト／マルチキャスト ストームコントロール
送信元 IP 詐称 偽の IP で通信 IP ソースガード、uRPF

6.3 802.1X と MAB（ISE）

何か

  • 802.1X: 端末が認証に成功するまでポートを開けない L2 の認証方式。登場人物は Supplicant（端末）／Authenticator（スイッチ・AP）／Authentication Server（ISE）。
  • MAB（MAC Authentication Bypass）: 802.1X に対応できない機器（プリンタ等）を MAC アドレスで認証する代替方式。MAC は偽装が容易なので、プロファイリングと組み合わせて制限付きの権限にします。
EAP 方式 特徴 推奨度
EAP-TLS 端末・サーバ双方の証明書で認証 最も安全。第一選択
PEAP（MSCHAPv2） サーバ証明書で保護したトンネル内でパスワード認証 広く使われるが、サーバ証明書の検証設定が重要
EAP-FAST PAC を使うトンネル方式 既存環境で利用
EAP-TEAP ユーザーと端末の認証を連結（チェイニング） 端末＋ユーザーの両方を確認したい場合 
! 802.1X のスイッチ側設定の例（概念。IBNS 2.0 ではポリシーマップ方式になる）

aaa authentication dot1x default group ISE-RADIUS
aaa authorization network default group ISE-RADIUS
aaa accounting dot1x default start-stop group ISE-RADIUS
dot1x system-auth-control
!
interface GigabitEthernet1/0/10
 switchport mode access

 authentication priority dot1x mab

 dot1x pae authenticator

導入の 3 段階（Cisco 公式の推奨アプローチ）

モード 動作 目的
モニターモード 認証は行うが失敗しても通信を許可（オープン認証） 影響なしで認証状況を可視化
ローインパクトモード 認証前は最小限の ACL で通信可、認証後に dACL 等で拡張 PXE・DHCP など最低限の通信を保ちながら段階的に強制
クローズドモード 認証成功まで通信を遮断 最も厳格

何か: 認証後に状況が変わった（プロファイリングで種別が判明、ポスチャ結果が出た、脅威が検知された）際に、サーバ（ISE）側から NAD へ「ポリシーを変更せよ」と通知する RADIUS 拡張（RFC 5176）です。

CoA の種類 動作
再認証（Reauthenticate） セッションを再評価し新しい認可を適用（通常はこれを使う）
ポートバウンス ポートを一時ダウン→アップ。DHCP を取り直させたい場合（VLAN 変更など）
切断（Disconnect） セッションを終了 
! NAD 側で ISE からの CoA を受け付ける設定の例
aaa server radius dynamic-author
 client 192.0.2.10 server-key <共有鍵>
ベストプラクティス
  • CoA は原則 再認証を使い、VLAN 変更が必要なときだけポートバウンスにする。
  • NAD 側で CoA を受け付ける送信元を ISE のみに限定し、共有鍵を強く保つ。
  • UDP 3799（機器により 1700）を ISE → NAD 方向で許可する（FW・ACL）。

2.3 無線 LAN の 802.1X

  • WPA2／WPA3-Enterprise で SSID を RADIUS 認証にし、WLC が ISE に問い合わせる。
  • AAA オーバーライド（ISE が VLAN／ACL を上書き）と CoA を有効化。
  • 認証に失敗する典型原因: サーバ証明書の不信頼、共有鍵、時刻、CoA の許可漏れ。

2.4 有線 802.1X（IBNS 2.0）とホストモード

ホストモード 動作
シングルホスト 1 ポートに 1 台のみ許可
マルチホスト 最初の 1 台が認証されれば以降の端末も通す（認証の抜け穴になりうる）
マルチドメイン 音声（IP 電話）とデータ（PC）を別々に認証
マルチオーセンティケーション 複数端末を個別に認証

IBNS 2.0 は、ポリシーマップ（policy-map type control subscriber）で認証の流れを柔軟に定義する新方式です。導入は モニター → ローインパクト → クローズドの順（SCOR 6.3 参照）。

2.5 MAB

  • 802.1X 非対応機器の MAC アドレス認証。ISE のエンドポイントグループやプロファイリングと組み合わせ、権限を限定。

インシデント対応の流れ（NIST の考え方）: 準備 → 検知・分析 → 封じ込め・根絶・復旧 → 事後対応（教訓）。最新の NIST SP 800-61 Rev.3 は CSF 2.0 の機能に沿って再構成されています。

3.2 リスクを下げる設計変更

リスク対応 内容
回避 リスクの原因となる活動をやめる
低減（軽減） 対策を追加して発生確率や影響を減らす
移転 保険・外部委託などで責任を移す
受容 残存リスクを理解した上で受け入れる
補足

リスク = 発生可能性 × 影響度。脅威モデリング（例: STRIDE）で「何が、どう攻撃され得るか」を洗い出して設計に反映します。

3.3 インシデント後の設計見直し

根本原因（Root Cause）を特定 → 欠けていた統制（コントロール）を特定 → 設計・運用を修正 → 再発防止を検証。「担当者のミス」で終わらせず、仕組みで防ぐ。
