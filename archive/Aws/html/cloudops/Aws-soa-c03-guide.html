7 事業継続(BC)と災害復旧(DR)の手順を実施する

Step 1. Task 1.1 メトリクス・アラーム・フィルターの実装

Skill 1.1.1 🔴 CloudWatch / CloudTrail / Managed Prometheus で監視とログを構成する

公式スキル文: AWS サービス(例: Amazon CloudWatch、AWS CloudTrail、Amazon Managed Service for Prometheus)を使い、ワークロード(例: サーバーレス、コンピュート、AI)の監視とログを構成する。

(1) まず用語を整理しよう

用語 意味 たとえ話
メトリクス 時系列の数値データ(CPU 使用率など) 体温計の数値
ログ テキストの記録(アプリのエラー出力など) 日記・業務日誌
トレース リクエストが通った経路の記録 荷物の追跡番号
アラーム メトリクスが閾値を超えたら状態が変わる仕組み 体温が 38 度を超えたらアラーム
監査ログ 「誰が・いつ・何をしたか」の記録 防犯カメラの記録

(2) 3 つの主要サービスの役割分担

サービス 役割 主な用途
Amazon CloudWatch メトリクス・ログ・アラーム・ダッシュボード 性能監視、アプリログ分析、異常検知
AWS CloudTrail AWS API 呼び出しの記録(監査) 「誰が SG を変更したか」の調査、コンプライアンス
Amazon Managed Service for Prometheus (AMP) Prometheus 互換のメトリクス管理サービス コンテナ(EKS / ECS)のメトリクス収集

💡 CloudWatch = 性能・稼働の監視 / CloudTrail = 操作の監査 と覚えると、選択肢の取り違えを防げます。

(3) CloudWatch の基本構造

押さえるポイント

項目 内容
名前空間(Namespace) メトリクスをグループ化する入れ物(例: AWS/EC2、エージェントの既定は CWAgent)
ディメンション メトリクスを識別する名前と値のペア(例: InstanceId)
EC2 の標準メトリクス 既定(基本モニタリング)は 5 分間隔、詳細モニタリングを有効化すると 1 分間隔
標準メトリクスに ない もの EC2 の メモリ使用率・ディスク使用率 は標準では取得できない → CloudWatch エージェント が必要(Skill 1.1.2)
高解像度カスタムメトリクス 最短 1 秒間隔で発行可能
メトリクスフィルター ログ内のパターン(例: ERROR)を数えてメトリクス化し、アラームにつなぐ
Logs Insights ログに対するクエリ言語での集計・検索
ログのリテンション ロググループごとに保持期間を設定(既定は無期限のため、コストに注意)

Logs Insights のクエリ例(エラーの件数を 5 分ごとに集計)

plaintext
fields @timestamp, @message
| filter @message like /ERROR/
| stats count() as errorCount by bin(5m)
| sort @timestamp desc

(6) ベストプラクティス

  • 標準メトリクスで足りない部分(メモリ・ディスク・プロセス)は CloudWatch エージェント で補う
  • ロググループには 保持期間を必ず設定 し、不要なログのコスト増大を防ぐ
  • 証跡(Trail)を全リージョンで有効化 し、S3 に保存。ログファイル検証を有効にする
  • 重要なアカウントでは 組織の証跡 で集約し、保存先 S3 を別アカウントに分離する
  • 「監視 = CloudWatch」「監査 = CloudTrail」の役割を混同しない
  • アラームは ユーザー影響に近い指標(エラー率・レイテンシ)を優先し、アラート疲れを避ける

(7) つまずきポイント(試験の定番)

症状・設問 答え
EC2 のメモリ使用率が CloudWatch に出ない 標準メトリクスには含まれない → CloudWatch エージェントをインストール

Skill 1.1.2 🔴 CloudWatch エージェントの設定と管理

公式スキル文: CloudWatch エージェントを設定・管理し、EC2 インスタンス、Amazon ECS クラスター、Amazon EKS クラスターからメトリクスとログを収集する。SOA-C03 で追加されたスキルです。

(1) なぜ必要か

EC2 の標準メトリクスは ハイパーバイザー側から見える情報 です。OS の内側(メモリ、ディスク使用率、プロセス、アプリログ)は見えません。これを補うのが CloudWatch エージェント です。

(2) EC2 への導入の流れ

項目 内容
必要な権限 AWS 管理ポリシー CloudWatchAgentServerPolicy を持つ IAM ロール(Parameter Store から設定を読む場合は追加権限が必要な場合あり)
インストール方法 Systems Manager の Run Command / Distributor、パッケージ手動インストール、AMI に事前組み込み
設定ファイル JSON。metrics(収集するメトリクス)、logs(収集するログファイル)などを定義。amazon-cloudwatch-agent-config-wizard で対話的に作成可能
設定の一元管理 Systems Manager Parameter Store に保存し、複数インスタンスで共有
既定の名前空間 CWAgent
収集できるもの メモリ、ディスク使用率、スワップ、ネットワーク、プロセス(procstat)、カスタムログファイル、StatsD / collectd のメトリクス
対応環境 Linux / Windows / オンプレミスサーバー(ハイブリッド)

設定ファイルの最小例(メモリ・ディスクとログ 1 つ)

json
{
  "metrics": {
    "append_dimensions": { "InstanceId": "${aws:InstanceId}" },
    "metrics_collected": {
      "mem":  { "measurement": ["mem_used_percent"] },
      "disk": { "measurement": ["used_percent"], "resources": ["/"] }
    }
  },
  "logs": {
    "logs_collected": {
      "files": {
        "collect_list": [
          {
            "file_path": "/var/log/messages",
            "log_group_name": "/ec2/messages",
            "log_stream_name": "{instance_id}"
          }
        ]
      }
    }
  }
}

(3) ECS / EKS での収集

環境 収集方法 ポイント
Amazon ECS Container Insights を有効化(クラスター設定)。EC2 起動タイプでは CloudWatch エージェントをデーモンとして実行する構成も使用 タスク / サービス単位の CPU・メモリ・ネットワークを可視化。Fargate はクラスターの Container Insights 設定で収集
Amazon EKS Amazon CloudWatch Observability の EKS アドオン(エージェントと Fluent Bit をまとめて導入) ノード / Pod / コンテナのメトリクスとログ。アドオン用のサービスアカウントに IAM 権限が必要(IRSA / EKS Pod Identity)

(4) ベストプラクティス

  • 設定ファイルは Parameter Store に集約 し、全台に同一設定を配布する(設定のばらつきを防ぐ)
  • エージェントは Golden AMI に組み込む か、State Manager の関連付け で導入・更新を自動化する
  • 収集するメトリクス・ログは 必要なものに絞る(カスタムメトリクスとログ取り込みは課金対象)
  • ログは ロググループの保持期間 を設定する
  • EKS は アドオン を使うと導入・更新が簡単。権限は ノードのロールではなく Pod 単位(IRSA / Pod Identity)で付与する方が最小権限に近づく

(5) つまずきポイント(トラブルシュート)

症状 確認すること
メトリクスが CloudWatch に出ない IAM ロールの権限、エージェントが起動しているか、設定ファイルの構文、ネットワーク経路(インターネット / NAT / CloudWatch の VPC エンドポイント)
ログが出ない file_path の誤り、ログファイルの読み取り権限、ロググループ名
設定を変えたのに反映されない fetch-config でエージェントの再読み込みをしたか
エージェントのログを見たい Linux では /opt/aws/amazon-cloudwatch-agent/logs/amazon-cloudwatch-agent.log

Skill 1.1.3 🔴 CloudWatch アラームの設定・特定・トラブルシュート(複合アラーム含む)

公式スキル文: AWS サービスを直接、または Amazon EventBridge 経由で呼び出せる CloudWatch アラームを設定・特定・トラブルシュートする(例: 複合アラームの作成と、呼び出せるアクションの特定)。

(1) アラームの 3 つの状態

状態 意味
OK メトリクスが閾値の範囲内
ALARM メトリクスが閾値を超えている(条件を満たした)
INSUFFICIENT_DATA データが不足していて判定できない(開始直後、データ欠落など)

(2) アラームの評価の仕組み

設定項目 意味
期間(Period) 1 つのデータポイントを集計する時間幅
統計(Statistic) 平均、最大、合計、パーセンタイルなど
評価期間 / M out of N 「直近 N 個のデータポイントのうち M 個が閾値超過」で ALARM(一時的なスパイクで鳴らさないために使う)
欠落データの扱い missing(既定)/ notBreaching(正常扱い)/ breaching(異常扱い)/ ignore(直前の状態を維持)
異常検知アラーム 過去の傾向から期待値の帯を学習し、外れたら ALARM
メトリクス数式 複数メトリクスを式で組み合わせてアラーム化(例: エラー数 / リクエスト数)

(3) アラームが実行できるアクション

アクションの種類 内容 単一アラーム 複合アラーム
SNS トピックへ通知 メール・SMS・Lambda など ○ ○
EC2 アクション 停止 / 終了 / 再起動 / 復旧(recover) ○ ×
Auto Scaling アクション スケーリングポリシーの実行 ○ ×
Systems Manager アクション OpsItem / インシデントの作成 ○ ○
EventBridge アラームの 状態変化イベント が自動的に EventBridge に送られ、ルールで Lambda 等を呼べる ○ ○

💡 試験の定番: 「アラームから直接 EC2 を復旧・再起動したい」→ 単一アラームの EC2 アクション。「複数のアラームの組み合わせで通知したい」→ 複合アラーム(ただし EC2 / Auto Scaling アクションは持てない)。

(4) 複合アラーム(Composite Alarm)

複数のアラームを AND / OR / NOT で組み合わせて 1 つのアラームにします。ノイズ(誤検知)の削減が目的です。

項目 内容
ルール式の例 ALARM("cpu-high") AND ALARM("latency-high")
利点 「CPU が高いだけ」では通知せず、「CPU も遅延も悪い」ときだけ通知できる
アクション抑制 抑制用アラーム(ActionsSuppressor)を指定して、メンテナンス中などに通知を止められる

(5) EC2 の自動復旧アラーム

StatusCheckFailed_System(システムステータスチェック失敗)に recover アクション を設定すると、基盤ハードウェア障害時に 同じインスタンス ID・同じ IP を保ったまま別ハードウェアへ復旧 できます。

(6) ベストプラクティス

  • 閾値超過が 一瞬だけ で鳴らないよう、M out of N と適切な期間を使う
  • 欠落データの扱い を意図的に選ぶ(例: 通常は定期的にデータが来るメトリクスで、途絶えたら異常にしたいなら breaching)
  • 複合アラームで 通知の重複・ノイズを減らす
  • アラームの名前・説明に 対応手順(ランブック)へのリンク を書く
  • アラームは IaC(CloudFormation / CDK)で管理 する

(7) トラブルシュート

症状 原因と対処
ずっと INSUFFICIENT_DATA メトリクスが発行されていない / ディメンションの指定ミス / リージョン違い / 欠落データの扱い設定
ALARM なのに通知が来ない SNS トピックのアクセスポリシー、サブスクリプションの未承認、トピックの KMS 暗号化設定(Skill 1.1.5 参照)
アクションが実行されない アクションの ARN 誤り、IAM 権限(例: EC2 アクションにはサービスリンクロール等)

(8) 参考 URL

  • CloudWatch アラーム: https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/AlarmThatSendsEmail.html
  • 複合アラーム: https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Create_Composite_Alarm.html

Skill 1.1.4 🟡 クロスアカウント / クロスリージョンのダッシュボード

項目 内容

Skill 1.1.5 🔴 SNS への通知設定

公式スキル文: AWS サービスが Amazon SNS に通知を送るよう設定し、アラームが SNS 通知を送るよう設定する。

(1) SNS の基本(Pub/Sub モデル)

用語 意味
トピック メッセージの送り先となる論理的なチャンネル
パブリッシャー トピックにメッセージを送る側(CloudWatch、S3、自分のアプリなど)
サブスクライバー トピックからメッセージを受け取る側
サブスクリプションのプロトコル メール、SMS、HTTP/HTTPS、Lambda、SQS、Kinesis Data Firehose、モバイルプッシュなど
標準トピック / FIFO トピック 標準 = 高スループット・順序は保証されない / FIFO = 順序保証・重複排除(SQS FIFO と組み合わせ)

(2) 「AWS サービス → SNS」で最重要の考え方

AWS サービスが SNS に発行するには、トピックのアクセスポリシー(リソースベースポリシー)で、そのサービスのプリンシパルに sns:Publish を許可 する必要があります。

発行元 プリンシパルの例 補足
CloudWatch アラーム cloudwatch.amazonaws.com コンソールから作成すると自動で許可されることが多い
S3 イベント通知 s3.amazonaws.com ソースのバケット ARN / アカウントを Condition で絞る
EventBridge ルール events.amazonaws.com ターゲットとして SNS を指定
Auto Scaling 通知 Auto Scaling が通知を送る設定 ライフサイクルイベントの通知など
CloudFormation スタックの通知 ARN に SNS を指定 スタックイベントの通知

アクセスポリシーの例(S3 から発行を許可)

json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "s3.amazonaws.com" },
    "Action": "sns:Publish",
    "Resource": "arn:aws:sns:ap-northeast-1:111122223333:my-topic",
    "Condition": {
      "ArnLike": { "aws:SourceArn": "arn:aws:s3:::my-bucket" },
      "StringEquals": { "aws:SourceAccount": "111122223333" }
    }
  }]
}

(3) 暗号化トピックの落とし穴

ポイント 内容
暗号化 トピックは KMS による保管時暗号化(SSE)を設定できる
AWS マネージドキー(alias/aws/sns)の制約 CloudWatch アラームや EventBridge などのサービスが発行する場合、AWS マネージドキーではキーポリシーを変更できず発行に失敗する
対処 カスタマー管理キー を使い、キーポリシーで cloudwatch.amazonaws.com などに kms:GenerateDataKey* と kms:Decrypt を許可する

(4) その他の機能

機能 内容
メッセージフィルタリング サブスクリプションごとにフィルターポリシーを設定し、必要なメッセージだけ受信
配信ポリシー / リトライ HTTP/S エンドポイントへの再試行設定
デッドレターキュー(DLQ) 配信に失敗したメッセージを SQS に退避
ファンアウト 1 つの SNS トピック → 複数の SQS キューへ配信

(5) ベストプラクティス

  • 通知先は 個人メールではなく配布リスト / ChatOps / オンコールツール にする
  • トピックアクセスポリシーは aws:SourceArn / aws:SourceAccount で発行元を絞る(混乱した代理人問題の対策)
  • 重大度別にトピックを分ける(例: critical / warning)
  • 重要な配信には DLQ を設定し、失敗を検知できるようにする
  • メールのサブスクリプションは 承認(Confirm)しないと有効にならない

(6) トラブルシュート

症状 原因
通知が届かない サブスクリプション未承認、アクセスポリシーの不足、KMS キーポリシーの不足、フィルターポリシーで除外
S3 イベント通知の設定が保存できない SNS トピックのアクセスポリシーに S3 からの発行許可がない

(7) 参考 URL

  • SNS 概要: https://docs.aws.amazon.com/sns/latest/dg/welcome.html
  • SNS の保管時暗号化: https://docs.aws.amazon.com/sns/latest/dg/sns-server-side-encryption.html

Step 2. Task 1.2 監視メトリクスによる問題の特定と修復

Skill 1.2.1 🔴 パフォーマンスメトリクスの分析と自動修復

公式スキル文: AWS サービスと機能(例: CloudWatch、Lambda、AWS Systems Manager、CloudTrail、Kiro、AWS DevOps Agent)を使い、パフォーマンスメトリクスを分析して修復戦略を自動化する。

(1) 自動修復の基本パターン

「検知 → 判断 → 実行」を 人手を介さずに つなぐのが自動修復です。

修復の例 方法
EC2 のハードウェア障害 CloudWatch アラーム(StatusCheckFailed_System)の recover アクション
アプリのハング アラーム → EventBridge → SSM Automation で再起動
負荷増大 アラーム → Auto Scaling ポリシー
設定ドリフト / 違反 AWS Config ルール → 修復アクション(SSM Automation)
不審な操作 CloudTrail イベント → EventBridge → Lambda で取り消し

(2) 使うサービスの役割

サービス 役割
CloudWatch メトリクス・ログ・アラームで「異常」を検知
CloudTrail 「誰が・何を変更したか」で原因を特定(変更起因の障害調査)
Lambda 任意のロジックによる修復処理
Systems Manager Automation ランブック、Run Command、OpsCenter による修復と運用管理

(3) 新しい AI 系の運用支援(公式文の例示)

サービス 概要
AWS DevOps Agent インシデントを自律的に調査する「フロンティアエージェント」。CloudWatch のアラームなどをトリガーに、テレメトリ・コード・デプロイ履歴を相関させ、原因の推定や緩和策の提案を行う。AWS だけでなくマルチクラウド / オンプレミスも対象。EventBridge イベントの発行にも対応
Kiro AWS のエージェント型開発支援ツール(IDE / CLI)。運用作業のスクリプト化や IaC の修正をエージェントに支援させる用途で例示されている

📝 学習上の注意: これらは公式スキル文の例示ですが、試験の中心は依然として CloudWatch / EventBridge / Lambda / Systems Manager による自動化の理解 です。AI エージェントは「調査・原因推定を速める補助」であり、権限(IAM)を最小化し、人間が承認する運用 を前提に考えるのが安全です。

(4) ベストプラクティス

  • まず検知を正確に: ユーザー影響に近い指標(エラー率・レイテンシ)でアラームを設定する
  • 自動修復は 冪等(何度実行しても同じ結果) に作る。再起動の無限ループにならないよう 回数制限やクールダウン を入れる
  • 自動修復の実行ロールは 最小権限
  • 変更が原因の障害は CloudTrail で変更履歴を確認 する
  • 重大な操作(削除・本番変更)は 承認ステップ(aws:approve) を挟む
  • 修復の結果も メトリクス / ログ / 通知で追跡 する

Skill 1.3.2 🔴 EBS の性能メトリクス分析・トラブルシュート・ボリュームタイプ最適化

公式スキル文: Amazon EBS のパフォーマンスメトリクスを分析し、問題をトラブルシュートし、ボリュームタイプを最適化して性能向上とコスト削減を図る。

(1) EBS ボリュームタイプ早見表

分類 タイプ 特徴 主な用途
汎用 SSD gp3 基準 3,000 IOPS / 125 MiB/s を容量と無関係に確保。IOPS・スループットを 個別に追加可能。gp2 より安価 大半のワークロードの既定の選択
汎用 SSD gp2 容量に比例して IOPS が増える(3 IOPS/GiB)+ バースト 旧世代。gp3 への移行を検討
プロビジョンド IOPS SSD io2 / io2 Block Express 高い耐久性・最大級の IOPS・低レイテンシ ミッションクリティカルな DB
プロビジョンド IOPS SSD io1 旧世代の PIOPS 旧環境
スループット最適化 HDD st1 低コスト・高スループットの シーケンシャル I/O ビッグデータ、ログ処理(ブートボリューム不可)
コールド HDD sc1 最安・アクセス頻度の低いデータ アーカイブ的なデータ(ブートボリューム不可)

💡 「gp2 → gp3」は王道の最適化: 多くの場合、ボリュームタイプを変更するだけで コストを下げつつ性能も維持・向上 できます。しかも Elastic Volumes によって 稼働中のまま 変更可能です。

(2) 見るべき EBS メトリクス

メトリクス 意味 読み方
VolumeReadOps / VolumeWriteOps I/O 回数 IOPS の消費状況
VolumeReadBytes / VolumeWriteBytes 転送バイト数 スループットの消費状況
VolumeQueueLength 待ち行列の長さ 大きいと I/O が詰まっている(性能不足のサイン)
VolumeIdleTime I/O が無かった時間 常に高いならほぼ未使用(コスト削減候補)
BurstBalance バースト残量(gp2、st1、sc1) 0 に近づくと性能が基準値まで低下
VolumeThroughputPercentage プロビジョンド IOPS の達成率 期待値に届いているか

(3) 性能が出ないときの切り分け

ポイント 内容
インスタンス側の上限 ボリュームだけ強くしても、EC2 インスタンス自体の EBS 帯域 / IOPS 上限 がボトルネックになる
EBS 最適化 現行世代の多くは既定で有効。EBS 専用帯域を確保
作成直後のスナップショットからのボリューム データが初回アクセス時に S3 から遅延ロードされ 初回は遅い → 高速スナップショットリストア(Fast Snapshot Restore) で回避、またはあらかじめ全ブロックを読む
Multi-Attach io1 / io2 を複数の Nitro インスタンス(同一 AZ)に同時接続(クラスター対応アプリ向け)

(4) Elastic Volumes による変更

変更できるもの 内容
サイズ 拡張のみ(縮小は不可)。拡張後は OS 側でファイルシステムも拡張 する必要がある
ボリュームタイプ 例: gp2 → gp3
IOPS / スループット 対応タイプで調整
制約 変更後、次の変更まで一定の待機時間(クールダウン)がある

(5) ベストプラクティス

  • 新規は gp3 を既定 にする。既存の gp2 は gp3 へ移行を検討
  • VolumeQueueLength・BurstBalance にアラーム を設定する
  • 未使用ボリューム(VolumeIdleTime が高い、未アタッチ)を 定期的に棚卸し する
  • 暗号化ボリュームは アカウント・リージョン単位の「既定で暗号化」 を有効にしておく
  • スナップショットは データライフサイクルマネージャー(DLM)/ AWS Backup で自動化する(Skill 2.3.1)

📝 S3 Files について: 2026 年 4 月に発表された新機能で、EC2、ECS、EKS、Lambda から S3 のデータをファイルとして扱えます。ファイル操作の変更は S3 に同期され、S3 側の変更もファイル側に反映されます(通常は数秒〜 1 分程度)。「S3 のデータをアプリ改修なしでファイルとして共有したい」という設問で選択肢になります。小さなファイルの頻繁な更新より、大きなファイルの順次読み取り に向いています。

ライフサイクル管理 一定期間アクセスのないファイルを IA / Archive に自動移行 してコスト削減。日数は 1〜365 日の選択肢から設定。アクセスされたら Standard に戻す 設定(Intelligent-Tiering)も可能
マウント マウントターゲット(各 AZ に作成)経由。セキュリティグループで NFS(TCP 2049) を許可
暗号化 保管時暗号化は 作成時に指定(後から変更不可)。転送中は TLS(amazon-efs-utils の -o tls)

Skill 2.1.3 🔴 マネージドデータベースのスケーリング(RDS / DynamoDB など)

公式スキル文: AWS マネージドデータベース(例: Amazon RDS、DynamoDB)のスケーリングを設定・管理する。

(1) RDS / Aurora のスケーリング手段

手段 方向 内容 注意
インスタンスクラス変更 垂直 CPU・メモリの増減 変更時に 一時的な停止(再起動) が発生。Multi-AZ なら短縮されるが、ゼロではない
ストレージの自動スケーリング 垂直 空きが少なくなると自動で拡張(上限を設定) 容量の縮小はできない
リードレプリカ 水平(読み取り) 読み取りを分散。非同期レプリケーション。RDS の MySQL / MariaDB / PostgreSQL は最大 15 台、Oracle / SQL Server は最大 5 台 書き込みは分散されない。ReplicaLag の監視が必要
Aurora レプリカ 水平(読み取り) 同一ストレージを共有するため レプリカラグが小さい。最大 15 台 リーダーエンドポイントで自動分散
Aurora Auto Scaling 水平 CPU や接続数に応じて Aurora レプリカを自動増減 書き込み(ライター)は対象外
Aurora Serverless v2 垂直(自動・細かい) ACU(Aurora Capacity Unit) 単位で負荷に応じて 秒単位で自動伸縮 最小・最大 ACU を設定

(2) DynamoDB のキャパシティモード

モード 内容 向いているケース
オンデマンド リクエスト数に応じて自動対応・課金。事前のキャパシティ計画が不要 予測不能・変動が大きい・新規ワークロード
プロビジョンド RCU(読み取りキャパシティ)/ WCU(書き込みキャパシティ) を指定。Auto Scaling と併用可能 予測可能で安定した負荷(コスト効率が良い)
用語 意味
RCU 1 RCU = 最大 4 KB の項目を 強力な整合性 で毎秒 1 回(結果整合性なら 2 回)読み取れる
WCU 1 WCU = 最大 1 KB の項目を毎秒 1 回書き込める
ProvisionedThroughputExceededException プロビジョンドの容量を超えた(スロットリング)。バックオフ付きリトライ、容量増加、Auto Scaling
ホットパーティション 特定のキーにアクセスが集中。パーティションキーの設計見直し(キーを分散)
アダプティブキャパシティ 偏りに応じてパーティション間で容量を自動調整(ただし万能ではない)
DAX DynamoDB 専用のインメモリキャッシュ(読み取りをマイクロ秒に)
グローバルテーブル 複数リージョンのマルチアクティブ・レプリケーション

(3) ベストプラクティス

  • 読み取り中心なら レプリカ / キャッシュ を先に検討(書き込みはスケールアップが基本)
  • ストレージの自動スケーリングを有効化 し、容量逼迫による停止を防ぐ
  • 変動が激しいワークロードは Aurora Serverless v2 / DynamoDB オンデマンド
  • 安定した DynamoDB は プロビジョンド + Auto Scaling でコスト最適化
  • SDK の 指数バックオフ + ジッター のリトライを活用し、スロットリングに備える
  • DB への接続爆発は RDS Proxy で緩和する

Skill 2.2.1 🔴 ELB と Route 53 ヘルスチェックの設定・トラブルシュート

公式スキル文: Elastic Load Balancing (ELB) と Amazon Route 53 のヘルスチェックを設定・トラブルシュートする。

(1) ロードバランサーの種類

種類 レイヤー 特徴 主な用途
ALB L7(HTTP / HTTPS / gRPC) パス・ホスト・ヘッダーによるルーティング、WAF 連携、Lambda ターゲット Web アプリ、マイクロサービス

(2) ヘルスチェックの仕組み

ロードバランサーはターゲットを定期的にチェックし、異常なターゲットへのトラフィックを止めます。

設定 内容
プロトコル / ポート / パス 例: HTTP:80 /health(軽量でアプリの状態を反映するエンドポイントを用意)
間隔(Interval) チェックの周期
タイムアウト 応答を待つ時間
正常のしきい値 / 異常のしきい値 連続成功 / 連続失敗が何回で状態を切り替えるか
成功コード(Matcher) 正常とみなす HTTP ステータス(既定は 200)

(3) ALB の関連機能

機能 内容
クロスゾーン負荷分散 全ターゲットに均等に分散。ALB は常に有効(NLB は既定で無効・有効化すると AZ 間データ転送料金が発生しうる)

(4) ALB のエラーコードと原因

コード 意味 よくある原因

ポート トラフィックポートとヘルスチェックポートの違い
アプリの起動時間 起動完了前にチェックされていないか(猶予期間・しきい値)
NACL・ルート サブネットの NACL がブロックしていないか

(6) Route 53 ヘルスチェック

種類 内容
エンドポイント Route 53 のヘルスチェッカーが世界各地から HTTP / HTTPS / TCP でエンドポイントを監視。間隔は 30 秒(標準)または 10 秒(高速)
計算されたヘルスチェック 複数のヘルスチェックを AND / OR などで組み合わせ
CloudWatch アラームベース CloudWatch アラームの状態をヘルスの判定に使用。プライベートなリソース(VPC 内)の監視に有効
重要ポイント 内容
到達性 ヘルスチェッカーは インターネット側から アクセスするため、SG / ファイアウォールでヘルスチェッカーの IP を許可 する必要がある

Skill 2.2.2 🔴 耐障害システムの構成(Multi-AZ など)

公式スキル文: 耐障害システム(例: Multi-AZ デプロイ)を構成する。

(1) 基本の考え方

単一障害点(SPOF)をなくす こと。AWS では 複数の AZ(アベイラビリティーゾーン) にまたがって配置するのが基本です。

用語 意味
リージョン 地理的な地域(例: 東京 ap-northeast-1)
AZ リージョン内の独立したデータセンター群(電源・ネットワークが分離)
高可用性 部分的な障害があってもサービスを継続できること
耐障害性 障害が起きても ユーザー影響なく 動き続けること

(2) サービス別の Multi-AZ

サービス 構成 ポイント
EC2 + ASG 複数 AZ のサブネットに分散 AZ 障害時は残りの AZ で稼働を継続し、不足分を補充
ELB 複数 AZ にノードを配置 各 AZ にサブネットを指定(ALB は 2 つ以上の AZ が必須)
RDS Multi-AZ(DB インスタンス) 同期レプリケーション のスタンバイを別 AZ に配置 障害時に 自動フェイルオーバー(エンドポイント名は変わらず DNS が切り替わる)。スタンバイは 読み取り不可
RDS Multi-AZ DB クラスター 読み取り可能なスタンバイ 2 台を 3 つの AZ に配置 高速なフェイルオーバーと読み取りのスケール
Aurora ストレージが 3 つの AZ に 6 つのコピー を自動保持 レプリカが別 AZ にあれば短時間でフェイルオーバー
EFS リージョナルな EFS は複数 AZ にデータを保存 各 AZ にマウントターゲットを作成
S3 標準クラスは複数 AZ に自動保存 One Zone 系クラスは 単一 AZ
NAT ゲートウェイ AZ 単位のリソース(AZ 内で冗長) AZ ごとに作成 し、各 AZ のルートテーブルから自 AZ の NAT へ
DynamoDB 複数 AZ に自動レプリケーション グローバルテーブルでマルチリージョン

(3) RDS Multi-AZ と リードレプリカの違い(超頻出)

項目 Multi-AZ リードレプリカ
目的 可用性・耐障害性 読み取りの性能向上(スケール)
レプリケーション 同期(DB インスタンス構成) 非同期
読み取り スタンバイは基本不可(Multi-AZ DB クラスターは可) 可能
フェイルオーバー 自動 手動で昇格(自動ではない)
別リージョン 不可(同一リージョン内) 可能(クロスリージョンレプリカ)

💡 「可用性を上げたい」→ Multi-AZ、「読み取り性能を上げたい」→ リードレプリカ と覚える。

(4) 耐障害性を検証する

手段 内容
AWS Fault Injection Service(FIS) 障害を意図的に注入して(インスタンス停止、ネットワーク遅延など)耐障害性を検証するカオスエンジニアリング
手動フェイルオーバー RDS の「再起動(フェイルオーバーあり)」でフェイルオーバーを試験
Well-Architected Framework 信頼性の柱でのレビュー

(5) ベストプラクティス

  • 本番は最低 2 AZ、可能なら 3 AZ に分散する
  • ステートレスにし、状態は外部に保持 する(AZ 障害時の入れ替えを容易に)
  • NAT ゲートウェイは AZ ごと に置き、AZ をまたぐ通信とコストを避ける
  • RDS の Multi-AZ を本番で有効化 する。アプリは エンドポイント(DNS 名)で接続 し、IP 直指定しない
  • 障害対応手順を 定期的にテスト(ゲームデイ / FIS) する
  • 「単一 AZ の構成」(One Zone ストレージ等)は 可用性要件と照らして選ぶ

  • AWS FIS: https://docs.aws.amazon.com/fis/latest/userguide/what-is.html

Skill 2.3.1 🔴 スナップショット・バックアップの自動化(AWS Backup など)

公式スキル文: AWS サービス(例: AWS Backup)を使い、AWS リソース(例: EC2 インスタンス、RDS DB インスタンス、EBS ボリューム、S3 バケット、DynamoDB テーブル)のスナップショットとバックアップを自動化する。

(1) AWS Backup の構成要素

要素 意味
バックアッププラン いつ・どのくらい保持するかのポリシー(複数のルールで構成)

(2) サービス別のバックアップ手段

DynamoDB オンデマンドバックアップ + PITR(35 日) AWS Backup と統合
S3 バージョニング、レプリケーション(CRR / SRR) AWS Backup による S3 バックアップ(継続バックアップで PITR も可)

  • 重要なバックアップは ボールトロック で削除・改ざんから保護する
  • Organizations のバックアップポリシー で全アカウントに統一ルールを適用する
  • バックアップは 暗号化(KMS)し、定期的にリストアテスト を行う(復元できて初めてバックアップ)
  • ライフサイクル でコールドストレージへ移行してコストを最適化する
  • Backup Audit Manager でコンプライアンスを継続確認する

Skill 2.3.2 🔴 データベースの復元方法(ポイントインタイムリストアなど)と RTO / RPO / コスト

公式スキル文: 復旧時間目標(RTO)、復旧時点目標(RPO)、コスト要件を満たすために、さまざまな方法でデータベースを復元する(例: ポイントインタイムリストア)。

(1) RTO と RPO

用語 意味 覚え方
RPO どの時点のデータまで戻せればよいか(許容データ損失) Point = 時点
RTO どれだけの時間で復旧すべきか(許容停止時間) Time = 時間

(2) RDS の復元方法

方法 内容 重要ポイント
スナップショットからの復元 手動 / 自動スナップショットの時点に戻す 常に新しい DB インスタンスを作成 → 新しいエンドポイント になる(アプリの接続先変更が必要)
ポイントインタイムリストア(PITR) 自動バックアップ + トランザクションログで 保持期間内の任意の時点(約 5 分前まで)に復元 自動バックアップが有効 であることが前提。新しい DB インスタンスとして復元
クロスリージョン スナップショットを別リージョンへコピーして復元 DR 用。暗号化スナップショットは KMS キーの扱いに注意
Aurora バックトラック MySQL 互換の Aurora で、DB クラスターを巻き戻す(新しいクラスターを作らず時間を戻す) MySQL 互換 Aurora のみ。事前に有効化が必要
Aurora クローン ストレージを共有する 高速・低コストな複製(テスト用など) コピーオンライト方式

⚠️ 復元は「その場で上書き」ではなく「新しいインスタンスを作る」 のが原則(Aurora バックトラックを除く)。復元後は エンドポイントの切り替え や、必要なデータだけを抽出して戻す 作業が必要です。

(3) DynamoDB の復元

方法 内容
PITR 過去 35 日以内の任意の時点(秒単位) に戻せる。新しいテーブルとして復元
オンデマンドバックアップ 任意のタイミングで取得。新しいテーブルとして復元
注意 PITR は 明示的に有効化 が必要(既定では無効)

(4) RTO / RPO / コストのトレードオフ

復元方式 一般的な RPO 一般的な RTO コスト
日次スナップショットからの復元 最大 24 時間 長め(新規作成 + 切替) 低
PITR 数分(直前まで) 中(新規作成 + 切替) 低〜中
Multi-AZ ほぼゼロ(同期) 1〜2 分程度(自動フェイルオーバー) 中(スタンバイ分)
クロスリージョン レプリカ / Aurora Global Database 秒単位の小さな遅延 分単位(昇格) 高

💡 ポイント: Multi-AZ は AZ 障害対策(可用性)であり、誤削除・論理的なデータ破損には効かない(破損も同期されてしまう)。論理的な破損には PITR / スナップショット / バックトラック が必要です。

(5) ベストプラクティス

  • 要件(RTO / RPO / コスト)から 手段を選ぶ(厳しい要件ほどコストが上がる)
  • RDS は 自動バックアップを有効化(保持期間を要件に合わせる)
  • 重要な DB は 復元を定期的に訓練 し、手順をランブック化する
  • 暗号化スナップショットを他アカウント / リージョンへ共有・コピーするときは カスタマー管理キーのキーポリシー・権限 を準備する
  • DynamoDB の本番テーブルは PITR を有効化 する

(6) 参考 URL

  • RDS のポイントインタイムリストア: https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html
  • DynamoDB のポイントインタイムリカバリ: https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Point-in-time-recovery.html

Skill 2.3.3 🟡 ストレージサービスのバージョニング(S3 / FSx など)

公式スキル文: ストレージサービス(例: Amazon S3、Amazon FSx)のバージョニングを実装する。

(1) S3 バージョニング

状態 内容
無効(既定) 上書き・削除すると元に戻せない
有効 同じキーへの上書きで 新しいバージョン が作られ、古いバージョンも残る
停止(Suspended) 新しいバージョンは作られないが、既存のバージョンは残る(一度有効化すると「無効」には戻せない)
動作 内容
削除 削除マーカー が付くだけで、実体は残る。バージョン ID を指定して削除すると完全に削除
復元 削除マーカーを削除する / 古いバージョンをコピーして最新にする
MFA Delete バージョンの完全削除とバージョニング状態の変更に MFA を要求(ルートユーザーのみ設定可)
ライフサイクル 非現行バージョン を一定期間後に移行・削除してコストを抑える
レプリケーション CRR / SRR は バージョニングが前提
Object Lock 保持期間・リーガルホールドで WORM を実現(バージョニングが前提)

(2) FSx のバージョニングに相当する機能

サービス 機能
FSx for Windows File Server シャドウコピー(Windows の「以前のバージョン」)でユーザーが自分でファイルを復元
FSx for NetApp ONTAP / OpenZFS スナップショット で時点を保持
共通 日次の自動バックアップ(AWS Backup 連携も可)

(3) ベストプラクティス

  • 重要なバケットでは バージョニングを有効化 する
  • 非現行バージョンのライフサイクル を必ず設定し、コストの無制限な増加を防ぐ
  • 誤削除 / ランサムウェア対策に MFA Delete や Object Lock を検討
  • FSx for Windows は シャドウコピーを有効化 してセルフ復元を可能に

Skill 2.3.4 🔴 災害復旧(DR)の手順とベストプラクティス

公式スキル文: 災害復旧の手順とベストプラクティスに従う(例: バックアップとリストア、パイロットライト、ウォームスタンバイ、アクティブ / アクティブ)。

(1) 4 つの DR 戦略

戦略 概要 RTO / RPO コスト
バックアップとリストア バックアップだけ別リージョンに保管。災害時にゼロから構築して復元 長い(時間〜日)/ 長い 最も低い
パイロットライト データ層だけ常時稼働(DB のレプリケーション)。アプリ層は停止状態(AMI / IaC)で、災害時に起動・拡張 数十分〜数時間 低い

マルチサイト(アクティブ / アクティブ) 複数リージョンで 常時フル稼働 し、Route 53 などで負荷分散 ほぼゼロ / ほぼゼロ 最も高い

💡 速くなるほど高くなる。「コスト最優先 → バックアップとリストア」「最小限のコアだけ常時稼働 → パイロットライト」「すぐ使える縮小版 → ウォームスタンバイ」「無停止 → アクティブ / アクティブ」。

(2) 戦略の選び方

(3) DR に使う AWS サービス

サービス 役割
AWS Backup クロスリージョン / クロスアカウントコピー
AWS Elastic Disaster Recovery(DRS) サーバーを継続的にレプリケーション(オンプレ / 他クラウド / AWS)し、災害時に短い RTO で起動(パイロットライト型)
Route 53 ヘルスチェック + フェイルオーバールーティングで切替
S3 クロスリージョンレプリケーション オブジェクトの別リージョンへの複製

DynamoDB グローバルテーブル マルチリージョンのアクティブ / アクティブ
CloudFormation / IaC 環境を 短時間で再現

(4) ベストプラクティス

  • RTO / RPO をビジネス要件から決め、それを満たす最小コストの戦略を選ぶ
  • DR 環境は別リージョン に置き、IaC で再現可能 にしておく

  • 暗号化キー(KMS)・シークレットも DR リージョンで利用可能に(マルチリージョンキー、シークレットのレプリケーション)
  • フェイルバック(元に戻す手順)も計画する

Skill 3.1.2 🔴 CloudFormation と AWS CDK によるリソース管理

公式スキル文: CloudFormation と AWS CDK を使って AWS リソースを作成・管理する。(SOA-C03 では「スタック」の作成・管理が追加)

(1) Infrastructure as Code(IaC)とは

インフラの構成を コード(テンプレート)として記述 し、同じ構成を 何度でも再現 できるようにする考え方です。

利点 内容
再現性 開発・本番で同じ構成を作れる
変更管理 Git で履歴・レビュー・ロールバック
自動化 CI/CD に組み込める
ドリフト検知 手動変更との差分を検出

(2) CloudFormation の基本

用語 意味
テンプレート YAML / JSON のリソース定義
スタック テンプレートから作られたリソースの まとまり(作成・更新・削除の単位)
変更セット(Change Set) 更新を 適用前にプレビュー する
ドリフト検出 実リソースがテンプレートと ズレていないか を検出

テンプレートの主なセクション

セクション 役割 必須
Parameters 実行時に渡す値(環境名、インスタンスタイプなど)
Mappings 固定の対応表(リージョン別 AMI など)
Conditions 条件によるリソース作成の切り替え
Resources 作成するリソース 必須
Outputs 他のスタックや利用者に出力する値(エクスポート可能)

よく使う組み込み関数

関数 用途
!Ref パラメータ値 / リソースの ID を参照
!GetAtt リソースの属性(ARN、DNS 名など)を取得
!Sub 文字列内に変数を埋め込む
!ImportValue 他スタックがエクスポートした値を参照
!If / !Equals 条件分岐

最小のテンプレート例

yaml
AWSTemplateFormatVersion: "2010-09-09"
Parameters:
  Env:
    Type: String
    AllowedValues: [dev, prod]
Resources:
  LogBucket:
    Type: AWS::S3::Bucket
    DeletionPolicy: Retain
    Properties:
      VersioningConfiguration:
        Status: Enabled
Outputs:
  BucketName:
    Value: !Ref LogBucket

(3) スタックの更新フロー

保護の仕組み 内容
DeletionPolicy スタック削除時の挙動(Delete / Retain / Snapshot。DB や EBS は Snapshot が有効)
UpdateReplacePolicy 更新で 置き換え が発生したときの旧リソースの扱い
スタックポリシー 更新時に 特定リソースの変更を禁止
終了保護 スタックの 誤削除を防止
ネストされたスタック 共通部品の再利用・テンプレートの分割
クロススタック参照 Outputs の Export と !ImportValue(参照されているスタックは削除不可)
カスタムリソース Lambda 等で CloudFormation 未対応の処理を実行
cfn-init / cfn-signal(CreationPolicy) EC2 内の設定と、起動完了のシグナル待ち

(4) AWS CDK(Cloud Development Kit)

項目 内容
概要 TypeScript / Python / Java / C# / Go などのプログラミング言語 でインフラを定義するフレームワーク
仕組み CDK のコード → cdk synth で CloudFormation テンプレートを生成 → CloudFormation がデプロイ
コンストラクト L1(CloudFormation そのもの)/ L2(推奨のデフォルト・ヘルパー付き) / L3(パターン = 複数リソースの組み合わせ)
主なコマンド cdk bootstrap(初回準備)、cdk synth、cdk diff(差分確認)、cdk deploy、cdk destroy
利点 ループ・条件・関数などで 簡潔に 書ける、型による補完、テスト可能

(5) ベストプラクティス

  • 変更セット / cdk diff で必ず差分を確認 してからデプロイ(特に 置換 に注意)
  • DB・ストレージなど 重要リソースには DeletionPolicy / UpdateReplacePolicy、スタックには 終了保護
  • ドリフト検出 を定期的に実施し、手動変更をしない 運用にする
  • テンプレートを ネスト / モジュール化 して再利用し、Git で管理する

  • リソース名をハードコードしすぎない(名前の固定は置換更新の失敗や重複の原因)
  • CloudFormation の実行には サービスロール を使い、最小権限にする

Skill 3.1.5 🔴 デプロイ戦略とサービスの実装

公式スキル文: デプロイ戦略とサービスを実装する。

(1) 主なデプロイ戦略の比較

戦略 仕組み ダウンタイム ロールバック コスト
All-at-once(一括) 全台を一度に更新 あり 遅い(再デプロイ) 最小
ローリング 数台ずつ順に更新 なし(ただし一部台数は処理能力が一時低下) やや遅い 低
ローリング(追加バッチ付き) 追加の新台数を先に立ててから更新 なし(能力維持) やや遅い 中
イミュータブル(Immutable) 新しい台数一式を別に作成し、成功したら切替・旧台数を削除 なし 速い(旧環境へ戻すだけ) 高(一時的に 2 倍)
Blue/Green 本番(Blue)と同じ新環境(Green)を用意し、トラフィックを切替 なし 非常に速い(切り戻し) 高(2 環境)
カナリア 一部(例 10%)のユーザーだけ 新バージョンへ → 問題なければ全体へ なし 速い 中
リニア 一定割合ずつ 段階的に 増やす なし 速い 中

(2) サービス別の実装

OU(組織単位) アカウントのグループ。ポリシーは OU 単位で継承
SCP(サービスコントロールポリシー) メンバーアカウントの権限の上限(ガードレール)。権限を「付与」するものではない
その他のポリシー タグポリシー、バックアップポリシー、AI サービスのオプトアウトポリシー、リソースコントロールポリシー(RCP)など
委任管理者 Security Hub、GuardDuty、Config、IAM Identity Center などの 管理を専用アカウントへ委任
一括請求 請求の統合・ボリューム割引

(3) SCP の重要ルール

ルール 内容
許可を与えない SCP は「許可できる最大範囲」。SCP で許可していても、IAM で許可しなければアクセスできない
管理アカウントには 適用されない 管理アカウントの ID は SCP の影響を受けない
影響範囲 メンバーアカウントのルートユーザーを含むすべての ID に影響
サービスリンクロール SCP の影響を受けない
戦略 拒否リスト方式(既定の FullAWSAccess を残し、禁止事項を Deny)が一般的 / 許可リスト方式(必要なものだけ許可)
よくある使い方 使用リージョンの制限、特定サービスの禁止、CloudTrail / Config の停止禁止、ルートユーザーの利用禁止、暗号化の強制

例: 東京・大阪以外のリージョンを拒否(グローバルサービスを除外)

json

  "Statement": [{

    "Resource": "",
    "Condition": {
      "StringNotEquals": { "aws:RequestedRegion": ["ap-northeast-1", "ap-northeast-3"] }
    }
  }]
}

(4) IAM Identity Center

項目 内容
役割 複数アカウントと業務アプリへの Single Sign-On(SSO) を一元管理
ID ソース Identity Center ディレクトリ / Active Directory / 外部 IdP(Okta、Entra ID など。SCIM でプロビジョニング)
権限セット(Permission Set) アカウントに割り当てる権限のテンプレート。各アカウントに IAM ロールとして自動展開 される
割り当て ユーザー / グループ × アカウント × 権限セット
利点 長期のアクセスキー不要(CLI も aws sso login で一時認証情報)、MFA の強制、集中管理

(5) AWS Control Tower(補足)

ランディングゾーン(推奨されるマルチアカウント環境)の自動構築と、ガードレール(予防的 = SCP / 検出的 = Config) の適用を提供します。

(6) ベストプラクティス

  • 管理アカウントを最小限に利用 し、ワークロードを置かない
  • ログ・セキュリティ用の 専用アカウント を作り、組織の証跡 のログは別アカウントに集約
  • SCP は小さく始めて段階的に適用(まず OU 単位でテスト)し、ルートでの Deny は慎重に
  • 人のアクセスは IAM Identity Center に統一し、IAM ユーザーを作らない
  • セキュリティサービスは 委任管理者で組織全体を集約管理

Skill 4.2.1 🟡 データ分類スキームの実装と強制

公式スキル文: データ分類スキームを実装し、強制する。

(1) データ分類とは

データを 機密度で分類(例: 公開 / 社内限定 / 機密 / 極秘)し、分類ごとに保護レベルを変える 考え方です。運用者は、決められた分類スキームを AWS 上で実装・強制 します(分類の定義自体は範囲外)。

分類(例) 保護の例
公開 暗号化は推奨、CloudFront で配信可
社内限定 IAM / SG でアクセス制限、暗号化
機密 KMS カスタマー管理キー、アクセスログ、MFA、ネットワーク制限
極秘 専用アカウント、Object Lock、厳格な監査、VPC エンドポイント経由のみ

(2) AWS での実装手段

手段 内容
タグ付け DataClassification=Confidential などを リソースに付与(分類の基盤)
Amazon Macie S3 内の機密データ(個人情報など)を自動検出・分類。機密データ検出ジョブ、自動検出。見つけた結果を EventBridge / Security Hub に連携
タグポリシー(Organizations) タグのキー・値の標準化(表記ゆれ防止)
ABAC(属性ベースのアクセス制御) タグを条件 にアクセス制御(aws:ResourceTag/DataClassification = aws:PrincipalTag/...)
SCP / IAM 条件 タグなしのリソース作成を拒否(aws:RequestTag)、タグの変更を制限
AWS Config required-tags ルールでタグの付与漏れを検出
保護の自動適用 分類に応じて 暗号化(KMS キー)、バージョニング、Object Lock、バックアップ を適用

(3) ベストプラクティス

  • 作成時にタグを強制(タグなしの作成を拒否)
  • Macie で想定外の場所にある機密データを継続的に検出
  • 分類ごとに 暗号化・アクセス制御・監査のレベルを標準化(IaC に組み込み)
  • ABAC で権限の管理をスケールさせる
  • 機密データの アクセスログ(S3 サーバーアクセスログ / CloudTrail データイベント) を有効化

Skill 4.2.2 🔴 保管時の暗号化の実装・設定・トラブルシュート(AWS KMS)

公式スキル文: 保管時の暗号化(例: AWS KMS)を実装・設定・トラブルシュートする。

(1) KMS の基本

用語 意味
KMS キー(旧 CMK) 暗号化に使うキー。キーそのものは KMS の外に出ない
エンベロープ暗号化 データは データキー で暗号化し、そのデータキーを KMS キーで暗号化 して保存
キーポリシー KMS キーに必須のリソースベースポリシー。キーポリシーが許可しない限り IAM だけではアクセス不可
グラント 一時的・プログラム的な権限委任(AWS サービスが内部的に使用)
エイリアス キーの別名(alias/my-key)

(2) キーの種類

種類 管理者 特徴
AWS 所有のキー AWS 利用者から見えない。無料
AWS マネージドキー(aws/s3 など) AWS(サービスごと) ローテーションは自動(毎年)。キーポリシーは変更不可
カスタマー管理キー 利用者 キーポリシーの管理、有効化 / 無効化、ローテーション設定、削除スケジュール、クロスアカウント共有が可能
項目 内容
キーローテーション カスタマー管理キーは 自動ローテーションを有効化(既定は 1 年ごと、期間を変更可能)。キー ID / ARN は変わらず、過去のデータは 古いキーマテリアルで復号 できる
削除 待機期間 7〜30 日(既定 30 日) を設ける。待機中は 使用不可、期間内なら キャンセル可能。削除したら そのキーで暗号化したデータは復号不能
キーの無効化 一時的に停止(復号もできなくなる)
マルチリージョンキー 同じキーマテリアルを複数リージョンで使用(DR、グローバルテーブル向け)
対称 / 非対称 既定は 対称(AES-256)

(3) サービス別の保管時暗号化

サービス ポイント
EBS ボリューム単位の暗号化。リージョンごとの「既定で暗号化」 を有効化可能。既存の暗号化なしボリュームを直接暗号化することはできない → スナップショット → 暗号化コピー → 新ボリューム
S3 SSE-S3(既定。すべての新規オブジェクトに自動適用)、SSE-KMS(監査・キー制御が必要な場合)、SSE-C、DSSE-KMS。S3 Bucket Keys で KMS 呼び出しを削減しコスト・スロットリングを軽減
RDS 作成時に暗号化を指定。既存の非暗号化インスタンスは直接暗号化できない → スナップショットを暗号化コピー → 復元。リードレプリカやスナップショットも暗号化される
DynamoDB 常に暗号化(キーの種類を選択)
EFS 作成時に暗号化を指定(後から変更不可)

(4) KMS のトラブルシュート

症状 原因と対処
AccessDeniedException / KMSInvalidStateException キーポリシーに許可がない、キーが 無効 / 削除予定、IAM 権限(kms:Decrypt、kms:GenerateDataKey、kms:Encrypt)
別アカウントから暗号化リソースを使えない キーポリシーで外部アカウントを許可 + 外部アカウントの IAM でも許可。AWS マネージドキーは共有不可
暗号化スナップショット / AMI を共有できない カスタマー管理キーで暗号化し、共有先にキーの使用権限を付与
EC2 / ASG の起動が失敗 サービスリンクロール(Auto Scaling) にキーの権限が必要
ThrottlingException(KMS のリクエスト上限) S3 の Bucket Keys、データキーのキャッシュ、リクエストの削減
キー削除後にデータが読めない 復旧不能。削除は待機期間を使い、使用状況を確認してから
条件 kms:ViaService 特定のサービス経由のみ キーを使えるように制限

(5) ベストプラクティス

  • 既定で暗号化(EBS の既定暗号化、S3 の既定暗号化、RDS・EFS は作成時に暗号化)
  • 監査・クロスアカウント・キー制御が必要なら カスタマー管理キー。自動ローテーションを有効化
  • キーポリシーは 最小権限、キー管理者と利用者を分離
  • 削除は 待機期間を使い、CloudTrail で使用状況を確認 してから
  • S3 + SSE-KMS には Bucket Keys でコスト・性能を最適化
  • KMS の使用は CloudTrail で全記録 されるため、監査に活用

  • キーのローテーション: https://docs.aws.amazon.com/kms/latest/developerguide/rotate-keys.html
  • EBS の暗号化: https://docs.aws.amazon.com/ebs/latest/userguide/ebs-encryption.html
  • S3 のデータ保護と暗号化: https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingEncryption.html

Skill 4.2.3 🔴 転送中の暗号化の実装・設定・トラブルシュート(AWS Certificate Manager)

公式スキル文: 転送中の暗号化(例: AWS Certificate Manager [ACM])を実装・設定・トラブルシュートする。

(1) 基本

TLS(HTTPS) で通信を暗号化し、盗聴と改ざん を防ぎます。AWS では ACM が証明書の発行と管理を担います。

ACM の機能 内容
パブリック証明書 無料。ドメイン所有を検証して発行
検証方法 DNS 検証(推奨):指定された CNAME レコードを DNS に追加。Route 53 なら自動追加も可能 / メール検証
自動更新 DNS 検証の CNAME を残している限り 自動更新される
統合サービス ALB / NLB / CloudFront / API Gateway などに 直接関連付け(ACM のパブリック証明書は標準では EC2 インスタンスに直接インストールできないため、LB や CloudFront で終端するのが基本)
プライベート CA 社内向けの プライベート証明書 を発行
インポート 外部で取得した証明書を ACM に取り込める(インポートした証明書は自動更新されない → 期限を自分で管理)

(2) 重要な注意点

注意点 内容
リージョン ACM の証明書は リージョンごと。ALB を使うならその ALB のリージョン に作成
CloudFront 用 米国東部(バージニア北部)us-east-1 で証明書を作成する必要がある(CloudFront の定番トラップ)
ワイルドカード *.example.com を発行可能(ルートドメイン example.com は別途追加が必要)

(3) 暗号化の実装ポイント

対象 設定
ALB HTTPS リスナー(443)に ACM 証明書 を設定。HTTP(80)→ HTTPS(443)のリダイレクト ルール。セキュリティポリシー(TLS バージョン・暗号スイート) を選択
CloudFront ビューアープロトコルポリシー(Redirect HTTP to HTTPS / HTTPS Only)、オリジンプロトコルポリシー
S3 バケットポリシーで aws:SecureTransport が false の場合は Deny
RDS SSL/TLS 接続を必須化(PostgreSQL の rds.force_ssl、MySQL の require_secure_transport など)。クライアントに RDS の CA 証明書バンドル を設定
EFS マウント時に TLS を有効化(amazon-efs-utils の tls オプション)
VPN / Direct Connect VPN は IPsec で暗号化。Direct Connect は 単体では暗号化されない → VPN や MACsec と組み合わせ

(4) トラブルシュート

症状 原因と対処
証明書が ALB / CloudFront の選択肢に出ない リージョン違い(CloudFront は us-east-1)
証明書が 「検証保留中」のまま DNS 検証の CNAME が未追加 / 誤り
証明書が 期限切れ 自動更新に失敗(CNAME の削除)/ インポート証明書の期限管理漏れ → EventBridge の「ACM 証明書の有効期限接近」イベントでアラート
ブラウザの証明書エラー ドメイン名が不一致(SAN に含まれない)、中間証明書の不足、期限切れ
古いクライアントが接続できない ALB / CloudFront の セキュリティポリシーが新しすぎる(TLS 1.0 / 1.1 を無効化しているなど)
HTTP → HTTPS で無限リダイレクト CloudFront とオリジンの両方でリダイレクトしている

(5) ベストプラクティス

インターネットへのデータ転送(アウト) インターネットへ出る通信 は課金(インバウンドは無料) CloudFront 経由 にする(オリジン → CloudFront の転送は無料、配信単価も下がる)
パブリック IPv4 アドレス 使用中・未使用を問わず時間課金 不要な Elastic IP / パブリック IP を解放、IPv6 や ALB の共有、プライベート通信への切替
VPC エンドポイント(インターフェイス) 時間 + データ量 AZ 数・本数を必要最小限 に。共有エンドポイントを検討
Transit Gateway アタッチメント時間 + データ量 少数の VPC なら VPC ピアリング(同一 AZ 内なら転送無料)が安い場合も
リージョン間転送 リージョンをまたぐ通信は課金 不要なクロスリージョン通信を避け、データを 利用する場所の近く に置く
VPC フローログ ログ取り込み・保管料金 対象と詳細度を絞る(必要な範囲のみ、S3 保管・ライフサイクル)
VPN / Direct Connect 接続時間 + データ転送 大量転送は Direct Connect のほうが転送単価が安い

(2) ベストプラクティス

  • まず可視化:Cost Explorer や CUR(Cost and Usage Report)で 使用タイプ別 に把握する
  • S3 / DynamoDB は必ずゲートウェイエンドポイント

  • パブリック IPv4 を最小化 し、未使用の Elastic IP を解放する

  • タグで コスト配分 を明確にする

ツール 内容

Skill 5.3.2 🔴 ネットワークログの収集と解釈(VPC フローログ / ELB / WAF / CloudFront / コンテナ)

公式スキル文: ネットワークログを収集・解釈してトラブルシュートする(例: VPC フローログ、ELB アクセスログ、AWS WAF Web ACL ログ、CloudFront ログ、コンテナログ)。

(1) ログの種類早見表

ログ 何が分かるか 出力先
VPC フローログ ENI / サブネット / VPC を通る IP 通信のメタデータ(誰から誰へ、ポート、許可 / 拒否) CloudWatch Logs / S3 / Firehose
ELB アクセスログ ロードバランサーが処理した各リクエスト(クライアント IP、ステータス、処理時間など) S3
WAF Web ACL ログ WAF が検査したリクエスト(どのルールで許可 / ブロックされたか) CloudWatch Logs / S3 / Firehose
CloudFront ログ エッジが処理したリクエスト(キャッシュ結果、ステータス、オリジン遅延) 標準ログ(S3 など) / リアルタイムログ(Kinesis Data Streams)

(2) VPC フローログの読み方

既定のフォーマットのフィールド

フィールド 意味
version / account-id / interface-id バージョン / アカウント / ENI
srcaddr / dstaddr 送信元 / 宛先 IP
srcport / dstport 送信元 / 宛先ポート
protocol プロトコル番号(6 = TCP、17 = UDP、1 = ICMP)
packets / bytes パケット数 / バイト数
start / end 集計の開始 / 終了時刻
action ACCEPT(許可)/ REJECT(拒否)
log-status OK / NODATA / SKIPDATA

サンプルと読み方

plaintext
2 123456789010 eni-0abc 203.0.113.12 10.0.1.5 49152 22 6 10 840 1700000000 1700000060 ACCEPT OK
2 123456789010 eni-0abc 203.0.113.99 10.0.1.5 49153 22 6 4 240 1700000000 1700000060 REJECT OK
行 解釈
1 行目 203.0.113.12 から 10.0.1.5 の TCP 22(SSH) への通信が 許可された
2 行目 203.0.113.99 からの SSH が 拒否された(SG / NACL でブロック)

判断のコツ

パターン 示唆すること
インバウンドが ACCEPT なのに、戻りが REJECT NACL(ステートレス)の復路の許可漏れ の可能性が高い(SG はステートフルなので戻りは自動許可)
宛先ポートが想定外で REJECT が大量 ポートスキャン / 不正アクセス の可能性
REJECT が出るのに SG は許可している NACL の拒否 を疑う
フローログに 出てこない 経路・ルートの問題(そもそも届いていない)、またはフローログの対象外
注意点 内容
フローログは「ペイロード」を記録しない メタデータのみ
記録されない通信 Amazon DNS サーバー宛の DNS 通信、DHCP、インスタンスメタデータ(169.254.169.254)、Amazon Time Sync Service、Windows ライセンス認証 など
集計間隔 1 分または 10 分
作成後の変更 フローログの設定は 作成後に変更不可(再作成が必要)
取り付け先 VPC / サブネット / ENI

CloudWatch Logs Insights で拒否が多い送信元を集計する例

plaintext
filter action = "REJECT"
| stats count(*) as rejectCount by srcAddr, dstPort
| sort rejectCount desc
| limit 20

(S3 に保存したフローログは Amazon Athena で SQL 分析できます。)

(3) ELB アクセスログ

主なフィールド 意味
elb_status_code ロードバランサーがクライアントに返したステータス
target_status_code ターゲットが返したステータス(ターゲットに届かなければ -)
request_processing_time / target_processing_time / response_processing_time LB の受付時間 / ターゲットの処理時間 / 応答送信時間
client:port / target:port クライアント / ターゲットのアドレス
読み方 示唆すること
elb_status_code = 502/503/504 + target_status_code が - ターゲットへ到達できていない、またはターゲットが応答していない(ヘルスチェック・SG・ターゲット停止)
target_processing_time が大きい アプリ(ターゲット)の遅さ が原因
elb_status_code = 5xx かつ target_status_code = 5xx アプリケーション自身のエラー

重要: アクセスログは既定で無効。有効化して S3 バケットに保存(バケットポリシーで ELB のログ配信を許可する必要がある)。

(4) WAF ログ

主なフィールド 意味
action ALLOW / BLOCK / COUNT
terminatingRuleId 最終的に判断したルール
ruleGroupList / nonTerminatingMatchingRules マッチしたルールグループ / 終端しないルール(Count)
httpRequest クライアント IP、URI、ヘッダー など

→ 「正当なユーザーがブロックされる(誤検知)」の調査 に使う。まず該当ルールを Count にして影響を確認する。

(5) CloudFront ログ

主なフィールド 意味
x-edge-result-type Hit / RefreshHit / Miss / Error など(キャッシュの結果)

Skill 5.3.3 🔴 CloudFront のキャッシュ問題の特定と修復

公式スキル文: CloudFront のキャッシュに関する問題を特定し修復する。

(1) まず確認:キャッシュは効いているか

レスポンスヘッダー X-Cache で確認できます。

X-Cache の値 意味
Hit from cloudfront エッジのキャッシュから返した
Miss from cloudfront キャッシュがなく オリジンから取得 した
RefreshHit from cloudfront 期限切れのキャッシュを オリジンで再検証 し、更新不要と判断して返した
Error from cloudfront エラー

Age ヘッダーは キャッシュされてからの経過秒数 を示します。

(2) よくある問題と対処

問題 原因 対処
ヒット率が低い キャッシュキーに 不要な値(全クエリ文字列・全ヘッダー・全 Cookie) を含めている キャッシュポリシーで必要な値だけ に絞る(不要なものは オリジンリクエストポリシー で転送)
ヒット率が低い オリジンが Cache-Control: no-cache / no-store / private を返している オリジンのヘッダーを見直す / CloudFront の 最小 TTL で上書き
更新したのに古い内容 TTL 内はキャッシュが返る 無効化(/* やパス指定)。ただし バージョン付きのファイル名 が確実・低コスト
他人の内容が見える 認証・個人用のコンテンツを共有キャッシュ に載せた キャッシュしない(Cache-Control: private)、キャッシュキーに識別子(Cookie / Authorization) を含める
オリジンへの負荷が高い ミスが多い、同時に同じオブジェクトを要求 Origin Shield の有効化、TTL を長く
S3 オリジンで 403 OAC の設定とバケットポリシーの不一致、オブジェクトが存在しない(権限がない場合 S3 は 403 を返すことがある) OAC とバケットポリシー(cloudfront.amazonaws.com + AWS:SourceArn)を確認
ALB オリジンで異常 Host ヘッダーを転送していない などで、ALB 側のルーティング / 証明書と不一致 オリジンリクエストポリシーで 必要なヘッダー(Host) を転送。オリジンの SG が CloudFront からのアクセスを許可しているか
エラー応答がキャッシュされて復旧しない エラーレスポンスも既定でキャッシュ(Error Caching Minimum TTL が既定 10 秒) エラーキャッシュの TTL を調整、オリジンを修復
圧縮されない 圧縮の有効化漏れ、オリジンの Content-Length / 対応形式 自動圧縮を有効化

(3) TTL の決まり方

設定 内容
最小 TTL / 既定 TTL / 最大 TTL ビヘイビアのキャッシュポリシーで設定
オリジンの Cache-Control: max-age / s-maxage / Expires あれば 最小 TTL と最大 TTL の範囲内で 採用。ない場合は 既定 TTL
注意 最小 TTL を 0 より大きくすると、オリジンの no-cache 等を上書きしてキャッシュする

(4) 無効化(Invalidation)のポイント

  • パスを指定(/images/*、/index.html など)して実行
  • 月あたり最初の 1,000 パスまで無料(以降は課金)。ワイルドカードは 1 パスとして数える
  • 完了まで 数分 かかる
  • 頻繁に無効化が必要なら、ファイル名にバージョン(ハッシュ)を付ける設計に変更 する

(5) 監視メトリクス

メトリクス 意味
Requests リクエスト数
4xxErrorRate / 5xxErrorRate エラー率
OriginLatency(追加メトリクス) オリジンの応答時間
CacheHitRate(追加メトリクス) キャッシュヒット率

(6) ベストプラクティス

  • キャッシュキーを最小限 にし、ヒット率を継続的に監視
  • 静的コンテンツは長い TTL + ファイル名のバージョニング、動的なパーソナライズ内容は慎重に
  • Origin Shield でオリジンの負荷を軽減
  • 標準ログ / リアルタイムログ と CloudWatch メトリクスで挙動を把握
  • オリジンのセキュリティ(OAC、SG)を CloudFront 経由のみに絞る

Skill 5.3.4 🔴 ハイブリッド接続・プライベート接続のトラブルシュート

公式スキル文: ハイブリッド接続とプライベート接続の問題を特定・トラブルシュートする。(VPN は SOA-C02 の Task 4.2 から SOA-C03 では Task 5.1 側に移動)

(1) ハイブリッド接続の選択肢

方式 特徴
Site-to-Site VPN インターネット経由の IPsec で暗号化。1 つの接続に 2 本のトンネル(冗長化)。終端は 仮想プライベートゲートウェイ(VGW)または Transit Gateway。ルーティングは BGP(動的)/ 静的。トンネルあたり最大 1.25 Gbps
Direct Connect 専用線 による接続。安定した帯域・低レイテンシ。単体では暗号化されない(VPN / MACsec と併用)。仮想インターフェイス(VIF): プライベート / パブリック / トランジット
Client VPN ユーザー(クライアント) が VPC / オンプレに接続する マネージドな OpenVPN ベース のサービス

(2) VPN のトラブルシュート

症状 主な原因
トンネルが DOWN 事前共有キー・IKE / IPsec パラメーター不一致、カスタマーゲートウェイの設定誤り、UDP 500 / 4500 のブロック、NAT-T の設定
トンネルは UP だが通信できない ルーティング(BGP の広告漏れ・ルート伝播が無効)、SG / NACL、CIDR の重複
通信が不安定・遅い 帯域上限(トンネルあたり)、MTU / 断片化、非対称ルーティング、ECMP の利用(Transit Gateway)

VPN の監視: CloudWatch メトリクス TunnelState(0 = DOWN / 1 = UP)、TunnelDataIn / TunnelDataOut、VPN ログ(CloudWatch Logs に出力可能)

(3) Direct Connect のトラブルシュート

症状 確認すること
接続(物理)が DOWN ConnectionState メトリクス、ケーブル・パートナー側の状態、ライト(光レベル)
VIF が down VLAN ID・BGP の ASN・認証キー・IP アドレス の設定、ルーター側の設定
BGP セッションが確立しない ピア IP / ASN / MD5 キーの不一致、ファイアウォールで TCP 179 をブロック
通信できない 仮想プライベートゲートウェイ / Direct Connect Gateway / Transit Gateway の関連付け、ルート広告・ルートテーブル、SG / NACL
冗長性 複数接続 / 複数ロケーション、バックアップとして VPN。BFD で障害検知を高速化

(4) プライベート接続(PrivateLink / VPC エンドポイント)のトラブルシュート

症状 確認すること
エンドポイントに接続できない エンドポイントの SG が 443(必要なポート)を許可しているか、サブネットの NACL、ルート
名前解決が パブリック IP のまま プライベート DNS が有効か、VPC の enableDnsSupport / enableDnsHostnames、クライアントの DNS 設定
ゲートウェイエンドポイント(S3) で通らない ルートテーブルにエンドポイントのルートがあるか、エンドポイントポリシー、S3 バケットポリシーの aws:SourceVpce
権限エラー エンドポイントポリシー が必要な操作を許可しているか
エンドポイントサービス(自社公開) 接続リクエストの承認、NLB のヘルスチェックと正常ターゲット、AZ の一致(利用者とサービスで共通の AZ が必要)
オンプレからエンドポイントを使えない DNS(Resolver インバウンド)、VPN / Direct Connect のルーティング

(5) ベストプラクティス

  • VPN は 2 本のトンネルをどちらも使えるように構成(カスタマー側も冗長化)。BGP で動的ルーティング
  • 重要な接続は Direct Connect + VPN バックアップ、複数ロケーション
  • TunnelState / ConnectionState にアラーム を設定
  • CIDR の重複を避ける ネットワーク設計
  • ハイブリッド DNS(Resolver エンドポイント) を忘れずに構成

問題 1(Domain 1)

EC2 インスタンス上のアプリケーションが、メモリ使用率が 90% を超えたときに運用チームへメール通知したい。最も運用負荷が低い 方法はどれか。

解答と解説

B. 複合アラームで AND 条件を設定する
C. SNS のフィルターポリシーを設定する
D. 各アラームを無効にする

解答と解説

正解: B。複合アラームは複数のアラームを AND / OR / NOT で組み合わせてノイズを減らす機能です。(Skill 1.1.3)

B. Lambda 関数のリソースベースポリシーで EventBridge からの呼び出しが許可されているか
C. Lambda 関数のメモリ設定が 128 MB か

B. gp3 に変更して必要な IOPS を設定する
C. sc1 に変更する
D. インスタンスストアに移行する(永続データも保存する)

解答と解説

正解: B。gp3 は基準の IOPS / スループットが容量と独立しており、gp2 のバーストクレジットに依存せず、一般に安価です。Elastic Volumes で稼働中に変更できます。(Skill 1.3.2)

問題 5(Domain 1)

Lambda 関数から RDS for MySQL に接続しているが、同時実行が増えると「Too many connections」エラーが発生する。最も適切な対策 は。

A. RDS のインスタンスクラスを必ず下げる
B. RDS Proxy を導入して接続をプールする
C. リードレプリカを追加する
D. Lambda のタイムアウトを延ばす

解答と解説

正解: B。短命な接続が多数発生する場合は RDS Proxy で接続を集約します。(Skill 1.3.5)

問題 6(Domain 2)

Web アプリの負荷が毎日ほぼ同じ時間帯(平日 9 時)に急増する。ユーザーが待たされないように 事前に台数を増やしたい。

A. ステップスケーリング
B. スケジュールスケーリング(または予測スケーリング)
C. シンプルスケーリング
D. 手動で台数を変更

解答と解説

正解: B。予測可能な負荷には、事前に増やすスケジュール / 予測スケーリングが適切です。(Skill 2.1.1)

問題 7(Domain 2)

ALB の背後のインスタンスで、アクセスログの elb_status_code が 504 を返している。最初に確認すべき のは。

A. ターゲットの応答時間とアイドルタイムアウト(既定 60 秒)の関係、およびターゲットの負荷
B. S3 バケットのバージョニング
C. Route 53 のレイテンシーポリシー
D. KMS キーのローテーション

解答と解説

正解: A。504 はターゲットの応答がタイムアウトしたことを示します。処理時間とアイドルタイムアウト、ターゲットの負荷や疎通(SG / NACL)を確認します。(Skill 2.2.1)

問題 8(Domain 2)

RDS で誤って重要なテーブルを削除してしまった。削除の 数分前の状態 に戻したい。Multi-AZ 構成である。

A. スタンバイにフェイルオーバーする
B. ポイントインタイムリストアで削除直前の時点に新しいインスタンスとして復元する
C. リードレプリカを昇格する(レプリカは削除済みのデータを持っている)
D. 何もしなくても自動で戻る

解答と解説

正解: B。Multi-AZ は同期レプリケーションのため削除もスタンバイに反映されます。PITR で新しいインスタンスとして復元し、必要なデータを戻します。(Skill 2.3.2)

問題 9(Domain 2)

RTO が数分、RPO がほぼゼロで、コストは許容される。最も適した DR 戦略は。

A. バックアップとリストア
B. パイロットライト
C. ウォームスタンバイ
D. マルチサイト(アクティブ / アクティブ)

解答と解説

正解: D(要件がほぼ無停止・ほぼデータ損失なしの場合)。数分の RTO を許容できて、コストを抑えたい場合はウォームスタンバイも候補ですが、「RPO がほぼゼロ、コストは許容」の条件ではアクティブ / アクティブが最も近いです。(Skill 2.3.4)

問題 10(Domain 3)

全アカウント(新規作成分を含む)に同じ IAM ロールと Config ルールを自動的に展開したい。

A. 各アカウントでスタックを手動作成
B. サービスマネージド型アクセス許可の CloudFormation StackSets(自動デプロイ有効)
C. AWS RAM でロールを共有
D. Lambda で毎日全アカウントにログイン

解答と解説

正解: B。StackSets のサービスマネージド型は Organizations と統合され、新規アカウントへ自動デプロイできます。RAM は IAM ロールの共有には使えません。(Skill 3.1.4)

問題 11(Domain 3)

CloudFormation スタックの作成が CREATE_FAILED で失敗した。トラブルシュートで 最初に すべきことは。

A. スタックを削除して、再試行する
B. スタックイベントを確認し、最初に失敗したリソースとその理由を特定する
C. リージョンを変更する
D. 管理者ユーザーに切り替える

解答と解説

正解: B。後続の失敗は連鎖の結果であることが多く、最初の失敗の理由を確認するのが基本です。(Skill 3.1.3)

問題 12(Domain 3)

プライベートサブネットの EC2 を、SSH ポートを開けずに管理し、操作ログも残したい。

A. 踏み台サーバーを置く
B. Systems Manager Session Manager を使う
C. SG で 22 番を 0.0.0.0/0 に開放する
D. EC2 Instance Connect Endpoint のみを使う(ログ要件は無視)

解答と解説

正解: B。Session Manager は SSH ポート不要で、操作ログを S3 / CloudWatch Logs に記録できます。管理対象になるには、エージェント、IAM ロール、ネットワーク経路(NAT または VPC エンドポイント)が必要です。(Skill 3.2.1)

問題 13(Domain 4)

S3 バケットのオブジェクトを読み取れない。ユーザーの IAM ポリシーには s3:GetObject が許可されている。オブジェクトは SSE-KMS(カスタマー管理キー)で暗号化されている。考えられる原因は。

A. KMS キーポリシー / 権限に kms:Decrypt の許可がない
B. S3 のバージョニングが有効
C. バケットが複数 AZ に保存されている
D. Route 53 のヘルスチェックの失敗

解答と解説

正解: A。SSE-KMS のオブジェクトを読むには KMS の復号権限も必要です。(Skill 4.2.2、4.1.2)

問題 14(Domain 4)

Organizations の SCP について 正しいもの はどれか。

A. SCP でサービスを許可すれば、IAM ポリシーがなくてもアクセスできる
B. SCP は管理アカウントにも適用される
C. SCP は権限の上限を定めるものであり、権限を付与するものではない
D. SCP はサービスリンクロールにも適用される

解答と解説

正解: C。SCP はガードレールで、付与は IAM で行います。管理アカウントとサービスリンクロールには影響しません。(Skill 4.1.3)

問題 15(Domain 4)

データベースの認証情報を 自動でローテーション し、アプリが常に最新の認証情報を取得できるようにしたい。

A. Parameter Store の標準パラメータ
B. AWS Secrets Manager
C. EC2 の環境変数
D. S3 バケットのテキストファイル

解答と解説

正解: B。ネイティブのローテーション機能を持つのは Secrets Manager です。(Skill 4.2.4)

問題 16(Domain 5)

プライベートサブネットの EC2 が S3 から大量にデータを取得しており、NAT ゲートウェイのデータ処理料金が高い。最も費用対効果の高い対策 は。

A. NAT ゲートウェイを大きなタイプにする
B. S3 用のゲートウェイ VPC エンドポイントを作成する
C. NAT ゲートウェイを増やす
D. インターフェイスエンドポイントのみを作成する

解答と解説

正解: B。S3 のゲートウェイエンドポイントは無料で、NAT を経由しないためデータ処理料金を削減できます。(Skill 5.1.2、5.1.4)

問題 17(Domain 5)

VPC フローログで、あるサーバー宛ての TCP 443 が ACCEPT されているのに、そのサーバーからの戻りのパケット(エフェメラルポート宛て)が REJECT されている。原因として最も可能性が高い のは。

A. セキュリティグループのインバウンドルール不足
B. ネットワーク ACL のアウトバウンド(復路)ルール不足
C. Route 53 のヘルスチェック
D. IGW の障害

解答と解説

正解: B。SG はステートフルなので戻りは自動許可されます。復路が REJECT なら、ステートレスな NACL の許可漏れが疑われます。(Skill 5.1.1、5.3.2)

問題 18(Domain 5)

CloudFront で配信するサイトに HTTPS を適用するため、ACM で証明書を発行したい。どのリージョン で発行すべきか。

B. 米国東部(バージニア北部)us-east-1
C. オリジン(ALB)と同じリージョン
D. どのリージョンでもよい

解答と解説

正解: B。CloudFront で使う ACM 証明書は us-east-1 で作成する必要があります。(Skill 4.2.3)

問題 19(Domain 5)

Site-to-Site VPN の両方のトンネルが UP だが、オンプレミスから VPC 内のインスタンスにアクセスできない。確認すべきこととして 適切なものを 2 つ 選べ。

A. VPC のルートテーブルにオンプレミス CIDR 向けのルート(またはルート伝播)があるか

正解: A、B。トンネルが UP ならネゴシエーションは成功しています。次にルーティングと SG / NACL を確認します。(Skill 5.3.4)

Direct Connect と Site-to-Site VPN を使うハイブリッド環境で、回線のパケットロスとレイテンシの劣化を継続的に監視 したい。エージェントのインストールは避けたい。
