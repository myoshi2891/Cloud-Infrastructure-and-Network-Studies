          Google Cloud チャレンジラボ

          GKE チャレンジラボ完全ガイド：echo-web を v1 から v2 へ更新してスケールアウトする

          対象読者
          Google Cloud・Docker・Kubernetes を触り始めた初学者
          関連資格
          Google Cloud Certified Professional Cloud Architect（PCA）
          所要時間の目安
          ラボ本体 約20〜30分（ビルド・LB の IP 発行待ちを含む）
          1. Task 1ビルド
          2. Task 2push
          3. Task 3v2 へ更新
          4. Task 4スケール
          5. Task 5動作確認

          0. このガイドの読み方

          チャレンジラボは「手順書が無いテスト形式」です。そのため、コマンドを暗記するよりも「なぜその操作が必要か」を理解することが合格への近道です。本ガイドでは各タスクを次の順で解説します。

          順番 内容
          1 そのタスクのゴール（何ができれば合格か）
          2 登場する概念の解説
          3 実行コマンドと一行ずつの意味
          4 確認方法・つまずきポイント
          5 ベストプラクティス（実務ではどうするか）

          1. シナリオの全体像

          1.1 何をするラボか

          あなたはテスト環境を引き継いだ担当者です。すでに GKE クラスタ echo-cluster が用意されており、アプリ echo-app の v1 が動いています。これを v2 に更新し、2 台構成（レプリカ 2） に増やし、外部から応答を確認します。

          1.2 登場人物（用語表）

          用語 意味 このラボでの名前
          コンテナイメージ アプリと実行環境を一つにまとめた「配布物」 echo-app
          タグ イメージのバージョン名札 v1、v2
          レジストリ イメージの保管庫 gcr.io（Container Registry のホスト名）
          GKE クラスタ Kubernetes を Google が管理してくれる環境 echo-cluster
          Deployment 「Pod を何個、どのイメージで動かすか」を宣言するリソース echo-web
          Pod コンテナを動かす最小単位 echo-web-xxxx
          Service Pod 群への固定の入口（ロードバランサ） echo-web（LoadBalancer）
          レプリカ 同じ Pod の複製数 2

          1.3 全体の流れ（フローチャート）

          1.4 システム構成図

          ポイント：ユーザーは Pod に直接アクセスしません。常に Service（固定の入口）を経由します。だから Pod が入れ替わっても、外部 IP は変わりません。

          2. 事前準備

          2.1 変数を設定する（最重要の時短テクニック）

          ラボ画面に表示される ZONE と バケット名 は、受講ごとに異なります。コマンドに毎回手打ちすると打ち間違いの原因になるため、シェル変数に入れておきます。

          bash 
          export ZONE="REPLACE_WITH_LAB_ZONE"      # ラボ画面に表示されたゾーンに置き換える
export BUCKET="REPLACE_WITH_LAB_BUCKET"  # ラボ画面に表示されたバケット名に置き換える
export PROJECT_ID=$(gcloud config get-value project)
          変数 役割
          ZONE クラスタのあるゾーン
          BUCKET echo-web-v2.tar.gz が置いてあるバケット名
          PROJECT_ID gcr.io 上のイメージ保存先パスに使うプロジェクト ID

          注意：< > は入力しません。値だけを書きます。Cloud Shell が切断されると変数は消えるため、再接続したら再設定してください。

          2.2 バケットにファイルがあるか確認する

          コンソールで Cloud Storage > バケット を開いて確認するか、コマンドで確認します。

          bash 
          gcloud storage ls gs://$BUCKET/

          echo-web-v2.tar.gz が表示されれば OK です。

          2.3 クラスタが作成済みか確認する

          コンソールの Kubernetes Engine > クラスタ で echo-cluster に 緑のチェックマークが付くまで待ちます。コマンドでも確認できます。

          bash 
          gcloud container clusters list

          STATUS 列が RUNNING になっていれば準備完了です。

          2.4 v1 をデプロイする（ラボ指定の手順）

          bash 
          # 既存の v1 Deployment / Service があれば作り直さず、無い場合だけ作成する
# 接続や確認のコマンドが失敗した場合は「未作成」と誤認せず、リソースを作成せずに止める
# ( ) のサブシェル内で exit 1 するため、Cloud Shell は閉じずに終了ステータスだけが 0 以外になる
(
if ! gcloud container clusters get-credentials echo-cluster --zone=$ZONE; then
  echo "クラスタの接続情報を取得できません。ZONE とクラスタ名を確認してください。" >&2
  exit 1
elif ! DEPLOYMENT=$(kubectl get deployment echo-web --ignore-not-found -o name); then
  echo "Deployment の確認に失敗しました。リソースは作成しません。" >&2
  exit 1
elif ! SERVICE=$(kubectl get service echo-web --ignore-not-found -o name); then
  echo "Service の確認に失敗しました。リソースは作成しません。" >&2
  exit 1
else
  if [ -z "$DEPLOYMENT" ]; then
    kubectl create deployment echo-web --image=gcr.io/qwiklabs-resources/echo-app:v1
  fi &&
  if [ -z "$SERVICE" ]; then
    kubectl expose deployment echo-web --type=LoadBalancer --port 80 --target-port 8000
  fi &&
  kubectl get deployment,service echo-web
fi
) || { echo "v1 の準備に失敗しました。上のエラーを解消するまで Task 1 以降へ進まないでください。" >&2; false; }
          コマンド 何をしているか
          get-credentials kubectl がどのクラスタを操作するかの接続情報を取得して設定する
          create deployment echo-web という Deployment を作り、v1 イメージで Pod を 1 つ起動する
          expose deployment Deployment に対する Service を作る
          get ... --ignore-not-found -o name 既存リソースの有無を確認する。ラボ環境で v1 が作成済みの場合は create / expose を実行せず、既存の Deployment と Service をそのまま使う（再実行すると AlreadyExists エラーになるため）。get-credentials や get 自体が失敗した場合（認証切れ・ゾーン違いなど）は空の結果と区別できないため、終了ステータスを確認し、失敗時はリソースを作成せずに止める

          expose の 3 つのオプションを理解する

          オプション 意味 値
          --type=LoadBalancer クラスタ外から届く Google Cloud のロードバランサを自動作成する LoadBalancer
          --port Service が外部に公開するポート 80
          --target-port Pod（コンテナ）が実際に待ち受けるポート 8000

          これが 504 エラーの最大原因です。 --target-port はアプリが実際に待ち受けているポート（今回は 8000）と一致させる必要があり、食い違うとロードバランサは Pod に到達できません。Dockerfile の EXPOSE 8000 は待ち受けポートを示す説明用のメタデータにすぎず、ポートを開いたり変更したりはしないため、確認の手掛かりとして使います。

          3. Task 1：アプリをビルドして v2 タグを付ける

          3.1 ゴール

          echo-web-v2.tar.gz をダウンロード → 展開 → Docker イメージをビルド → v2 タグを付ける。

          3.2 概念：イメージ名の構造

          イメージ名は次の 4 つの部品でできています。

          部品 例 説明
          レジストリのホスト名 gcr.io 保管庫の住所
          プロジェクト ID qwiklabs-gcp-xx-xxxx あなたのプロジェクト
          イメージ名 echo-app アプリの名前
          タグ v2 バージョンの名札

          完成形は次のとおりです。

          text 
          gcr.io/<プロジェクトID>/echo-app:v2

          push 先のレジストリを決めるのは、イメージ名の先頭部分（ホスト名とプロジェクト ID）です。 先頭を正しく付けないと、push は Docker Hub 側に向かって失敗します。

          3.3 手順

          手順 1：ダウンロード

          bash 
          gcloud storage cp gs://$BUCKET/echo-web-v2.tar.gz .
          部分 意味
          gcloud storage cp Cloud Storage との間でファイルをコピーする
          gs://$BUCKET/... バケット内のファイルの場所
          . 保存先はカレントディレクトリ

          旧来の gsutil cp でも同じ結果になります。現在は gcloud storage の利用が推奨されています。

          手順 2：専用ディレクトリへ展開し、Dockerfile の場所を確認

          bash 
          mkdir -p echo-web-v2
tar -xzf echo-web-v2.tar.gz -C echo-web-v2
# Dockerfile が見つからないまま dirname を呼ぶと "." になり、意図しないディレクトリでビルドしてしまうため先に確認する
DOCKERFILE_PATH=$(find echo-web-v2 -name Dockerfile -print -quit)
if [ -z "$DOCKERFILE_PATH" ]; then
  echo "展開結果に Dockerfile が見つかりません。echo-web-v2.tar.gz の中身を確認してください。" >&2
else
  BUILD_DIR=$(dirname "$DOCKERFILE_PATH")
  echo "BUILD_DIR=${BUILD_DIR}"
fi

          展開先を専用ディレクトリ echo-web-v2 に分けることで、カレントディレクトリにある他のファイル（ダウンロードした tar.gz など）がビルドコンテキストに混ざりません。BUILD_DIR= が表示されない場合は、手順 3 に進まず展開結果を確認してください。

          部分 意味
          mkdir -p echo-web-v2 展開専用のディレクトリを作る（既にあってもエラーにしない）
          tar -xzf ... -C echo-web-v2 x 展開・z gzip 解凍・f ファイル指定。-C で展開先を専用ディレクトリにする
          find ... -name Dockerfile -print -quit 展開結果から最初に見つかった Dockerfile のパスを取得する
          dirname Dockerfile のあるディレクトリ（ビルドコンテキスト）を取り出す

          手順 3：ビルド（ホスト名つきのタグで）

          bash 
          docker build -t gcr.io/$PROJECT_ID/echo-app:v2 "$BUILD_DIR"
          部分 意味
          docker build Dockerfile からイメージを作る
          -t イメージに名前とタグを付ける（tag）
          "$BUILD_DIR" ビルドコンテキスト。手順 2 で特定した、Dockerfile とアプリ一式があるディレクトリだけを渡す

          よくある失敗：ビルドコンテキストの引数を忘れると「引数が足りません」というエラーになります。BUILD_DIR が空のまま実行すると同じエラーになるため、手順 2 で BUILD_DIR= の表示を確認してから実行してください。

          3.4 確認

          bash 
          docker images

          gcr.io/<プロジェクトID>/echo-app の TAG 列に v2 があれば成功です。

          4. Task 2：イメージを Container Registry に push する

          4.1 ゴール

          gcr.io/<プロジェクトID>/echo-app:v2 をレジストリに保存する。

          4.2 概念：なぜ push が必要か

          GKE の Pod は、あなたの Cloud Shell 内のイメージを見られません。クラスタがダウンロードできる共有の保管庫（レジストリ）にアップロードする必要があります。

          4.3 手順

          手順 1：Docker に Google Cloud の認証を設定（初回のみ）

          bash 
          gcloud auth configure-docker

          Docker が gcr.io に push するときに、ログイン中の Google アカウントの資格情報を使えるようにする設定です。確認メッセージが出たら Y を入力します。

          手順 2：push

          bash 
          docker push gcr.io/$PROJECT_ID/echo-app:v2

          手順 3：確認

          bash 
          gcloud artifacts docker tags list us-docker.pkg.dev/$PROJECT_ID/gcr.io/echo-app

          TAG 列に v2 が表示されれば成功です。ここで Check my progress を押します。

          4.4 つまずきポイント

          症状 原因 対処
          denied: Token exchange failed Docker の認証設定がない gcloud auth configure-docker を実行
          repository does not exist プロジェクト ID の打ち間違い echo $PROJECT_ID で値を確認
          tag does not exist build 時のタグと push 時のタグが違う docker images で名前を確認

          4.5 ベストプラクティス：Container Registry から Artifact Registry へ

          Google Cloud では Container Registry は非推奨で、後継の Artifact Registry への移行が案内されています。本ラボは試験・学習用に gcr.io を使いますが、実務では次を意識してください。

          観点 Container Registry（旧） Artifact Registry（推奨）
          リポジトリ単位の IAM 不可（バケット単位） 可能
          リージョン指定 限定的 自由に選択可能
          脆弱性スキャン 限定的 統合されている
          対応形式 コンテナのみ コンテナ・各種パッケージ

          5. Task 3：更新したアプリを GKE にデプロイする

          5.1 ゴール

          • Deployment 名は echo-web のまま
          • イメージを v2 に変更
          • 外部からポート 80 でアクセスできる

          5.2 概念：ローリングアップデート

          Deployment のイメージを書き換えると、Kubernetes は古い Pod を一度に止めず、新しい Pod を起動してから順に入れ替えます。これを ローリングアップデートと呼び、サービスを止めずに更新できます。

          5.3 手順

          手順 1：コンテナ名を確認する

          kubectl set image では「Deployment 内のどのコンテナを更新するか」をコンテナ名で指定します。kubectl create deployment --image=.../echo-app:v1 で作った場合、コンテナ名はイメージ名から自動で echo-app になりますが、既存の Deployment が別の名前で作られている場合もあるため、実際の名前を取得して変数に保存します。

          bash 
          CONTAINER_NAME=$(kubectl get deployment echo-web -o jsonpath='{.spec.template.spec.containers[0].name}')
echo "CONTAINER_NAME=${CONTAINER_NAME}"

          手順 2：イメージを更新

          bash 
          kubectl set image deployment/echo-web "${CONTAINER_NAME}=gcr.io/$PROJECT_ID/echo-app:v2"
          部分 意味
          deployment/echo-web 更新対象の Deployment
          ${CONTAINER_NAME}= 更新するコンテナ名（等号の左）。手順 1 で既存の Deployment から取得した名前
          gcr.io/.../echo-app:v2 新しいイメージ（等号の右）

          手順 3：更新の完了を待つ

          bash 
          kubectl rollout status deployment/echo-web --timeout=5m

          successfully rolled out と出れば完了です。5 分以内に終わらない場合はタイムアウトして制御が戻るので、kubectl describe deployment echo-web と kubectl get events で原因を確認してください。

          手順 4：イメージが v2 になったか確認

          bash 
          kubectl get deployment echo-web -o jsonpath='{.spec.template.spec.containers[0].image}'

          5.4 外部公開（Service）について

          v1 のデプロイ時に作成した echo-web Service（LoadBalancer、80 → 8000）がそのまま v2 の Pod にも通信を届けます。Service は Pod の「ラベル」で対象を選ぶため、イメージを更新しても作り直す必要はありません。

          もし Service を誤って削除していた場合は、次で再作成します。

          bash 
          kubectl expose deployment echo-web --type=LoadBalancer --port 80 --target-port 8000

          5.5 ベストプラクティス：宣言的に管理する

          kubectl set image は手軽ですが、実務ではマニフェストファイル（YAML）で管理し、Git で変更履歴を残します。

          yaml 
          apiVersion: apps/v1
kind: Deployment
metadata:
  name: echo-web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: echo-web
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: echo-web
    spec:
      containers:
        - name: echo-app
          image: gcr.io/PROJECT_ID/echo-app:v2
          ports:
            - containerPort: 8000
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              memory: 256Mi
          readinessProbe:
            httpGet:
              path: /
              port: 8000
            initialDelaySeconds: 3
            periodSeconds: 5
          設定 狙い
          maxUnavailable: 0 更新中に利用可能な Pod 数を減らさない
          maxSurge: 1 更新中に一時的に 1 つ多く Pod を起動できる
          resources.requests スケジューラが適切なノードに配置できる
          readinessProbe 準備ができた Pod にだけ通信を流す（504 の予防）

          6. Task 4：2 レプリカにスケールアウトする

          6.1 ゴール

          echo-web の Pod を 2 つにして、すべて Running にする。

          6.2 概念：スケールアウトとスケールアップ

          種類 意味 例
          スケールアウト（水平） 台数を増やす Pod を 1 → 2
          スケールアップ（垂直） 1 台の性能を上げる CPU・メモリを増やす

          Kubernetes は水平スケールが基本です。複数 Pod に分散することで、負荷分散と障害時の可用性が得られます。

          6.3 手順

          bash 
          kubectl scale deployment echo-web --replicas=2

          2 つのレプリカがどちらも Ready になるまで待ちます（scale は台数の指定を変えるだけで、Pod の起動完了は待ちません）。

          bash 
          kubectl rollout status deployment/echo-web --timeout=5m
kubectl get deployment echo-web

          rollout status が successfully rolled out で終わり、READY 列が 2/2 になったことを確認してから次へ進みます。タイムアウトした場合は kubectl describe deployment echo-web と kubectl get events で原因を確認してください。

          Ready を確認したうえで、Pod の一覧を見ます。

          bash 
          kubectl get pods -l app=echo-web
          列 期待する値
          READY 1/1
          STATUS Running
          行数 2 行

          ラベルの注意：kubectl create deployment echo-web で作成した場合、Pod には app=echo-web のラベルが自動で付きます。表示されない場合は単に kubectl get pods で確認してください。

          6.4 ベストプラクティス：手動スケールから自動スケールへ

          本番では負荷に応じて自動で増減させる HPA（Horizontal Pod Autoscaler） が一般的です。

          bash 
          kubectl autoscale deployment echo-web --min=2 --max=5 --cpu-percent=70

          ラボでの注意：チェッカーは「レプリカ数が 2」であることを見ます。HPA を設定すると数が変動し、判定に影響する恐れがあるため、本ラボでは実行しないでください。実務向けの知識として押さえておきましょう。

          7. Task 5：アプリの動作を確認する

          7.1 ゴール

          外部 IP にアクセスして、v2 の応答（バージョン番号つき）が返ることを確認する。

          7.2 手順

          手順 1：外部 IP を調べる

          bash 
          kubectl get service echo-web

          EXTERNAL-IP 列に IP アドレスが表示されるまで待ちます。<pending> の間はロードバランサを作成中です。

          自動で待機したい場合は次のコマンドを使います。

          bash 
          kubectl get service echo-web --watch

          IP が出たら Ctrl + C で止めます。

          手順 2：アクセスして確認

          bash 
          export EXTERNAL_IP=$(kubectl get service echo-web -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
curl http://$EXTERNAL_IP

          出力に バージョン番号（v2） が含まれていれば成功です。ブラウザで http://<EXTERNAL-IP> を開いても確認できます。

          8. トラブルシューティング

          8.1 症状別の対処表

          症状 想定原因 確認コマンド 対処
          504 Gateway Timeout ポートの不一致 kubectl describe service echo-web targetPort が 8000 か確認
          504 Gateway Timeout 起動直後で未初期化 kubectl get pods 1〜2 分待って再試行
          ImagePullBackOff イメージ名・タグの誤り、または未 push kubectl describe pod <Pod名> イメージのパスとタグを修正
          ErrImagePull レジストリの権限不足 kubectl describe pod <Pod名> イメージのパスが正しいか確認
          CrashLoopBackOff アプリが起動直後に終了 kubectl logs <Pod名> ログのエラーを確認
          EXTERNAL-IP が <pending> のまま LB 作成中 kubectl describe service echo-web 数分待つ
          kubectl が別クラスタに接続 認証情報が未設定 kubectl config current-context get-credentials を再実行

          8.2 診断の進め方（フローチャート）

          9. 完全版コマンド集（コピーして使う用）

          以下を上から順に実行すれば、全タスクが完了します。ZONE と BUCKET はラボ画面の値に置き換えてください。

          bash 
          # 0. 変数
export ZONE="REPLACE_WITH_LAB_ZONE"      # ラボ指定のゾーンに置き換える
export BUCKET="REPLACE_WITH_LAB_BUCKET"  # ラボ指定のバケット名に置き換える
export PROJECT_ID=$(gcloud config get-value project)

# 0-1 以降は ( ) のサブシェルで実行する。接続や確認に失敗すると exit 1 で
# サブシェルだけが終了し、古い kubectl コンテキストに対して Task 1〜5 を実行しない
# （Cloud Shell 自体は閉じない）。set -e で途中のコマンド失敗時も以降を止める
# （set -e を有効に保つため、サブシェルを || や && の左辺に置かない）
(
set -e

# 0-1. 接続と v1 のデプロイ
# 既存の v1 Deployment / Service があれば作り直さず、無い場合だけ作成する
# 接続や確認のコマンドが失敗した場合は「未作成」と誤認せず、リソースを作成せずに止める
if ! gcloud container clusters get-credentials echo-cluster --zone=$ZONE; then
  echo "クラスタの接続情報を取得できません。ZONE とクラスタ名を確認してください。" >&2
  exit 1
elif ! DEPLOYMENT=$(kubectl get deployment echo-web --ignore-not-found -o name); then
  echo "Deployment の確認に失敗しました。リソースは作成しません。" >&2
  exit 1
elif ! SERVICE=$(kubectl get service echo-web --ignore-not-found -o name); then
  echo "Service の確認に失敗しました。リソースは作成しません。" >&2
  exit 1
else
  # if 文を && でつなぐと set -e が効かず、失敗しても以降の Task に進んでしまう。
  # そのため各コマンドを独立した文にし、create / expose の失敗時は即座に exit 1 で止める
  if [ -z "$DEPLOYMENT" ]; then
    kubectl create deployment echo-web --image=gcr.io/qwiklabs-resources/echo-app:v1 || exit 1
  fi
  if [ -z "$SERVICE" ]; then
    kubectl expose deployment echo-web --type=LoadBalancer --port 80 --target-port 8000 || exit 1
  fi
  kubectl get deployment,service echo-web
fi

# Task 1: ダウンロード・展開・ビルド
gcloud storage cp gs://$BUCKET/echo-web-v2.tar.gz .
mkdir -p echo-web-v2
tar -xzf echo-web-v2.tar.gz -C echo-web-v2
# Dockerfile が見つからないまま dirname を呼ぶと "." になり、意図しないディレクトリでビルドしてしまうため先に確認する
DOCKERFILE_PATH=$(find echo-web-v2 -name Dockerfile -print -quit)
if [ -z "$DOCKERFILE_PATH" ]; then
  echo "展開結果に Dockerfile が見つかりません。echo-web-v2.tar.gz の中身を確認してください。" >&2
  exit 1
fi
BUILD_DIR=$(dirname "$DOCKERFILE_PATH")
echo "BUILD_DIR=${BUILD_DIR}"
docker build -t gcr.io/$PROJECT_ID/echo-app:v2 "$BUILD_DIR"

# Task 2: push
gcloud auth configure-docker
docker push gcr.io/$PROJECT_ID/echo-app:v2

# Task 3: v2 へ更新（コンテナ名は既存の Deployment から取得する）
CONTAINER_NAME=$(kubectl get deployment echo-web -o jsonpath='{.spec.template.spec.containers[0].name}')
kubectl set image deployment/echo-web "${CONTAINER_NAME}=gcr.io/$PROJECT_ID/echo-app:v2"
kubectl rollout status deployment/echo-web --timeout=5m

# Task 4: スケールアウト（2 レプリカが Ready になるまで待つ）
kubectl scale deployment echo-web --replicas=2
kubectl rollout status deployment/echo-web --timeout=5m
kubectl get deployment echo-web
kubectl get pods

# Task 5: 動作確認
kubectl get service echo-web
# LoadBalancer に外部 IP が割り当てられるまで最大 10 分（10 秒 × 60 回）待つ（空のまま curl しない）
EXTERNAL_IP=""
for attempt in $(seq 1 60); do
  EXTERNAL_IP=$(kubectl get service echo-web -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
  [ -n "$EXTERNAL_IP" ] && break
  echo "外部 IP の割り当て待ち... (${attempt}/60)"
  sleep 10
done
if [ -z "$EXTERNAL_IP" ]; then
  echo "外部 IP が割り当てられませんでした。Service のイベントを確認してください。" >&2
  kubectl describe service echo-web
  kubectl get events --field-selector involvedObject.kind=Service,involvedObject.name=echo-web
  exit 1
else
  # -f で HTTP エラー（4xx/5xx）を失敗として扱う。LB の準備中は一時的なエラーが出るため再試行する
  if ! RESPONSE=$(curl -fsS --retry 6 --retry-delay 10 --retry-all-errors "http://${EXTERNAL_IP}"); then
    echo "外部 IP からの応答が HTTP エラーまたは接続失敗でした。" >&2
    exit 1
  fi
  echo "$RESPONSE"
  # 応答に v2 が含まれることを確認する（v1 のままなら失敗にする）
  if ! printf '%s\n' "$RESPONSE" | grep -q "v2"; then
    echo "応答に v2 が含まれていません。Deployment のイメージを確認してください。" >&2
    exit 1
  fi
fi
)
# サブシェルを || の左辺に置くと set -e が無効になるため、終了ステータスは別の行で判定する
status=$?
if [ "$status" -ne 0 ]; then
  echo "途中で失敗したため、以降のコマンドは実行していません。上のエラーを確認してください。" >&2
fi
# 保存した終了ステータスを最後のコマンドの結果として返す（exit と違い Cloud Shell は閉じない）
(exit "$status")

          失敗時は診断メッセージを表示したうえで、最後の (exit "$status") により全体が保存した終了ステータス（失敗時は 0 以外）で終わります（サブシェル内の exit なので Cloud Shell は閉じません）。docker push や kubectl set image の失敗も、スクリプトや CI にそのまま伝わります。

          docker build のビルドコンテキストは、Dockerfile のあるディレクトリ（上の BUILD_DIR）を指定してください。

          10. 実務で役立つベストプラクティス総まとめ

          分野 やること 理由
          イメージ管理 latest を使わず、明示的なバージョンタグを使う どのバージョンが動いているか追跡できる
          イメージ管理 可能ならダイジェスト（@sha256:...）で固定する タグの付け替えによる意図しない変更を防ぐ
          レジストリ Artifact Registry を使う Container Registry は非推奨
          デプロイ YAML を Git で管理する 変更履歴とレビューが可能になる
          更新 ローリングアップデートと maxUnavailable: 0 を設定する 無停止で更新できる
          可用性 2 レプリカ以上にする 1 つ落ちても継続できる
          可用性 readinessProbe を設定する 準備未完了の Pod に通信を流さない
          可用性 livenessProbe を設定する 固まった Pod を自動で再起動する
          リソース requests と limits を指定する 他の Pod への影響を防ぎ、配置を適切にする
          公開 実務では Ingress と HTTPS を使う 通信の暗号化と柔軟なルーティング
          セキュリティ 最小権限のサービスアカウントを使う 侵害時の被害範囲を小さくする
          スケール HPA を設定する 負荷に応じて自動で増減できる
          ロールバック kubectl rollout undo を把握しておく 問題発生時にすぐ戻せる

          10.1 困ったときの切り戻し

          bash 
          kubectl rollout history deployment/echo-web
kubectl rollout undo deployment/echo-web

          直前のバージョン（v1）に戻せます。Deployment は過去の ReplicaSet を保持しているため、素早い復旧が可能です。

          13. まとめ

          1. イメージ名は gcr.io/<プロジェクトID>/echo-app:v2 の形にすると、build から push、デプロイまで一貫して使える。
          2. push しないとクラスタは使えない。レジストリは Cloud Shell と GKE をつなぐ共有の保管庫。
          3. Service が固定の入口なので、イメージを更新しても外部 IP は変わらない。
          4. --port は外向き、--target-port はコンテナ向き。504 の最大要因はここの食い違い。
          5. 失敗したら describe と logs を見れば、ほぼ原因が分かる。

          この流れは、実務の CI/CD パイプライン（ビルド → push → デプロイ → スケール → 監視）の縮小版です。手を動かしながら、各コマンドの「なぜ」を意識して取り組んでください。
