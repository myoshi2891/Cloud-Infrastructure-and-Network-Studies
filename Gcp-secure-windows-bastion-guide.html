Google Cloud ・ Challenge Lab ・ PCA 対策

Google Cloud チャレンジラボ解説ガイド

セキュアな Windows 環境を踏み台ホスト（Bastion Host）と VPC で構築する

対象読者
Google Cloud 初学者〜Professional Cloud Architect（PCA）受験準備中の方
ゴール
「インターネットから完全に隔離された Windows サーバー」を作り、「踏み台サーバー経由でのみ」管理できる構成を自力で構築できるようになる
範囲
ラボ画面の 6 つの Checkpoint を対象とします。公式 Tasks のうちスタートアップスクリプトを参照する VM の作成と HTTP 許可ルールの追加は扱いません（14.3 参照）

1. このラボで学ぶこと

1.1 シナリオの要約

会社が新しいアプリケーションをクラウドに展開します。あなたは Windows サーバーを安全に管理する枠組み を作る担当です。

要件 内容
本番サーバーの隔離 インターネットから 直接アクセスできない、かつ インターネットへ直接接続もできない
管理用の入口 踏み台ホスト を用意し、インターネットから RDP のみ で接続できる
踏み台の通信制限 踏み台は VPC 内の他の VM と RDP のみ で通信できる
監視システム 監視は default VPC で稼働しているため、全 VM に第2ネットワークインターフェース（default VPC への内部接続のみ）が必要

1.2 習得できるスキル

スキル 説明
カスタムモードVPCの作成 自分で IP 範囲を決めるネットワーク設計
ネットワークタグによる FW 制御 「特定の VM だけ」にルールを適用する方法
マルチ NIC インスタンス 1台の VM を複数の VPC に同時接続する構成
外部 IP の有無による隔離 外部 IP を持たせないことでインターネットから隔離
踏み台（Bastion）パターン 安全な管理アクセスの定番設計
Windows VM の初期設定 パスワードリセットと RDP 接続

2. 事前知識：用語をまず理解する

2.1 基本用語

用語 意味 たとえ話
VPC ネットワーク Google Cloud 上の仮想的なプライベートネットワーク 会社の敷地
サブネット VPC を分割した IP アドレスの区画（リージョン単位） 敷地内の建物
ファイアウォールルール 通信を許可・拒否するルール 守衛室の入館ルール
ネットワークタグ VM に付けるラベル。FW ルールの適用対象指定に使う 社員証の部署シール
外部 IP（External NAT） インターネットから到達できるグローバル IP 外から見える代表電話番号
内部 IP VPC 内でのみ使えるプライベート IP 社内の内線番号
RDP Remote Desktop Protocol。Windows の画面を遠隔操作する仕組み（TCP 3389） 遠隔で席に座る
踏み台ホスト（Bastion Host / Jump Box） 内部サーバーへ入るための唯一の中継サーバー 受付ロビー
IIS Internet Information Services。Windows 標準の Web サーバー Windows 版の Web サーバー
NIC Network Interface Card。VM のネットワーク接続口 差込口

2.2 重要な Google Cloud の仕様（必ず押さえる）

仕様 内容
暗黙の拒否ルール 受信（Ingress）は デフォルトで全拒否。許可ルールを作らない限り通信できない
暗黙の許可ルール 送信（Egress）は デフォルトで全許可
カスタムモード VPC 自動でサブネットが作られず、自分で作る。さらに デフォルトで FW ルールが 1 つもない
マルチ NIC の制約 各 NIC は 異なる VPC ネットワーク に接続する必要がある
IP 範囲の重複禁止 マルチ NIC で接続する VPC 同士のサブネット範囲は 重複不可
NIC ごとの外部 IP 外部 IP は NIC ごとに設定する。付けなければ内部専用
デフォルトゲートウェイ マルチ NIC VM では nic0 がデフォルトゲートウェイ を持つ
注意

注意: default VPC（自動モード）には default-allow-rdp（0.0.0.0/0 から TCP 3389）や default-allow-internal が最初から存在します。この事実が Task 3 の挙動に影響します（後述）。

2.3 踏み台ホストパターンとは

ポイント: 守るべきサーバーはインターネットに 一切露出させず、露出するのは「厳重に監視する踏み台 1 台だけ」にします。攻撃面（Attack Surface）を最小化する設計です。

5. Step 0：準備（リージョン・ゾーンの設定）

ラボの画面左側に リージョン と ゾーン が表示されています。Cloud Shell を開いて、環境変数に設定しておくとコマンドの打ち間違いを防げます。

5.1 Cloud Shell を開く

  1. Google Cloud コンソール右上の Cloud Shell をアクティブにする（>_ アイコン）をクリック
  2. 認証の確認が出たら 承認 をクリック

5.2 変数を設定する

補足

以下の REGION_VALUE と ZONE_VALUE は、ラボ画面に表示されている値 に必ず置き換えてください。 

export REGION="REGION_VALUE"     # 例: us-central1 ※ラボ画面の値を使う
export ZONE="ZONE_VALUE"         # 例: us-central1-a ※ラボ画面の値を使う

gcloud config set compute/region $REGION
gcloud config set compute/zone $ZONE

5.3 設定確認

gcloud config list
確認項目 期待する結果
region ラボ指定のリージョン
zone ラボ指定のゾーン
ヒント

なぜ変数にするのか: ラボごとに地域が異なるため、値を 1 か所で管理すれば コピペだけで再利用 できます。ベストプラクティスとしても、設定値のハードコードは避けます。

6. Task 1：VPC ネットワーク・サブネット・ファイアウォールルール

6.1 VPC ネットワーク securenetwork の作成

6.1.1 考え方：自動モード vs カスタムモード

項目 自動モード カスタムモード
サブネット作成 全リージョンに自動作成 自分で作成
IP 範囲 Google が決める（10.128.0.0/9 内） 自分で設計
本番推奨 非推奨 推奨
今回の選択 ❌ ✅
重要

ベストプラクティス: 本番環境では カスタムモード を使います。使うリージョンだけにサブネットを作り、IP 設計を意図的に管理できるためです。

6.1.2 コンソールでの手順

  1. ナビゲーションメニュー（≡）→ VPC ネットワーク → VPC ネットワーク
  2. VPC ネットワークを作成 をクリック
  3. 以下を入力
項目 設定値
名前 securenetwork
サブネット作成モード カスタム

6.1.3 gcloud コマンドでの手順

gcloud compute networks create securenetwork \
  --subnet-mode=custom
オプション 意味
securenetwork 作成するネットワーク名（ラボ指定）
--subnet-mode=custom カスタムモードで作成

6.2 サブネットの作成

6.2.1 IP 範囲の決め方

検討ポイント 内容
default VPC との重複 重複不可。default は 10.128.0.0/9 内を使うため、10.0.0.0/24 は安全
規模 VM は数台なので /24（約 250 台分）で十分
予約アドレス 各サブネットで先頭 2 つと末尾 2 つの計 4 アドレスは Google が予約

6.2.2 コンソールでの手順

  1. 作成した securenetwork をクリック → サブネットを追加（または作成画面の「新しいサブネット」）
  2. 以下を入力
項目 設定値
名前 secure-subnet
リージョン ラボ指定のリージョン
IP スタックタイプ IPv4
IPv4 範囲 10.0.0.0/24
限定公開の Google アクセス オン

6.2.3 gcloud コマンドでの手順

gcloud compute networks subnets create secure-subnet \
  --network=securenetwork \
  --region=$REGION \
  --range=10.0.0.0/24 \
  --enable-private-ip-google-access

# 2 つ目の NIC を接続する default VPC のサブネットでも有効化する
gcloud compute networks subnets update default \
  --region=$REGION \
  --enable-private-ip-google-access

6.2.4 確認

gcloud compute networks subnets list --network=securenetwork

# 限定公開の Google アクセスが両サブネットで True になっていることを確認
gcloud compute networks subnets describe secure-subnet --region=$REGION \
  --format="value(privateIpGoogleAccess)"
gcloud compute networks subnets describe default --region=$REGION \
  --format="value(privateIpGoogleAccess)"

# Windows ライセンス認証（kms.windows.googlecloud.com / 35.190.247.13）への経路を確認
gcloud compute routes list \
  --filter='network~"(securenetwork|default)" AND (destRange=0.0.0.0/0 OR destRange=35.190.247.13/32)' \
  --format="table(name,network.basename(),destRange,nextHopGateway.basename())"
ヒント

限定公開の Google アクセスを有効にする理由: 外部 IP を持たない Windows VM（vm-securehost の両 NIC、vm-bastionhost の default 側 NIC）は、そのままでは Google の KMS サーバー kms.windows.googlecloud.com（35.190.247.13）に到達できず、Windows のライセンス認証が失敗することがあります。両サブネットで限定公開の Google アクセスを有効にし、各 VPC に 0.0.0.0/0（または 35.190.247.13/32）宛てで次ホップが default-internet-gateway のルートが残っていることを確認してください。このルートを削除した VPC では、35.190.247.13/32 宛てのルートを個別に追加する必要があります。

6.3 ファイアウォールルールの作成（RDP 許可）

6.3.1 要件の整理

補足

「インターネットから 踏み台ホストへの RDP（TCP 3389）のみ を許可。ルールは ネットワークタグ で適切なホストに適用する」

要素 設定値 理由
ネットワーク securenetwork 作成した VPC に適用
方向 Ingress（受信） 外から入ってくる通信
アクション 許可
ターゲット 指定されたターゲットタグ bastion 踏み台だけに適用し、セキュアホストには適用しない
ソース IPv4 範囲 0.0.0.0/0 ラボでは全許可（本番は後述の通り絞る）
プロトコル/ポート TCP: 3389 RDP

6.3.2 ここが最重要ポイント：なぜタグを使うのか

タグを使わず「ネットワーク内のすべてのインスタンス」にすると、セキュアホストにも許可ルールが適用されてしまいます。最小権限の原則 に従い、必要な VM だけにタグで絞ります。

6.3.3 コンソールでの手順

  1. VPC ネットワーク → ファイアウォール → ファイアウォール ルールを作成
  2. 以下を入力
項目 設定値
名前 allow-rdp-bastion
ネットワーク securenetwork
トラフィックの方向 上り（Ingress）
一致したときのアクション 許可
ターゲット 指定されたターゲットタグ
ターゲットタグ bastion
ソースフィルタ IPv4 範囲
ソース IPv4 範囲 0.0.0.0/0
プロトコルとポート 指定したプロトコルとポート → TCP にチェック → 3389

6.3.4 gcloud コマンドでの手順

gcloud compute firewall-rules create allow-rdp-bastion \
  --network=securenetwork \
  --direction=INGRESS \
  --action=ALLOW \
  --rules=tcp:3389 \
  --source-ranges=0.0.0.0/0 \
  --target-tags=bastion
オプション 意味
--direction=INGRESS 受信ルール
--action=ALLOW 許可
--rules=tcp:3389 TCP 3389（RDP）のみ
--source-ranges=0.0.0.0/0 全 IPv4 から（ラボ用）
--target-tags=bastion bastion タグを持つ VM にだけ適用
注意

タグ名は一字一句同じに: ここで bastion と決めたら、Task 2 で踏み台を作るときにも bastion を付けます。タグが一致しないとルールが効かず RDP できません。

6.3.5 Task 1 の採点

Check my progress を 3 回（VPC、サブネット、FW ルール）クリックして確認します。

7. Task 2：Windows インスタンスのデプロイとパスワード設定

7.1 事前に理解：マルチ NIC の考え方

ルール 内容
NIC の数 1 台に複数持たせられる（マシンタイプにより上限あり）
NIC と VPC 1 NIC = 1 VPC。同じ VPC に複数の NIC は接続できない
作成タイミング VM 作成時にのみ 追加可能（後から NIC を追加できない）
最初の NIC nic0 がデフォルトルートを持つ
ヒント

なぜ後から追加できないのか: 構成ミスの手戻りが大きいため、作成時の NIC 設計が重要 です。このラボでも作成コマンドを間違えると作り直しになります。

7.2 セキュアサーバー vm-securehost の作成

7.2.1 要件

項目 設定値
名前 vm-securehost
ゾーン ラボ指定のゾーン
OS Windows Server 2016 Datacenter（Desktop Experience）
nic0 securenetwork / secure-subnet、外部 IP: なし
nic1 default / default サブネット、外部 IP: なし

7.2.2 コンソールでの手順

  1. Compute Engine → VM インスタンス → インスタンスを作成
  2. 基本設定
項目 設定値
名前 vm-securehost
リージョン / ゾーン ラボ指定の値
マシンタイプ e2-standard-2 程度（Windows は 2 vCPU 以上を推奨）
  1. OS とストレージ → 変更
項目 設定値
オペレーティング システム Windows Server
バージョン Windows Server 2016 Datacenter（Desktop Experience が付くもの。Core ではない）
ブートディスクのサイズ 50 GB 以上

  1. ネットワーキング → ネットワーク インターフェース → デフォルトを編集

    • nic0（1つ目）: ネットワーク securenetwork、サブネット secure-subnet、外部 IPv4 アドレス: なし
    • ネットワーク インターフェースを追加 → nic1（2つ目）: ネットワーク default、サブネットは default のもの、外部 IPv4 アドレス: なし

  2. 作成 をクリック

7.2.3 gcloud コマンドでの手順

gcloud compute instances create vm-securehost \
  --zone=$ZONE \
  --machine-type=e2-standard-2 \
  --image-family=windows-2016 \
  --image-project=windows-cloud \
  --boot-disk-size=50GB \
  --network-interface=network=securenetwork,subnet=secure-subnet,no-address \
  --network-interface=network=default,no-address
オプション 意味
--image-family=windows-2016 Windows Server 2016 Datacenter（Desktop Experience）
--image-project=windows-cloud Google 提供の Windows イメージ置き場
--network-interface=...,no-address（1つ目） securenetwork に接続し、外部 IP を付けない
--network-interface=network=default,no-address（2つ目） default に接続し、外部 IP を付けない
重要

最重要: no-address は 外部 IP を付けない 指定です。外部 IP がなければ、インターネットから直接到達できず、VM が外部 IP を使ってインターネットへ直接接続することもできません。

注意

注意: no-address だけでは インターネットへの送信（egress）は止まりません。接続先 VPC・サブネットに Cloud NAT やプロキシなど別の送信経路があれば、外部 IP がなくても外部へ出られます。送信も厳密に遮断する場合は、Cloud NAT の有無と Egress ファイアウォールルールもあわせて確認してください。

注意

イメージ名について: ラボ環境や時期によってイメージファミリー名が異なる場合があります。エラーが出たら gcloud compute images list --filter="family~windows-2016" で確認してください。

注意

ライフサイクルについて: Windows Server 2016 は Google Cloud でのサポート終了（EOS）とイメージの非推奨化が 2027 年 1 月 12 日 に予定されています。本ラボはラボの指示どおり Windows Server 2016 を明示的に選択します。この日以降にラボを実施する場合は、最新のラボ手順を確認するか、代替のイメージ（例: windows-2019 / windows-2022 ファミリー）の利用を検討してください。

7.3.1 要件

ゾーン ラボ指定のゾーン

7.3.3 コンソールでの手順

セキュアホストとほぼ同じ手順で、以下だけ変更します。

項目 設定値
名前 vm-bastionhost
ネットワーキング → ネットワーク タグ bastion
nic0 の外部 IPv4 アドレス エフェメラル

8.3.3 なぜこの接続が成立するのか

通信 経路 許可している設定
管理者 PC → 踏み台 インターネット → 外部 IP allow-rdp-bastion（securenetwork）
踏み台 → セキュアホスト default VPC 内の内部通信（両 VM の nic1） allow-rdp-bastion-to-securehost（default、下記で作成）
重要

補足（重要）: 踏み台からセキュアホストへの RDP は、両 VM の nic1 が接続された default VPC 側を通ります。default VPC には default-allow-internal（VPC 内の全通信を許可）が最初から存在するため、何もしなくても接続できてしまいますが、この広いルールに依存すると、セキュアホストの nic1 が default VPC の全 VM から全ポートで到達可能なままになります。次の手順で 踏み台からセキュアホストへの TCP 3389 だけ を許可するルールを作成し、そのうえで、default VPC の全 VM へインターネット（0.0.0.0/0）からの到達を許可する既定ルール default-allow-rdp（TCP 3389）・default-allow-ssh（TCP 22）・default-allow-icmp（ICMP）を削除し、RDP のみに絞るため default-allow-internal も（依存通信を個別ルールへ置き換えたうえで）削除します（踏み台への管理者 PC からの RDP は securenetwork 側の外部 IP と allow-rdp-bastion で成立するため影響しません）。 

# 踏み台の nic1（default VPC 側）の内部 IP を取得する
BASTION_DEFAULT_IP=$(gcloud compute instances describe vm-bastionhost --zone=$ZONE \
  --format="get(networkInterfaces[1].networkIP)")
echo "BASTION_DEFAULT_IP=${BASTION_DEFAULT_IP}"

# セキュアホストにルールの適用対象となるタグを付与する（11.2 と共通）
gcloud compute instances add-tags vm-securehost \
  --zone=$ZONE \
  --tags=securehost

# default VPC で、踏み台の nic1 からセキュアホストへの TCP 3389 だけを許可する
gcloud compute firewall-rules create allow-rdp-bastion-to-securehost \
  --network=default \
  --direction=INGRESS \
  --action=ALLOW \
  --rules=tcp:3389 \
  --source-ranges="${BASTION_DEFAULT_IP}/32" \
  --target-tags=securehost

広い許可ルールの削除: default-allow-internal（default VPC 内の全通信を許可）が残っていると、踏み台からセキュアホストへの RDP は上で作成したルールがなくても成立するため、接続できても新しいルールが機能している証明になりません。そこで、次の順序で進めます。

  1. default-allow-internal への依存を個別ルールへ移す: 監視エージェントやヘルスチェックなど、default-allow-internal に依存している通信を、送信元・宛先（ターゲット）・ポートを限定した個別ルールとして先に作成し、置き換えた通信が動作することを確認します（下の注意を参照）。
  2. default-allow-internal と default-allow-rdp を無効化する: default-allow-rdp はソースが 0.0.0.0/0 のため、踏み台の nic1 からの RDP にも一致します。両方を無効化しないと、新しいルールが機能しているかを確認できません。削除ではなく無効化にしておくと、問題があったときに --no-disabled ですぐ戻せます。無効化の前に、下の「削除前の確認」で default-allow-rdp に依存する他の VM がないことを確認してください。
  3. 新しい RDP セッションで確認する（両方の既定ルールを無効化した後に行う）: 踏み台から既存のセキュアホストへの RDP セッションを切断し、新しく接続し直して allow-rdp-bastion-to-securehost 経由で接続できることを確認します。ルールのロギングを有効にすると、この接続がどのルールに一致したかを Cloud Logging で確認できます。
  4. 残りの既定ルールを削除する: 確認できたら無効化した default-allow-internal と default-allow-rdp を削除し、続いて 0.0.0.0/0 から全 VM への受信を許可する default-allow-ssh（TCP 22）・default-allow-icmp（ICMP）を削除します。これらはセキュアホストの nic1 への到達経路になります。

default-allow-rdp・default-allow-ssh・default-allow-icmp は default VPC の 全 VM に適用されるため、無効化・削除の前に、同じ default VPC 上の他の VM（ラボ外の既存 VM を含む）がこれらのルールに依存した RDP・SSH・ICMP 通信を使っていないことを必ず確認してください。依存する VM がある場合は、その VM 専用にソース範囲とターゲットを絞ったルールを先に作成してから無効化・削除します。 

# 削除前の確認（手順 2 の前に実行する）: default VPC 上の VM と、各ルールの適用範囲（ターゲット未指定なら全 VM）を確認する
gcloud compute instances list --filter="networkInterfaces.network ~ /default$" \
  --format="table(name,zone.basename(),tags.items.list())"
gcloud compute firewall-rules describe default-allow-rdp --format="yaml(sourceRanges,targetTags,targetServiceAccounts)"
gcloud compute firewall-rules describe default-allow-ssh --format="yaml(sourceRanges,targetTags,targetServiceAccounts)"
gcloud compute firewall-rules describe default-allow-icmp --format="yaml(sourceRanges,targetTags,targetServiceAccounts)"
# 手順 2（手順 1 と上の確認の後に実行する）: default-allow-internal と default-allow-rdp を無効化し、新しいルールのロギングを有効にする
# 2 つの無効化とロギング有効化の 3 つすべてが成功した場合だけ STEP2_OK=true にする。1 つでも失敗したら手順 3 以降に進まない
# 途中で失敗した場合は、この手順で無効化したルール（実行前に有効だったもの）だけを有効に戻す
STEP2_OK=false
STEP2_ROLLBACK_RULES=""
step2_disable_rule() {
  local rule=$1 was_disabled
  was_disabled=$(gcloud compute firewall-rules describe "$rule" --format="value(disabled)") || return 1
  gcloud compute firewall-rules update "$rule" --disabled || return 1
  [ "$was_disabled" = "True" ] || STEP2_ROLLBACK_RULES="${STEP2_ROLLBACK_RULES} ${rule}"
}
if step2_disable_rule default-allow-internal &&
  step2_disable_rule default-allow-rdp &&
  gcloud compute firewall-rules update allow-rdp-bastion-to-securehost --enable-logging; then
  STEP2_OK=true
  echo '手順 2 が完了しました。踏み台から新しい RDP セッションでセキュアホストへ接続してから、手順 3 のログ確認を実行してください。'
else
  # 全ルールの復元に成功した場合だけ「戻した」と報告する
  STEP2_ROLLBACK_FAILED=""
  for RULE in $STEP2_ROLLBACK_RULES; do
    if ! gcloud compute firewall-rules update "$RULE" --no-disabled; then
      STEP2_ROLLBACK_FAILED="${STEP2_ROLLBACK_FAILED} ${RULE}"
      echo "${RULE} を有効に戻せませんでした。手動で --no-disabled を実行してください。" >&2
    fi
  done
  if [ -z "$STEP2_ROLLBACK_FAILED" ]; then
    echo '既定ルールの無効化またはロギングの有効化に失敗しました。無効化済みのルールは元の有効状態へ戻しました。原因を解消するまで手順 3 以降に進まないでください。' >&2
  else
    echo "既定ルールの無効化またはロギングの有効化に失敗し、次のルールが無効のまま残っています:${STEP2_ROLLBACK_FAILED}。手動で gcloud compute firewall-rules update <ルール名> --no-disabled を実行して復元するまで、手順 3 以降に進まないでください。" >&2
  fi
fi
# 手順 3: 新しい RDP セッションで接続した後に実行する。手順 2 の 3 つの更新がすべて成功した場合（STEP2_OK=true）だけログを確認する
if [ "${STEP2_OK:-false}" = true ]; then
  gcloud logging read \
    'jsonPayload.rule_details.reference="network:default/firewall:allow-rdp-bastion-to-securehost"' \
    --limit=5 --freshness=10m
else
  echo '手順 2 が完了していません（STEP2_OK が true ではありません）。ログ確認は行いません。' >&2
fi
# 手順 4: 新しい RDP セッションを確認した後に実行する
gcloud compute firewall-rules delete default-allow-internal --quiet
gcloud compute firewall-rules delete default-allow-rdp default-allow-ssh default-allow-icmp --quiet
注意

例外（RDP のみの要件を満たさない）: default-allow-internal を残す場合、default VPC 内の他の VM からセキュアホストの nic1 へは全ポートで到達できる状態が続きます。これは「RDP のみ」の要件に対する 例外 として扱い、理由と期限を記録してください（下表の効果は default-allow-internal も削除した場合のものです）。

項目 内容
ソース 踏み台の nic1（default VPC 側）の内部 IP のみ（/32）
ターゲット タグ securehost を持つ VM（セキュアホスト）のみ
効果 既定の許可ルールを削除すると、インターネットからセキュアホストの nic1 へは届かない。default-allow-internal も削除した場合は、default VPC 側でも踏み台からの RDP（3389）以外はセキュアホストへ届かない
注意

securenetwork のルールでは保護されない: 11.2 の allow-rdp-internal は securenetwork に作るルールで、セキュアホストの nic0（securenetwork 側）にしか作用しません。セキュアホストの nic1（default VPC 側）への通信は default VPC のファイアウォールルールだけで決まるため、上のとおり default 側でも許可を絞る必要があります。

ヒント

監視などで内部通信が必要な場合: default-allow-internal を削除すると、default VPC 内の他の通信も拒否されます。監視エージェントやヘルスチェックなどで必要な通信がある場合は、必要なポートだけを、送信元を必要な IP 範囲（ヘルスチェックなら Google の指定範囲など）に限定した個別のルールとして追加してください。

検証 方法 期待結果

送信経路の確認コマンド（厳密な送信遮断が必要な場合）:

# 両 VPC のルーターごとに、そのリージョンの Cloud NAT 構成を一覧する（ルーター一覧だけでは NAT の有無はわからない）
for NET in securenetwork default; do
  gcloud compute routers list --filter="network ~ /${NET}$" \
    --format="value(name,region.basename())" |
  while read -r ROUTER ROUTER_REGION; do
    echo "== ${NET} / ${ROUTER} (${ROUTER_REGION}) =="
    gcloud compute routers nats list --router="$ROUTER" --region="$ROUTER_REGION"
  done
done

# 両 VPC のルート（0.0.0.0/0 の次ホップなど）を確認する（部分的な確認。下の注意を参照）
gcloud compute routes list --filter='network~"(securenetwork|default)"' \
  --format="table(name,network.basename(),destRange,nextHopGateway.basename(),nextHopInstance.basename(),priority)"

# セキュアホストの各 NIC に実際に適用される Egress ルールを確認する（nic0 / nic1）
gcloud compute instances network-interfaces get-effective-firewalls vm-securehost \
  --zone=$ZONE --network-interface=nic0
gcloud compute instances network-interfaces get-effective-firewalls vm-securehost \
  --zone=$ZONE --network-interface=nic1
注意

ルート一覧は部分的な確認です: gcloud compute routes list には、Cloud Router が学習した動的ルート、VPC ネットワーク ピアリングでインポートされたルート、ポリシーベース ルートなど一部の種類のルートが表示されません。そのため、この一覧だけで Egress 経路の有無を判断しないでください。最終的には Google Cloud コンソールの VPC ネットワーク → ルート → 有効なルート（Effective routes） タブで、vm-securehost の nic0 と nic1 それぞれについて、そのネットワーク インターフェースに実際に適用されるすべてのルートを確認します。

踏み台からセキュアホストに RDP できない 両 VM が同じ VPC に接続されていない NIC 構成を確認（nic1 の default が両方に必要）
同上 内部 IP の入力ミス gcloud compute instances describe で再確認
パスワードリセットに失敗する 起動直後で Windows の初期設定が未完了 数分待ち、シリアル出力で完了を確認して再実行
認証に失敗する 2 台のパスワードを取り違えた 各 VM 用パスワードを再確認。必要ならもう一度リセット
外部 IP が付いてしまった no-address の付け忘れ VM を削除して作り直す（または nic の外部 IP を削除）
NIC が追加できない NIC は作成後に追加不可 VM を削除して再作成
default ネットワークが見つからない ラボ環境で削除されている ラボ環境を確認（通常は存在する）

11.2 追加推奨：securenetwork 内の RDP を明示的に許可（最小限）

「踏み台はセキュアホストと RDP のみ通信」を securenetwork 側でも明示する場合の例です（任意）。

注意

このルールは実際の RDP 経路を制御しない: 8.3.3 のとおり、踏み台からセキュアホストへの RDP は両 VM の nic1 が接続された default VPC を通ります。securenetwork に作る allow-rdp-internal は nic0 側にしか作用しないため、RDP のみに絞る効果は default 側のルール（allow-rdp-bastion-to-securehost の作成と default-allow-internal などの削除）で担保します。まずセキュアホストにネットワークタグ securehost を付与し、そのうえで送信元を bastion タグ、宛先を securehost タグに限定したルールを作成します。 

# セキュアホストにルールの適用対象となるタグを付与する
gcloud compute instances add-tags vm-securehost \
  --zone=$ZONE \
  --tags=securehost

# bastion タグの VM から securehost タグの VM への TCP 3389 だけを許可する
gcloud compute firewall-rules create allow-rdp-internal \
  --network=securenetwork \
  --direction=INGRESS \
  --action=ALLOW \
  --rules=tcp:3389 \
  --source-tags=bastion \
  --target-tags=securehost
項目 内容
ソース タグ bastion を持つ VM（踏み台）のみ
ターゲット タグ securehost を持つ VM（セキュアホスト）のみ
効果 securenetwork 側（nic0）の受信を RDP（3389）に限定することを明示できる。default VPC を通る実際の RDP 経路には作用しない
ヒント

送信（Egress）の制限は任意: 全送信を拒否するような包括的な Egress 拒否ルールは必須ではありません。追加する場合は、ターゲットを踏み台の NIC（タグ bastion など）に限定し、セキュアホストへの RDP や、監視・更新など必要な依存通信を許可したうえで設定してください。

14.3 補足：問題文の「キータスク」について

補足

問題文冒頭の公式「Tasks」一覧には「スタートアップスクリプトを参照する VM の作成」と「HTTP アクセスを許可するファイアウォールルールの追加」が含まれていますが、ラボ画面に表示される 6 つの Checkpoint（上表）には対応する項目がありません。本ガイドが扱う範囲は、この 6 つの Checkpoint だけです。本ガイドはラボの公式 Tasks をすべて網羅する完全な手順書ではなく、本ガイドだけでラボのすべての Tasks が完了するわけではありません。 スタートアップスクリプトを参照する VM の作成（対象 VM、スクリプトの配置場所、作成コマンド、完了確認）と HTTP アクセスを許可するルールの追加は本ガイドの範囲外のため、これらが必要な場合はラボの公式手順を参照してください。

以下は本ガイドの範囲外の参考例です（採点には不要）。HTTP アクセスを許可するルールを作る場合の書き方を示します。ルールは securehost タグ（13 章の一括コマンドで vm-securehost に付与）を持つ VM だけに適用されます。 

gcloud compute firewall-rules create allow-http-secure \
  --network=securenetwork \
  --direction=INGRESS \
  --action=ALLOW \
  --rules=tcp:80 \
  --source-ranges=10.0.0.0/24 \
  --target-tags=securehost

ただし「本番サーバーは当初インターネットから完全に隔離」という要件に反しないよう、ソースは内部範囲に限定しています。
