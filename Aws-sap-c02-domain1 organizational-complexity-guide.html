2.2 Step 1: 基礎用語を押さえる

用語 意味 試験でのポイント
CIDR IP アドレス範囲の表記 (例 10.0.0.0/16) VPC 間でCIDRが重複するとピアリングや TGW の経路が成立しない
サブネット VPC を AZ 単位で分割した範囲 1つのサブネットは1つの AZ にのみ属する
ルートテーブル 宛先ごとの転送先を決める表 接続を作っただけでは通信できず、経路追加が必要
Internet Gateway VPC とインターネットを結ぶ出入口 パブリックサブネットはこれへの経路を持つ
NAT Gateway プライベートサブネットから外向きのみ通信させる AZ 単位のリソース。AZ ごとに配置して耐障害性を確保する
推移的ルーティング A-B-C とつながるとき A から C へ B 経由で通信できること VPC ピアリングでは成立しない (非推移的)

2.3 Step 2: AWS グローバルインフラと Region / AZ の選び方

構成要素 説明
Region 地理的に独立した拠点。サービス提供状況や価格はリージョンで異なる
Availability Zone リージョン内の独立したデータセンター群。低遅延でつながる
Local Zone / Wavelength / Outposts 利用者やオンプレミスに近い場所で AWS を使うための拡張
エッジロケーション CloudFront や Global Accelerator などのコンテンツ配信と受付拠点

リージョン選択で確認する観点 (優先順の目安):

  1. 法規制とデータ所在地の要件 (データを国外に出せない場合は最優先)
  2. 利用者とのレイテンシ
  3. 必要なサービスや機能がそのリージョンで提供されているか
  4. 料金
  5. DR 構成を組む場合の対になるリージョンの距離と提供状況

2.4 Step 3: 複数 VPC をつなぐ方式を選ぶ

方式 仕組み 向いているケース 制約と注意点
VPC ピアリング 2つの VPC を1対1で接続 VPC が少数で単純な接続 非推移的。CIDR 重複不可。VPC 数が増えると接続数が急増して管理困難
Transit Gateway (TGW) リージョナルなハブに VPC や VPN を接続 多数の VPC とオンプレミスを集約 アタッチメントとデータ処理に課金。ルートテーブルで分離が可能
AWS PrivateLink 特定のサービスだけを非公開で公開 CIDR が重複していてもサービス単位で提供したい場合 一方向 (利用者から提供者) の接続。VPC 全体の接続ではない
VPC 共有 (RAM) 1つの VPC のサブネットを他アカウントに共有 ネットワークを一元管理して多数のアカウントで使う サブネット共有で、アカウントごとの VPC は作らない

    B -->|"はい"| C["PrivateLink を使う"]
    B -->|"いいえ"| D["CIDR は重複していないか"]
    D -->|"重複している"| C
    D -->|"重複なし"| E["接続する VPC は少数か"]
    E -->|"はい 数個程度"| F["VPC ピアリング"]
    E -->|"いいえ 多数または今後増える"| G["Transit Gateway"]
    G --> H["オンプレミス接続や分離も必要なら TGW のルートテーブルで設計"]

Transit Gateway の重要ポイント

  • 接続対象 (アタッチメント): VPC, Site-to-Site VPN, Direct Connect Gateway, 他の TGW (ピアリング), Connect (SD-WAN 向け)
  • ルートテーブルの「関連付け (association)」と「伝播 (propagation)」で、どのアタッチメント同士が通信できるかを制御できます。本番と開発を分離するときの定番手法です
  • リージョン間は TGW ピアリングで接続できます (ピアリング経路は静的ルート)
  • 検査用 VPC (ファイアウォール機器など) を経由させる場合は、往復の経路を同じ AZ に揃えるため Appliance mode を有効にします
  • VPN アタッチメントで ECMP を使うと、VPN トンネル1本あたりの帯域を超えて合算できます

    A["本番 VPC"] --> T["Transit Gateway"]
    B["開発 VPC"] --> T
    C["共有サービス VPC"] --> T
    D["検査 VPC"] --> T
    E["オンプレミス"] --> T

    T --> R2["開発用ルートテーブル 開発と共有サービスのみ"]

推移的ルーティングの考え方 (頻出)

  • VPC ピアリングでは、A-B と B-C をつないでも A から C へは通信できません
  • ピアリング先の VPC にある VPN、Direct Connect、NAT Gateway、インターネットゲートウェイを経由した通信 (エッジ間ルーティング) もできません
  • 解決策は「ハブとなる TGW を使う」か「必要な組み合わせの分だけ直接ピアリングする」です

2.5 Step 4: オンプレミスやコロケーションと接続する

方式 特徴 向いているケース 注意点
Site-to-Site VPN インターネット経由の IPsec。1接続に2本のトンネル 早く安く始めたい。バックアップ回線 標準トンネルの帯域は1本あたり約1.25 Gbps が上限。Transit Gateway または Cloud WAN にアタッチした接続では Large Bandwidth Tunnels により1本あたり最大5 Gbps。インターネット品質に依存
AWS Direct Connect 専用線でAWSに接続 安定した帯域と低遅延、大容量転送 開通に時間がかかる。標準では暗号化されない
Direct Connect + VPN 専用線上で IPsec を重ねる 専用線でも暗号化が必須の要件 構成が複雑になる。MACsec という選択肢もある
Client VPN 利用者端末向けの VPN リモートワーカーの接続 拠点間接続ではない

Direct Connect の基本構成

  • 接続 (Connection): 専用接続 (Dedicated) とホスト型接続 (パートナー経由)
  • 仮想インターフェイス (VIF): Private VIF (VPC や VGW への接続), Public VIF (AWS のパブリックサービスへの接続), Transit VIF (Transit Gateway への接続)
  • Direct Connect Gateway: 複数リージョンの VPC や TGW に1本の Direct Connect から到達させる
  • 回復性の考え方: 1拠点1回線は単一障害点です。AWS は「最大の回復性 (2ロケーションに各2回線)」「高い回復性 (2ロケーションに各1回線)」「開発とテスト用」といったモデルを提示しています
  • 低コストのバックアップには Site-to-Site VPN を併用するのが定番です

2.6 Step 5: ハイブリッド DNS (Route 53 Resolver)

オンプレミスと AWS の間で名前解決を相互に行うための仕組みです。

構成要素 役割

転送ルール (Forwarding Rule) 特定のドメインを特定の DNS サーバーへ転送するルール
Route 53 Profiles / RAM ルールや設定を複数 VPC やアカウントで共有する

ベストプラクティス
  • Resolver Endpoint は可用性のため複数 AZ に配置する
  • 転送ルールは共有サービスアカウントで一元管理し、AWS RAM で他アカウントに共有する
  • プライベートホストゾーンを複数 VPC やアカウントで使うときは、VPC の関連付けを行う (別アカウントの VPC には関連付けの認可が必要)

2.7 Step 6: ネットワーク分割と IP アドレス設計

  • 最初に全社の IP 計画を作り、VPC の CIDR を重複させないことが最大の原則です。後から変更するのは困難です
  • IP アドレス管理には Amazon VPC IP Address Manager (IPAM) を使うと、組織全体の CIDR の割り当てと重複検出を自動化できます
  • IP アドレスが不足する場合は VPC にセカンダリ CIDR を追加できます
  • コンテナ (EKS など) は Pod が VPC の IP を消費しやすく、枯渇しがちです。セカンダリ CIDR を使う、IPv6 を使うといった対策が必要です
  • セキュリティグループ (インスタンス単位、ステートフル) とネットワーク ACL (サブネット単位、ステートレス) の使い分けは Task 1.2 で扱います

2.8 Step 7: サービスエンドポイント (VPC エンドポイント)

種類 対象 仕組み 料金 オンプレミスからの利用
Gateway エンドポイント Amazon S3 と DynamoDB のみ ルートテーブルにエントリを追加 無料 不可 (ピアリング先 VPC からも不可)
Interface エンドポイント 多数の AWS サービス, 他社提供サービス, 自社公開サービス サブネットに ENI を作成 (PrivateLink) 時間料金とデータ処理料金 可 (Direct Connect や VPN 経由)
Gateway Load Balancer エンドポイント ファイアウォールなど仮想アプライアンス トラフィックをアプライアンスへ透過的に誘導 時間料金とデータ処理料金 用途による
✓
ベストプラクティス
  • VPC 内から S3 や DynamoDB へのアクセスは、まず無料の Gateway エンドポイントを検討する (NAT Gateway のデータ処理料金も削減できる)
  • オンプレミスから S3 へプライベートにアクセスしたい場合は、Interface エンドポイントを使う
  • エンドポイントポリシーで、アクセスできるバケットやアクション、組織 (aws:PrincipalOrgID) を絞り込む

3.2 Step 1: IAM の基本と権限評価の考え方

用語 意味
ID ベースのポリシー ユーザー、グループ、ロールにアタッチして許可を与える
リソースベースのポリシー S3 バケット、KMS キー、SQS キューなどリソース側に付けて、誰に許可するかを書く
信頼ポリシー IAM ロールを「誰が引き受けられるか」を定義する
アクセス許可の境界 (Permissions Boundary) IAM ユーザーやロールが持てる権限の上限を決める
SCP (サービスコントロールポリシー) Organizations で、アカウントが使える権限の上限を決める (Task 1.4 で詳述)
セッションポリシー ロール引き受け時に、そのセッションの権限をさらに絞る

評価の基本原則 (簡略化したもの):

  1. 明示的な Deny があれば、他に Allow があっても拒否される
  2. 何も許可されていなければ、デフォルトで拒否される (暗黙の Deny)
  3. SCP や権限境界は「許可を与える」のではなく「上限を決める」。上限の内側で、さらに ID ベースやリソースベースのポリシーが許可して初めて実行できる 
flowchart TD
    A["リクエスト"] --> B["明示的な Deny があるか"]
    B -->|"はい"| X["拒否"]
    B -->|"いいえ"| C["Organizations の SCP が許可しているか"]
    C -->|"いいえ"| X
    C -->|"はい"| D["権限境界やセッションポリシーの範囲内か"]
    D -->|"いいえ"| F["同一アカウントのリソースベースポリシーが<br/>IAM ユーザー ARN または引き受けたロールの<br/>セッション ARN を直接許可しているか"]
    F -->|"はい (暗黙の Deny を越えて許可。明示的な Deny は B で評価済み)"| Y
    F -->|"いいえ (ロール ARN への許可など)"| X
    D -->|"はい"| E["ID ベースまたはリソースベースのポリシーが許可しているか"]
    E -->|"いいえ"| X
    E -->|"はい"| Y["許可"]

補足: 同一アカウント内で、リソースベースポリシーが IAM ユーザー ARN (arn:aws:iam::<アカウントID>:user/<ユーザー名>) または引き受けたロールのセッション ARN (arn:aws:sts::<アカウントID>:assumed-role/<ロール名>/<セッション名>) に直接許可を与えている場合、権限境界による暗黙の Deny では制限されません。ロール ARN に対する許可は、従来どおり権限境界の範囲に制限されます。どちらの場合も明示的な Deny は優先されます。

出典: https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic.html

3.3 Step 2: クロスアカウントアクセス

別のアカウントのリソースにアクセスさせる方法は主に2つです。

方式 仕組み 向いているケース
IAM ロールの引き受け (AssumeRole) 相手アカウントのロールを一時的に引き受ける。一時認証情報が発行される 管理者や自動化処理が別アカウントを操作する。最も推奨される標準方式
リソースベースのポリシー リソース側のポリシーで、他アカウントのプリンシパルを許可する S3, SQS, SNS, KMS, ECR などで、ロールを引き受けずに直接アクセスさせたい場合

異なるアカウント間では、「リソース側のアカウントが許可」と「アクセス元のアカウントの ID ポリシーが許可」の両方が揃う必要があります。

3.6 Step 5: 暗号化戦略 (保存時と転送時)

AWS KMS の基礎

鍵の種類 管理者 特徴
AWS 所有のキー AWS 利用者からは見えない。無料。監査や制御はできない
AWS マネージドキー AWS サービスごとに作成され、自動ローテーション。ポリシーは変更できない
カスタマーマネージドキー (CMK) 利用者 キーポリシー、ローテーション、無効化、削除を制御できる。クロスアカウント共有が可能
  • エンベロープ暗号化: データ本体はデータキーで暗号化し、データキーを KMS のキーで暗号化する
  • KMS では「キーポリシー」が必須で、アクセス制御の基点になる。IAM ポリシーだけでは許可されない (キーポリシーが IAM に委任している場合のみ IAM ポリシーが効く)
  • マルチリージョンキーを使うと、リージョンをまたいで同じキーを使った暗号化と復号ができる (グローバルテーブルやDR で有効)
  • 暗号化済みの EBS スナップショットや AMI を別アカウントと共有するには、AWS マネージドキーではなくカスタマーマネージドキーが必要で、相手アカウントにキーの使用を許可する

ACM (AWS Certificate Manager)

  • TLS 証明書の発行、デプロイ、自動更新を行う。ELB, CloudFront, API Gateway などの統合サービスに関連付けて使う
  • パブリック証明書は ACM で無料発行できる。プライベート CA (AWS Private CA) で社内用の証明書を発行する選択肢もある
  • CloudFront 用の証明書は米国東部 (バージニア北部) リージョンで発行する必要がある (頻出)
  • 証明書のエクスポートの可否など仕様は更新されるため、最新の挙動は公式ドキュメントで確認すること

4.2 Step 1: RTO と RPO を理解する

4.4 Step 3: AWS Elastic Disaster Recovery (DRS)

組織のポリシーの種類

ポリシー 役割
SCP (サービスコントロールポリシー) アカウント内のプリンシパルが使える権限の上限を決める

SCP の重要ルール (頻出)

  • SCP は権限を「付与」せず、「上限」を決める。許可の付与は IAM ポリシーが行う
  • 管理アカウントには SCP は適用されない。だからこそ管理アカウントにワークロードを置かない
  • メンバーアカウントのルートユーザーを含むすべてのプリンシパルに適用される
  • サービスにリンクされたロールには影響しない
  • 階層 (ルート、OU、アカウント) のすべてで許可されている権限だけが、実効権限になる (積集合)
  • 運用しやすいのは、既定の FullAWSAccess を残して特定の操作を拒否する拒否リスト方式

問題 1

数十の VPC を持つ組織で、今後も VPC が増え続ける。VPC 間とオンプレミスの接続を一元管理したい。最も運用負荷が低い構成はどれか。

  • Aすべての VPC 同士をピアリングで接続する
  • BTransit Gateway を使い、各 VPC と VPN や Direct Connect をアタッチする
  • C各 VPC にインターネットゲートウェイを付け、インターネット経由で通信する
  • DVPC ごとに専用の VPN を作成する
答えを見る

答え: B。VPC が多数で増加する場合、ピアリングは接続数が急増し、非推移的で管理困難。Transit Gateway でハブ・アンド・スポークにする。

問題 2

オンプレミスのアプリケーションから、インターネットを経由せずに Amazon S3 へアクセスしたい。Direct Connect で接続済みである。どの構成が適切か。

  • AS3 の Gateway エンドポイントを作成する
  • BS3 の Interface エンドポイント (PrivateLink) を作成し、Direct Connect 経由でアクセスする
  • CNAT Gateway を作成する
  • DVPC ピアリングを作成する
答えを見る

答え: B。Gateway エンドポイントはオンプレミスからは利用できない。Interface エンドポイントを使う。

問題 3

管理アカウントのセキュリティ担当者が、組織内のすべてのメンバーアカウントで、CloudTrail の停止を禁止したい。最も適切な方法はどれか。

  • BOrganizations で、CloudTrail の停止を拒否する SCP を組織ルート (またはメンバーアカウントを含むすべての OU) に適用する

答え: B。予防型の統制として SCP が適切。D は検出であり、停止自体を防げない。

問題 4

RTO が15分、RPO が1分未満で、リージョン障害に備える必要がある。データベースは Amazon Aurora を使用している。コストも考慮したい。適切な構成はどれか。

  • A日次スナップショットを別リージョンにコピーする
  • BAurora Global Database を使い、副リージョンにウォームスタンバイ構成を用意する
  • C単一リージョンの Multi-AZ のみとする
  • Dオンデマンドで復旧時にインフラを再構築する
答えを見る

答え: B。リージョン間の継続的レプリケーションで RPO を短く、ウォームスタンバイで RTO を短くできる。ただしレプリケーションは非同期のため、RPO 1分未満は保証値ではなく、レプリケーション遅延に依存する一般的な目標値である (通常の遅延は1秒未満)。上限を明示的に担保したい場合は、Aurora PostgreSQL Global Database の管理対象 RPO (rds.global_db_rpo パラメータ、秒単位) で許容遅延の上限を設定し (すべてのセカンダリクラスターの遅延が目標値を超えると、いずれかが目標値内に戻るまでプライマリでのコミットがブロックされる)、遅延と CloudWatch の AuroraGlobalDBRPOLag を監視する。A と D は RTO と RPO を満たせない。C はリージョン障害に備えられない。

問題 5

事業部門ごとにコストを把握したい。タグを付けているが、Cost Explorer でタグ別の集計が表示されない。原因として最も可能性が高いものはどれか。

  • Aコスト配分タグを有効化していない
  • Bタグポリシーを作成していない
  • CSavings Plans を購入していない
  • DCompute Optimizer を有効にしていない
答えを見る

答え: A。タグを付けただけではコスト管理には反映されず、請求コンソールでコスト配分タグを有効化する必要がある。

問題 6

多数の従業員が、既存の外部 ID プロバイダーでサインインして、複数の AWS アカウントを利用する。IAM ユーザーは作成したくない。最も適切な方法はどれか。

  • Aアカウントごとに IAM ユーザーを作成する
  • BIAM Identity Center と外部 IdP を連携し、権限セットを割り当てる
  • CAmazon Cognito のユーザープールを使う
  • Dアクセスキーを共有する
答えを見る

答え: B。従業員のマルチアカウントのシングルサインオンは IAM Identity Center が標準。Cognito は顧客向けアプリの認証が主目的。
