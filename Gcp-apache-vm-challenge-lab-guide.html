      GOOGLE CLOUD CHALLENGE LAB

      Google Cloud チャレンジラボ解説ガイド：Compute Engine で Apache Web サーバーを公開する

      対象読者Google Cloud 初学者（Professional Cloud Architect 試験の土台づくりにも最適）
      所要時間の目安読む 20 分 ＋ 実習 10〜15 分

      このラボの本質：「VM を作る」→「外から入れる穴（ファイアウォール）を開ける」→「Web サーバーを入れる」→「ブラウザで確認する」という、クラウドで Web サイトを公開する最小の流れを自力で再現できるかを試すものです。

      1. このラボのゴールと全体像

      1.1 シナリオの整理

      新製品の Web サイトが完成したが、構築した担当者が退職してしまい、誰も公開できていない状況です。あなたは Apache を仮のサイト（プレースホルダー）として Compute Engine 上に公開し、インターネット越しに「Hello World!」が表示される状態を作ります。

      1.2 4 つのタスクの関係

      1.3 完成時の構成図

      訪問者のリクエストが VM に届くまでの経路です。ファイアウォールを通過できるかどうかが成否を分けます。

      1.4 各タスクで「何を学ぶか」

      タスク やること 学べること 対応する GCP サービス
      Task 1 VM を作る 名前・ゾーン・マシンタイプ・OS イメージの選択 Compute Engine
      Task 2 公開用の穴を開ける ファイアウォールルールとネットワークタグの関係 VPC ファイアウォール
      Task 3 Apache を入れる Linux サーバーとして VM を操作する基本 SSH / apt / systemd
      Task 4 動作確認する 外部 IP・HTTP と HTTPS の違い・切り分け方 ブラウザ / curl

      2. 先に押さえる基礎知識

      実習前に、この 6 つの用語だけ理解しておくと、手順の「なぜ」が見えてきます。

      用語 意味 このラボでの役割
      Compute Engine Google Cloud の仮想マシン（VM）サービス Web サーバーを動かす土台
      ゾーン (Zone) データセンターの区画（例：us-central1-a） VM の置き場所。ラボ指定のゾーンを必ず使う
      外部 IP アドレス インターネットから VM に到達するための住所 ブラウザでアクセスする宛先
      VPC ネットワーク プロジェクト内の仮想ネットワーク 本ラボでは default ネットワークを使用
      ファイアウォールルール 通信を許可・拒否するルール（既定では外部からの受信は拒否） 80 番ポートを開けるために作成
      ネットワークタグ VM に付ける目印のラベル ルールの適用対象を VM に絞り込む

      2.1 最重要ポイント：ルールとタグはセットで機能する

      このラボで最も多い失敗は「ルールは作ったのに VM にタグを付け忘れた」ケースです。ファイアウォールルールは 「どの VM に適用するか」をタグで指定します。

      2.2 HTTP と HTTPS の違い

      項目 HTTP HTTPS
      ポート番号 80 443
      暗号化 なし あり（TLS）
      このラボでの扱い こちらを使う Apache の既定状態では未設定のため接続できない

      ブラウザは https:// に自動で書き換えることがあります。URL は必ず http://外部IP で確認してください。

      4. Task 1：Linux VM インスタンスを作成する

      4.1 要件

      • Linux の仮想マシンを作る
      • 名前はラボ指定の Instance name
      • ゾーンはラボ指定の Compute zone

      4.2 手順（Cloud Console）

      詳細ステップ

      1. Cloud Console の左上 ナビゲーションメニュー（≡） を開き、Compute Engine → VM インスタンス を選びます。
      2. 初回は API の有効化に 1 分ほどかかることがあります。完了したら インスタンスを作成 をクリックします。
      3. 名前 に、ラボ画面の Instance name を 一字一句そのまま 入力します（大文字小文字・ハイフンに注意）。
      4. リージョン と ゾーン で、ラボ指定の Compute zone を選びます。
      5. マシン構成：ラボから別の指定がなければ既定（汎用 E2 シリーズ）のままで構いません。
      6. ブートディスク：既定の Debian GNU/Linux のままで OK です（Linux であることが要件）。
      7. ファイアウォール：この画面で後述の Task 2 の設定を行います（次章参照）。
      8. 作成 をクリックし、一覧でインスタンス名の左に緑のチェックが付くまで待ちます。
      9. プロジェクト ID を控える（10 章の後片付けで使用）：画面上部のプロジェクト選択ツール（プロジェクト名の表示部分）をクリックし、VM を作成したプロジェクトの ID 列の値（名前ではなく ID）をメモします。ダッシュボードの「プロジェクト情報」カードの プロジェクト ID でも確認できます。

      4.3 設定値の早見表

      項目 設定値 補足
      名前 ラボ指定の Instance name 作成後は変更不可。間違えたら作り直し
      ゾーン ラボ指定の Compute zone 採点はこの値を見る
      マシンタイプ 既定（E2 系） 指定がなければ変更不要
      ブートディスク Debian GNU/Linux（既定） apt コマンドが使える
      ネットワーク default 既定のまま
      外部 IP エフェメラル（既定） 再起動すると変わる場合がある

      4.4 gcloud での同等コマンド（Task 2 のタグ指定込み） 

      # 作成先のプロジェクト ID を記録する（10 章の後片付けで同じプロジェクトを明示指定するため）
# 未設定時は空文字または "(unset)" になるため、どちらでも VM を作成せずに止める
PROJECT_ID=$(gcloud config get-value project 2>/dev/null)
if [ -z "$PROJECT_ID" ] || [ "$PROJECT_ID" = "(unset)" ]; then
  PROJECT_ID=""
  echo "プロジェクトが未設定です。gcloud config set project を実行してから再実行してください" >&2
else
  echo "PROJECT_ID=$PROJECT_ID"
  gcloud compute instances create INSTANCE_NAME \
    --project="$PROJECT_ID" \
    --zone=ZONE \
    --machine-type=e2-medium \
    --image-family=debian-12 \
    --image-project=debian-cloud \
    --tags=http-server
fi
      オプション 意味
      --project VM を作るプロジェクト。記録した PROJECT_ID を明示し、後片付けでも同じ値を使う
      --zone VM を作るゾーン
      --machine-type CPU とメモリの組み合わせ
      --image-family / --image-project 使用する OS イメージ（Debian 12）
      --tags=http-server Task 2 で必要なネットワークタグ。作成時に付けておくと漏れない

      5. Task 2：VM への公開アクセスを有効にする

      5.1 なぜ必要か

      Google Cloud の default ネットワークには SSH（22）や ICMP などの許可ルールはありますが、HTTP（80）の許可ルールは最初からは存在しません。外部からの受信通信は既定で拒否されるため、自分で穴を開ける必要があります。

      5.2 方法 A：VM 作成画面のチェックボックスを使う（最も簡単）

      VM 作成画面の ファイアウォール 欄で HTTP トラフィックを許可する にチェックを入れます。

      自動的に行われること 内容
      ネットワークタグの付与 VM に http-server タグが付く
      ファイアウォールルールの作成 default-allow-http（TCP 80、ソース 0.0.0.0/0、ターゲットタグ http-server）が作られる

      5.3 方法 B：後から手動で設定する

      作成時にチェックを忘れた場合は、次の 2 ステップで修正できます。

      Step 1：VM にネットワークタグを追加する

      1. Compute Engine → VM インスタンス で対象 VM 名をクリックします。
      2. 編集 をクリックします。
      3. ネットワーク タグ に http-server を入力して Enter を押します。
      4. 保存 をクリックします。

      Step 2：ファイアウォールルールを作成する

      1. ナビゲーションメニューから VPC ネットワーク → ファイアウォール を開きます。
      2. ファイアウォール ルールを作成 をクリックし、下表のとおり入力します。
      項目 設定値 意味
      名前 default-allow-http この名前で作成する（最終チェックリストやコマンドと一致させる）
      ネットワーク default VM が所属するネットワーク
      トラフィックの方向 上り（Ingress） 外から VM に入る通信
      一致したときのアクション 許可
      ターゲット 指定されたターゲットタグ
      ターゲットタグ http-server VM に付けたタグと完全一致させる
      ソースフィルタ IPv4 範囲
      ソース IPv4 範囲 0.0.0.0/0 全世界からの公開（一般公開サイトのため）
      プロトコルとポート TCP、ポート 80 HTTP
      1. 作成 をクリックします。

      5.4 gcloud での同等コマンド

      # 0) 後片付け用の記録を初期化する（以前の値を引き継がない）
FW_RULE_NAME=""
# 4.4 で VM 作成時に記録した PROJECT_ID を使い、VM と同じプロジェクトを明示的に操作する（空なら止める）
echo "PROJECT_ID=${PROJECT_ID:?4.4 で記録した PROJECT_ID を設定してください}"

# 1) VM に既にあるタグを追加する。失敗した場合はファイアウォールルールを作成しない
if ! gcloud compute instances add-tags INSTANCE_NAME \
  --project="$PROJECT_ID" \
  --zone=ZONE \
  --tags=http-server; then
  echo "VM へのタグ追加に失敗しました。ファイアウォールルールは作成しません" >&2
# 2) タグ追加に成功した場合だけルールを作成し、3) 新規作成に成功した場合だけ後片付け用にルール名を記録する
elif gcloud compute firewall-rules create default-allow-http \
  --project="$PROJECT_ID" \
  --network=default \
  --direction=INGRESS \
  --action=allow \
  --rules=tcp:80 \
  --source-ranges=0.0.0.0/0 \
  --target-tags=http-server; then
  FW_RULE_NAME=default-allow-http
fi

# 4) 後片付け用に記録したルール名を表示する（空なら新規作成していない）
echo "FW_RULE_NAME=${FW_RULE_NAME:-（新規作成なし）}"

      記録の控え: FW_RULE_NAME と 4.4 の PROJECT_ID はシェル変数のため、Cloud Shell を閉じたり再接続したりすると消えます。4) で FW_RULE_NAME=default-allow-http と表示された場合は、その値と PROJECT_ID の値を控えておいてください（10 章の後片付けで使います）。

      方法 A で既に default-allow-http が作られている場合、同名で再作成するとエラー（already exists）になります。まず一覧で存在を確認してください。

      5.5 設定の確認方法

      # Cloud Console（4.2）で VM を作成した場合は PROJECT_ID が未設定のため、
# 4.2 の手順 9 で控えたプロジェクト ID に VM_PROJECT_ID を置き換えて設定する（4.4 で記録済みならその値を使う）
PROJECT_ID="${PROJECT_ID:-VM_PROJECT_ID}"
echo "PROJECT_ID=$PROJECT_ID"
gcloud compute firewall-rules describe default-allow-http --project="$PROJECT_ID" \
  --format="yaml(name,direction,allowed,sourceRanges,targetTags)"
gcloud compute instances describe INSTANCE_NAME --project="$PROJECT_ID" --zone=ZONE --format="get(tags.items)"
      確認項目 期待される結果
      ルールの内容 allowed に IPProtocol: tcp・ports: ['80']、targetTags に http-server が表示される
      VM のタグ http-server が含まれる

      ここまで終えたら、ラボ画面の Check my progress で Task 1〜2 の判定を受けましょう。

      6. Task 3：Apache Web サーバーをインストールする

      6.1 全体の流れ

      6.2 SSH で VM に接続する

      1. Compute Engine → VM インスタンス で、対象 VM の行の SSH ボタンをクリックします。
      2. 別ウィンドウでターミナルが開き、ユーザー名@INSTANCE_NAME:~$ のように表示されれば接続成功です。

      接続できない場合は、default ネットワークの default-allow-ssh（TCP 22）ルールが削除されていないか確認してください。

      6.3 Apache2 をインストールする

      VM のターミナルで次の 2 コマンドを順に実行します。

      sudo apt-get update
sudo apt-get install apache2 -y
      コマンド 意味 なぜ必要か
      sudo 管理者権限で実行 パッケージの導入には root 権限が必要
      apt-get update パッケージ一覧を最新化 古い一覧のままだと取得に失敗することがある
      apt-get install apache2 Apache2 本体を導入 Debian 系では Apache のパッケージ名は apache2
      -y 確認プロンプトに自動で Yes 対話入力を省略するため

      6.4 起動状態を確認する

      sudo systemctl status apache2
      表示 意味
      active (running) 正常に稼働中（q キーで画面を抜ける）
      inactive (dead) 停止中 → sudo systemctl start apache2 で起動
      failed 起動失敗 → sudo journalctl -u apache2 -n 50 でログ確認 
      # 参考：自動起動の設定（Debian では通常インストール時に有効）
sudo systemctl enable apache2

      6.5 「Hello World!」ページを配置する（必須）

      Debian に Apache2 を入れると、既定で「Apache2 Debian Default Page」が表示されます。ラボのゴールは「Hello World! ページが見える」状態なので、Task 4 で確認する前に、次のコマンドで必ずページを置き換えてください。 

      echo '<!doctype html><html><body><h1>Hello World!</h1></body></html>' | sudo tee /var/www/html/index.html
      要素 意味
      /var/www/html/ Apache が公開するフォルダ（ドキュメントルート）
      index.html フォルダ名だけで開いたときに最初に返されるファイル
      tee 標準出力とファイル書き込みを同時に行う（sudo 付きで権限問題を回避）

      sudo echo ... > file と書くと、リダイレクト（>）は sudo の権限外で実行されるため失敗します。tee を使うのがポイントです。

      6.6 VM 内部から先に動作確認する（切り分けの基本）

      外部から見る前に、VM の中から確認すると原因の切り分けが楽になります。

      curl http://localhost
      結果 意味 次の一手
      HTML が返る VM 内では Apache が応答している（外部から届くかは未確認） 外部から見えない場合は、7.1 で VM の外部 IP を再確認し、Task 2（ファイアウォールルールとタグ）を確認する
      接続拒否 Apache が動いていない systemctl status apache2 を確認

      ここで Check my progress を押して Task 3 の判定を受けます。

      7. Task 4：サーバーをテストする

      7.1 外部 IP アドレスを確認する

      1. Compute Engine → VM インスタンス を開きます。
      2. 対象 VM の 外部 IP 列の値をコピーします。
      # gcloud で確認する場合（VM を作成したプロジェクトの ID を明示し、選択中の別プロジェクトを参照しない）
# Cloud Console（4.2）で作成した場合は、4.2 の手順 9 で控えた ID に VM_PROJECT_ID を置き換える（4.4 で記録済みならその値を使う）
PROJECT_ID="${PROJECT_ID:-VM_PROJECT_ID}"
gcloud compute instances describe INSTANCE_NAME \
  --project="$PROJECT_ID" \
  --zone=ZONE \
  --format="get(networkInterfaces[0].accessConfigs[0].natIP)"

      7.2 ブラウザでアクセスする

      新しいタブで、次の形式の URL を開きます。

      http://EXTERNAL_IP
      入力例 結果
      http://EXTERNAL_IP 正しい（HTTP）
      https://EXTERNAL_IP 失敗（HTTPS は未設定）
      EXTERNAL_IP（スキームなし） ブラウザが https に補完する場合があり、失敗しやすい

      7.3 Cloud Shell から確認する方法

      ブラウザで表示されない場合、Cloud Shell からも確認できます（ブラウザの https 自動変換の影響を避けられます）。 

      curl http://EXTERNAL_IP

      7.4 判定

      ページが表示されたら、ラボ画面で Check my progress を押して Task 4 の判定を受けます。すべて緑になれば完了です。

      8. トラブルシューティング

      8.1 原因の切り分けフロー

      8.2 症状別の対処表

      症状 主な原因 対処
      Connection Refused（接続拒否） 通信は VM まで届いているが、Apache が TCP 80 で待ち受けていない（未インストール・停止中） sudo systemctl status apache2 と sudo ss -ltnp 'sport = :80' で待ち受けを確認し、必要なら sudo systemctl start apache2
      読み込み中のままタイムアウト ① ファイアウォールルールがない　② VM のネットワークタグとルールのターゲットタグが一致しない　③ ルールのポート・ソース範囲の設定違い　④ https://（TCP 443）で接続している（tcp:80 だけを許可しているため、443 番への通信はファイアウォールで破棄される） ルールの存在・ターゲットタグ・ポート・ソース範囲と VM のタグを確認。URL を http:// に修正
      「Apache2 Debian Default Page」が出る Apache は正常だが、6.5 の Hello World ページ配置が未実施 6.5 の手順（必須）で Hello World に置き換えてから再確認
      apt-get install が失敗する update 未実施・一時的なネットワーク障害 sudo apt-get update を実行して再試行
      default-allow-http 作成時に「already exists」 作成時のチェックボックスで既に作成済み 新規作成せず、内容が正しいか確認する
      SSH ボタンで接続できない default-allow-ssh が無い／VM が起動中でない ルールと VM の状態を確認
      Check my progress が通らない 名前・ゾーンの入力違い 指定値と完全一致しているか確認。違う場合は VM を作り直す

      9. ベストプラクティス（本番運用の視点）

      本ラボは学習用の最小構成です。実務や試験（PCA など）では、次の観点で「なぜラボのやり方は本番に向かないのか」を理解しておくことが重要です。

      9.1 ラボ構成と本番構成の比較

      観点 このラボの構成 本番での推奨 理由
      通信の暗号化 HTTP（80 番）のみ HTTPS（443） ＋ 証明書（Google マネージド証明書など） 盗聴・改ざんの防止
      公開経路 VM の外部 IP に直接アクセス 外部アプリケーション ロードバランサ 経由 可用性・スケール・DDoS 対策
      外部 IP エフェメラル（再起動で変わりうる） 静的 IP または LB の IP + DNS 名 アドレスの固定化
      VM の台数 1 台 マネージド インスタンス グループ（MIG） で複数台・複数ゾーン 単一障害点の排除
      セットアップ方法 SSH で手動実行 起動スクリプト やカスタムイメージで自動化 再現性・作業ミス防止
      SSH 接続 ブラウザ SSH OS Login ＋ IAP トンネル 認証の一元管理・ポート 22 を公開しない
      ソース範囲 0.0.0.0/0 必要に応じて Cloud Armor・IP 制限 攻撃面の縮小
      サービスアカウント 既定の Compute Engine SA 専用の最小権限 SA 権限の最小化
      VM のセキュリティ 既定 Shielded VM、最新 OS パッチの定期適用 OS レベルの保護
      管理 ラベルなし ラベル でコスト・環境・担当を識別 コスト管理・運用の見通し

      9.2 ベストプラクティスを活かした作成例（参考）

      起動スクリプトで Apache の導入を自動化し、タグと最小権限の考え方を取り入れた例です。この例の VM は Google Cloud API にアクセスしないため、サービスアカウントを接続せずに作成します。 

      gcloud compute instances create INSTANCE_NAME \
  --zone=ZONE \
  --machine-type=e2-small \
  --image-family=debian-12 \
  --image-project=debian-cloud \
  --tags=http-server \
  --labels=env=lab,app=product-site \
  --shielded-secure-boot \
  --shielded-vtpm \
  --shielded-integrity-monitoring \
  --no-service-account \
  --no-scopes \
  --metadata=startup-script='#! /bin/bash
apt-get update
apt-get install -y apache2
echo "<h1>Hello World!</h1>" > /var/www/html/index.html
systemctl enable --now apache2'
      要素 狙い
      startup-script VM 起動時に自動でセットアップ。手作業の再現ミスを排除
      --labels 環境や用途を明示し、請求や棚卸しで追跡しやすくする
      --shielded-* ブートレベルの改ざん検知を有効化
      --no-service-account / --no-scopes 既定のサービスアカウントを接続しない（--no-service-account は --no-scopes と併用が必須）。この例の VM は Google Cloud API を呼ばないため、認証情報を持たせない（最小権限）
      --machine-type=e2-small 用途に合った適正サイズ（コスト最適化）

      注意：本ラボでは指定されたとおりの手順で採点されます。上記は理解を深めるための参考例であり、ラボ本番では既定値・指示どおりに進めてください。

      9.3 ファイアウォール設計の原則

      原則 説明
      最小権限 必要なポート・必要な送信元だけを許可する
      タグ／サービスアカウントで対象を絞る 「ネットワーク全体」ではなく、該当する VM だけに適用
      意味のある名前 allow-http-from-internet のように目的が分かる名前にする
      不要なルールの棚卸し 使わなくなったルールは削除して攻撃面を減らす
      ログの活用 ファイアウォールルール ログや VPC フローログで通信を可視化する

      10. 後片付け（クリーンアップ）

      チャレンジラボのリソースはラボ終了時に自動で破棄されますが、個人プロジェクトで試した場合は課金を避けるため必ず削除してください。

      ファイアウォールルールは、このラボで自分が新規作成したものだけを削除します。作業前から存在していたルール（既存の default-allow-http を含む）は他の VM が利用している可能性があるため削除しません。5.4 のスクリプトでルールを新規作成した場合は、その時点で記録した名前（FW_RULE_NAME）を使います。

      方法 A（VM 作成画面のチェックボックス）でルールが新規作成された場合、FW_RULE_NAME は記録されません（5.4 のスクリプトを経由しないため）。作業前に default-allow-http が存在せず、このラボで初めて作られたと確認できる場合に限り、VM の削除後に gcloud compute firewall-rules delete default-allow-http --project="$PROJECT_ID" --quiet で手動削除してください。

      後片付けのコマンドは、Cloud Shell で現在選択中のプロジェクトではなく、VM を作成したプロジェクトの ID（gcloud で作成した場合は 4.4 で記録した PROJECT_ID、Cloud Console で作成した場合は 4.2 の手順 9 で控えた ID）を全コマンドに --project で明示指定します。別の Cloud Shell セッション（再接続後など）や Console だけで作業した場合は PROJECT_ID が空のため、控えから設定し直してください（gcloud config get-value project の結果で代用しないでください）。控えが無い場合は、Cloud Console の Compute Engine → VM インスタンス で対象 VM が表示されるプロジェクトを上部のプロジェクト選択ツールで選び、そのダイアログの ID 列で確認します。PROJECT_ID が空のままでは何も削除しません。 

      # 4.2 の手順 9 または 4.4 で控えた、VM を作成したプロジェクト ID に置き換えて実行する
PROJECT_ID=VM_PROJECT_ID

      5.4 とは別の Cloud Shell セッション（再接続後など）で後片付けをする場合、FW_RULE_NAME は空になっています。5.4 の 4) で FW_RULE_NAME=default-allow-http と表示されたことを確認できた場合に限り、後片付けの前に次を実行して値を設定し直します。確認できない場合は設定せず、未設定のまま進めてください（ルールは削除されません）。 

      # 5.4 の 4) の表示で新規作成を確認できた場合だけ実行する
FW_RULE_NAME=default-allow-http
      # FW_RULE_NAME は 5.4 のスクリプトでルールを新規作成したときに記録した値（方法 A や既存ルールの流用では未設定のまま）
# VM の削除が成功した（または既に削除済みだと確認できた）場合だけ、ファイアウォールルールの削除へ進む
# 全コマンドに VM 作成時に記録した PROJECT_ID を明示し、Cloud Shell で選択中の別プロジェクトを対象にしない
VM_DELETED=false
if [ -z "${PROJECT_ID:-}" ]; then
  echo "PROJECT_ID が未設定です。VM を作成したプロジェクト ID を設定するまで何も削除しません" >&2
elif ! VM_FOUND=$(gcloud compute instances list --project="$PROJECT_ID" --zones=ZONE \
  --filter="name=INSTANCE_NAME" --format="value(name)"); then
  echo "VM の存在確認に失敗しました。ファイアウォールルールは削除しません" >&2
elif [ -z "$VM_FOUND" ]; then
  # 空の一覧だけでは、ZONE や INSTANCE_NAME の置き換え間違いと区別できない。次の 3 点をすべて確認できた場合だけ削除済みとみなす
  #   1) 全ゾーンを対象にした一覧でも同名の VM が見つからない（別ゾーンに残っていない）
  #   2) 対象 VM を直接参照し、ゾーンではなくインスタンス自体の not found エラーが返る（ZONE の誤りではない）
  #   3) INSTANCE_NAME が 4.4 で作成した VM 名と一致することを利用者が明示的に確認する（名前の書き間違いではない）
  if ! ALL_ZONES_FOUND=$(gcloud compute instances list --project="$PROJECT_ID" \
    --filter="name=INSTANCE_NAME" --format="value(name,zone.basename())"); then
    echo "全ゾーンでの VM の存在確認に失敗しました。ファイアウォールルールは削除しません" >&2
  elif [ -n "$ALL_ZONES_FOUND" ]; then
    echo "同名の VM が別のゾーンに存在します（ZONE を確認してください）。ファイアウォールルールは削除しません" >&2
    printf '%s\n' "$ALL_ZONES_FOUND" >&2
  elif DESCRIBE_ERR=$(gcloud compute instances describe INSTANCE_NAME --project="$PROJECT_ID" --zone=ZONE \
    --format="value(name)" 2>&1 >/dev/null); then
    echo "VM が存在します（一覧と結果が一致しません）。ファイアウォールルールは削除しません" >&2
  elif printf '%s\n' "$DESCRIBE_ERR" | grep -q "instances/INSTANCE_NAME' was not found"; then
    # not found だけでは、INSTANCE_NAME の書き間違い（別名の VM が残っている）と区別できない。
    # 4.4 で作成した VM 名と完全に一致することを利用者が明示的に確認した場合だけ削除済みとみなす
    echo "インスタンス INSTANCE_NAME（ゾーン ZONE）は見つかりませんでした。" >&2
    read -r -p "これが 4.4 で作成した VM 名と完全に一致し、既に削除済みであれば yes と入力: " VM_ABSENT_CONFIRM
    if [ "$VM_ABSENT_CONFIRM" = yes ]; then
      echo "VM は既に削除済みです（not found と利用者の確認により判断）"
      VM_DELETED=true
    else
      echo "VM の不在を確認できませんでした。ファイアウォールルールは削除しません" >&2
    fi
  else
    echo "VM の不在を確認できませんでした。ファイアウォールルールは削除しません" >&2
    printf '%s\n' "$DESCRIBE_ERR" >&2
  fi
else
  # 削除前に対象を表示し、4.2 / 4.4 で控えた値と一致することを利用者が確認した場合だけ削除する
  echo "削除対象: PROJECT_ID=${PROJECT_ID}  ZONE=ZONE  INSTANCE_NAME=INSTANCE_NAME"
  read -r -p "このラボで控えた PROJECT_ID・ZONE・INSTANCE_NAME と完全に一致すれば yes と入力: " VM_DELETE_CONFIRM
  if [ "$VM_DELETE_CONFIRM" != yes ]; then
    echo "削除対象を確認できませんでした。VM とファイアウォールルールは削除しません" >&2
  elif gcloud compute instances delete INSTANCE_NAME --project="$PROJECT_ID" --zone=ZONE --quiet; then
    VM_DELETED=true
  else
    echo "VM の削除に失敗しました。ファイアウォールルールは削除しません" >&2
  fi
fi

# このラボで作成したルールが記録されていて、VM を削除できた場合だけ削除する
if [ "$VM_DELETED" = true ] && [ -n "${FW_RULE_NAME:-}" ]; then
  gcloud compute firewall-rules delete "$FW_RULE_NAME" --project="$PROJECT_ID" --quiet
fi
      削除対象 理由
      VM インスタンス 稼働中は CPU・メモリ・ディスクが課金対象
      ファイアウォールルール 不要な公開ルールを残さないため

      11.2 理解度チェック

      Q1. ファイアウォールルールを作ったのに接続できない。最初に疑うべきことは？

      A. VM に、ルールのターゲットタグと同じネットワークタグが付いているかです。ルールとタグが一致しないと、ルールは VM に適用されません。

      Q2. Google Cloud の VPC ファイアウォールの既定の挙動は？

      A. 受信（Ingress）は既定で拒否、送信（Egress）は既定で許可（暗黙のルール）です。外部公開するには受信を許可するルールを明示的に作成します。

      Q3. `https://EXTERNAL_IP` で開くと読み込み中のままタイムアウトする。なぜか？

      A. ファイアウォールが tcp:80 だけを許可しているため、TCP 443 への通信は VM に届く前に破棄（ドロップ）され、応答がないままタイムアウトします。URL を http:// に直してください。Connection Refused は、通信が VM まで届いたものの Apache が待ち受けていない場合に出るエラーで、HTTPS の問題とは別物です。

      Q4. Apache が動いているか VM 内で確認する最短コマンドは？

      A. curl http://localhost。応答があれば Apache は正常で、問題はネットワーク（ファイアウォール）側と切り分けられます。

      Q5. 本番環境で VM の外部 IP に直接アクセスさせない理由と代替案は？

      A. 単一障害点になり、暗号化・負荷分散・攻撃対策も難しいためです。外部アプリケーション ロードバランサ ＋ マネージド インスタンス グループ ＋ HTTPS ＋ Cloud Armor の構成が代表的な代替案です。

      まとめ

      ポイント 要点
      流れ VM 作成 → ファイアウォール（ルール＋タグ）→ Apache 導入 → HTTP で確認
      最大の落とし穴 ルールとタグの不一致、および https:// でのアクセス
      切り分けの型 VM 内の curl localhost → タグ → ルール → URL の順で確認
      本番への視点 HTTPS 化・ロードバランサ・MIG・起動スクリプト・最小権限へ発展させる
