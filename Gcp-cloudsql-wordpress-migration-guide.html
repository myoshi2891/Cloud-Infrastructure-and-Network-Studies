WordPress のローカル MySQL を Cloud SQL へ移行する

初学者向けステップバイステップ解説。ゴールは、blog 上の WordPress がローカル MySQL ではなく Cloud SQL を使って動く状態にすることです（全 5 タスク）。

1. 全体像

項目内容
現状VM blog に WordPress と MySQL が同居（/var/www/html/wordpress）
既存 DB / ユーザーwordpress ／ blogadmin（パスワードはラボ画面の指定値）
目標DB をマネージドな Cloud SQL へ移し、接続先だけ差し替える

移行後の構成

WordPress は同じ VM 上の Cloud SQL Auth Proxy（127.0.0.1:3307）に接続します。プロキシが Cloud SQL のサーバー証明書を検証したうえで暗号化し、IAM で認可します。

5 つのタスクの流れ

2. 事前準備

ラボ左パネルの Region / Zone を確認し、Cloud Shell で変数を設定します（指定値以外を使うとチェックに通らないことがあります）。

export REGION=us-central1   # ★ラボ指定の値
export ZONE=us-central1-a   # ★ラボ指定の値
export INSTANCE_NAME=wordpress-sql DB_NAME=wordpress DB_USER=blogadmin
export DB_VERSION=MYSQL_8_0
gcloud services enable sqladmin.googleapis.com

パスワードはコマンドに書かない。 --prompt-for-password で対話入力します（履歴やプロセス一覧に残りません）。Cloud Shell を再接続したら変数をもう一度設定してください。

Task 1: Cloud SQL インスタンスを作成する

判断選択理由
エンジンCloud SQL for MySQLWordPress は MySQL / MariaDB 前提
バージョン既存と同じか新しい版新しい版へは取り込めるが、逆は失敗しやすい
場所ラボ指定の Region / Zone問題文の指示
接続パブリック IP ＋ 承認済みネットワークラボでは最も簡単（本番は Private IP）

先に blog に SSH して既存の版を確認します。mysql --version はクライアントの版なので使いません。

gcloud compute ssh blog --zone=$ZONE
sudo mysql -e "SELECT VERSION();"    # 8.0.x / 5.7.x / MariaDB を確認して exit

本ガイドは既存が MySQL 8.0 以前または MariaDB の場合だけが対象で、MYSQL_8_0 を指定します。MySQL 8.4 など新しい場合は公式ドキュメントで移行方法を確認してください。

gcloud sql instances create $INSTANCE_NAME \
  --database-version=$DB_VERSION --edition=ENTERPRISE \
  --cpu=1 --memory=3840MiB --zone=$ZONE \
  --storage-type=SSD --storage-size=10GB
gcloud sql users set-password root --instance=$INSTANCE_NAME --host=% --prompt-for-password
gcloud sql instances list    # STATUS が RUNNABLE なら成功

作成には 5〜10 分かかります。エディションと構成の組み合わせでエラーになったら、メッセージを読んで --edition と --cpu / --memory を調整します。完了したら Check my progress を押します。

Task 2: データベースとユーザーを設定する

既存と同じ名前の DB とユーザーを作ると、Task 4 の変更箇所が DB_HOST だけで済みます。ただしコンソールや --database-roles なしで作ったユーザーには管理者相当の cloudsqlsuperuser が付くため、wordpress.* だけに絞ったロールを使います。

gcloud sql databases create $DB_NAME --instance=$INSTANCE_NAME
gcloud sql connect $INSTANCE_NAME --user=root    # root のパスワードを入力
CREATE ROLE 'wordpress_app';
GRANT ALL PRIVILEGES ON wordpress.* TO 'wordpress_app';
exit
gcloud sql users create $DB_USER --instance=$INSTANCE_NAME --host=% --database-roles=wordpress_app
gcloud sql users set-password $DB_USER --instance=$INSTANCE_NAME --host=% --prompt-for-password
gcloud sql connect $INSTANCE_NAME --user=root
SET DEFAULT ROLE 'wordpress_app' TO 'blogadmin'@'%';
SHOW GRANTS FOR 'blogadmin'@'%';    -- cloudsqlsuperuser が無く wordpress_app だけなら成功

既定ロールを設定しないと、ログイン時にロールが有効にならず、Task 3 のインポートが Access denied で失敗します。

Task 3: ダンプを取得してインポートする

3-1 承認済みネットワークと TLS

export BLOG_IP=$(gcloud compute instances describe blog --zone=$ZONE \
  --format='get(networkInterfaces[0].accessConfigs[0].natIP)')
gcloud sql instances patch $INSTANCE_NAME --authorized-networks=${BLOG_IP}/32 --quiet
gcloud sql instances patch $INSTANCE_NAME --ssl-mode=ENCRYPTED_ONLY --quiet
export SQL_IP=$(gcloud sql instances describe $INSTANCE_NAME --format='get(ipAddresses[0].ipAddress)')
gcloud sql ssl server-ca-certs list --instance=$INSTANCE_NAME --format='value(cert)' > server-ca.pem
gcloud compute scp server-ca.pem blog:server-ca.pem --zone=$ZONE

/32 は「その 1 台だけ」を許可する指定です。--authorized-networks は既存リストを上書きするので、複数ある場合はカンマ区切りで全部書きます。この手順が Task 3 の Check my progress の対象です。

3-2 ダンプ前にサイトを読み取り専用にする

ダンプ後に書き込まれた記事やコメントは Cloud SQL に移らず失われます。blog の Apache で POST 等と wp-cron.php を拒否し、wp-config.php に DISABLE_WP_CRON を true で追加して、検証が終わるまで書き込みを止めます（閲覧の GET / HEAD は可能です）。設定ファイルと途中で失敗した場合に中止する安全な手順は、配布している Markdown 版の 6.4 を使ってください。

3-3 ダンプと取り込み（blog 上で実行）

mysqldump -u blogadmin -p --databases wordpress --hex-blob --no-tablespaces \
  --single-transaction --set-gtid-purged=OFF --default-character-set=utf8mb4 \
  > wordpress_backup.sql
grep -c "CREATE TABLE" wordpress_backup.sql    # 約 12 個前後

SQL_IP="★Cloud Shell で表示された値"
mysql -h "$SQL_IP" -u blogadmin -p --ssl-mode=VERIFY_CA --ssl-ca=server-ca.pem \
  --default-character-set=utf8mb4 wordpress < wordpress_backup.sql
オプション意味
-pパスワードを対話入力（引数に書かない）
--hex-blobバイナリ列を 16 進で書き出し、破損を防ぐ
--single-transactionInnoDB をロックせず一貫した時点で取得
--set-gtid-purged=OFFGTID 文を出さない（MariaDB では外す）
VERIFY_CACA 証明書でサーバーを検証（REQUIRED は検証しない）

MariaDB クライアントの場合は --ssl が証明書を検証しないため、IP 直結はせず、Task 4 の Auth Proxy を先に起動して -h 127.0.0.1 -P 3307 で取り込みます。つながらずタイムアウト（ERROR 2003）になる場合は、承認済みネットワークを確認します。

取り込み後は SHOW TABLES; と投稿テーブルの件数で確認します。テーブル接頭辞は wp_ とは限らないため、wp-config.php の $table_prefix に合わせます。

Task 4: WordPress の接続先を変更する

WordPress 本体は証明書の CA を指定できず、パブリック IP への TLS 直結では検証を無効にするしかありません。そこで blog 上で Cloud SQL Auth Proxy を動かし、DB_HOST を 127.0.0.1:3307 にします。ローカル MySQL が 3306 を使うため、プロキシは 3307 です。

問題文は「DB_HOST を Cloud SQL の IP に」と求めています。本ガイドは安全性を優先したプロキシ構成です。採点で IP の値が必要な場合はラボ画面の指示に従ってください。

4-1 権限を付与する（Cloud Shell）

export BLOG_SA=$(gcloud compute instances describe blog --zone=$ZONE \
  --format='value(serviceAccounts[0].email)')
export CONNECTION_NAME=$(gcloud sql instances describe $INSTANCE_NAME --format='value(connectionName)')
gcloud projects add-iam-policy-binding "$(gcloud config get-value project)" \
  --member="serviceAccount:${BLOG_SA}" --role=roles/cloudsql.client
gcloud compute instances describe blog --zone=$ZONE --format='value(serviceAccounts[0].scopes)'

スコープに cloud-platform か sqlservice.admin が無い場合は、VM を停止してスコープを変更します（外部 IP が変わっても、プロキシ接続は承認済みネットワークに依存しません）。

4-2 プロキシを常駐させる（blog 上）

CONNECTION_NAME="★Cloud Shell で表示された値"
curl -sSfL -o cloud-sql-proxy \
  https://storage.googleapis.com/cloud-sql-connectors/cloud-sql-proxy/v2.26.3/cloud-sql-proxy.linux.amd64
echo "5533a05cdbf12f8a0cb46db34c775847a496e181d47f863284d3d02b0fad49fa  cloud-sql-proxy" | sha256sum -c -
sudo install -m 0755 cloud-sql-proxy /usr/local/bin/cloud-sql-proxy

SHA-256 が一致しなければ中止します。続けて systemd のユニットを作ります。

sudo tee /etc/systemd/system/cloud-sql-proxy.service > /dev/null <<EOF
[Unit]
Description=Cloud SQL Auth Proxy
Wants=network-online.target
After=network-online.target
[Service]
ExecStart=/usr/local/bin/cloud-sql-proxy --address 127.0.0.1 --port 3307 ${CONNECTION_NAME}
Restart=always
DynamicUser=yes
[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload && sudo systemctl enable cloud-sql-proxy \
  && sudo systemctl restart cloud-sql-proxy && sudo systemctl is-active cloud-sql-proxy

4-3 wp-config.php を更新する

定数変更理由
DB_NAME / DB_USER / DB_PASSWORD不要Task 2 で同じ値を作成済み
DB_HOST必要localhost → 127.0.0.1:3307
# バックアップは Web ルートの外（/root）に 0600 で保存する
sudo install -m 0600 -o root -g root /var/www/html/wordpress/wp-config.php /root/wp-config.php.bak
sudo sed -i -E "s/define\( *['\"]DB_HOST['\"] *, *['\"][^'\"]*['\"] *\);/define( 'DB_HOST', '127.0.0.1:3307' );/" \
  /var/www/html/wordpress/wp-config.php
grep -E "DB_HOST|MYSQL_CLIENT_FLAGS" /var/www/html/wordpress/wp-config.php

DB_PASSWORD を画面に出さないよう、確認は DB_HOST など必要な行だけにします。MYSQLI_CLIENT_SSL_DONT_VERIFY_SERVER_CERT を含む行があれば削除します。完了したら Check my progress を押します。

Task 5: 検証とトラブルシューティング

curl -I http://localhost/wordpress/    # HTTP/1.1 200 OK なら正常

ブラウザで http://<blog の外部 IP> も開きます。任意で、ローカル MySQL（サービス名は mysql / mysqld / mariadb）を止めても表示されれば、確実に Cloud SQL を参照しています。確認後は sudo systemctl start で戻せます。

移行を確認できたら、sudo a2disconf wp-readonly、構文検査、sudo systemctl reload apache2 が全て成功した場合だけ、追加した DISABLE_WP_CRON の行を消して書き込みを再開します。確認できない場合は /root/wp-config.php.bak に戻します。
